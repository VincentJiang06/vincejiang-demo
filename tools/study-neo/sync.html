用互斥锁保护同一笔状态

售票记录同时有“剩余张数”和“已售张数”。把每个整数分别锁起来，报表能读到一笔完整的售票吗？

假设座位固定为 8，正确状态必须满足“剩余＋已售＝8”。若只分别保护两个数，报表可能在卖票线程扣掉余票、尚未增加已售时读到一笔不完整的交易。让售票和报表都在同一把互斥锁（mutex）内接触这两个字段，即可维护这条跨字段的规则。

pthread_mutex_lock 成功后调用者是持有者，其他竞争者须等到锁可得。持有者调用 pthread_mutex_unlock 释放；后续成功取得同一把锁的线程能观察到释放前受保护的写入。两场无关演出可以各带一把锁，从而独立售票。跨场次操作要同时考虑两场状态和取锁顺序。

再想一步

使用前可静态初始化 pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER，或对未初始化的对象调用 pthread_mutex_init(&m, NULL)。选其中一种。检查这些函数直接返回的错误号，检查也可封装成函数。所有使用者结束且锁未被持有后，动态锁可 pthread_mutex_destroy。不要把有副作用的调用藏进可能被编译掉的 assert。

A · trylock 忙时立即返回 EBUSY。timedlock 需要绝对截止时间，超时通常返回 ETIMEDOUT。普通 mutex 由持有者解锁。

为什么锁本身需要原子操作

给锁一个标志位，0 表示空闲，1 表示占有。两个线程先读标志，再写 1，谁赢？

若测试和置位是两次独立访问，甲可在读出 0 后暂停，乙读出 0 并写 1，甲恢复后也写 1。两者都认为自己成功。让硬件把“写新值、返回旧值”实现成一个不可分的交换，所有对同一标志的交换就会排成一个顺序。初始为 0 时，当中只有第一人会取得旧值 0。

把原子交换放进循环，看到旧值 1 就重试，就得到自旋锁（spin lock）。实际实现还需要内存顺序保证，令成功获取具备 acquire 语义，释放具有 release 语义。只把几条普通 C 赋值包进名叫 TestAndSet 的函数并不能产生这种硬件保证。

/* C11，自旋锁的最小示意。 */
#include <stdatomic.h>
static atomic_flag occupied = ATOMIC_FLAG_INIT;

void take(void) {
    while (atomic_flag_test_and_set_explicit(
               &occupied, memory_order_acquire)) { }
}
void give_back(void) {
    atomic_flag_clear_explicit(&occupied, memory_order_release);
}

等待一把锁，究竟该占着 CPU 吗

单核上甲持锁时被抢占，还差 1 毫秒完成。若乙接下来忙等 5 毫秒，甲会提早解锁吗？

评价一把锁至少要分开问三件事：临界区是否始终至多一人进入，每个等待者有没有机会进入，以及空闲或争用时各付多少代价。原子交换能给出互斥；总被新人抢先的线程仍可能饥饿。单核若缺少抢占或主动让出，忙等者甚至能一直挡住持锁者运行。

多核且持锁者仍在另一核执行时，短时间自旋可以省掉睡眠和唤醒的开销。yield 把竞争者从运行态放回就绪态，调度器以后还能立即选中它。队列锁可登记等待者并 park 使它睡眠，释放者再 unpark 指定线程；登记、释放与入睡要配合好，否则唤醒可能抢在入睡前丢失。两阶段锁先短暂自旋，仍未得到锁就入队休眠。

条件变量等的是哪一句话

必须等音频索引制作完成才可读取它。若制作者比读取者先跑完，一次唤醒能留到以后使用吗？

把“索引可读”写成共享布尔式 ready，这种可检查的判断叫谓词。互斥锁 m 保护索引的发布和 ready；条件变量 cv 提供等待队列。读取者持锁检查，发现为假便调用 pthread_cond_wait(&cv, &m)。它把加入等待与放开 m 做成一个对通知方不可插入的过程，醒来后重新取得 m 才返回。

制作者持 m 填好索引、置 ready，再发 signal 并解锁。在一个等待者的场景，制作者先到时没有线程接收信号，但 ready 留下了完成的事实；读取者先到时会睡眠。若不保存 ready，迟到者可能永远睡下；若先自行解锁再去睡，中间又会留下“已经通知却无人接收”的窗口。

/* m、cv 已初始化；ready 初值为 0。单个读取者。 */
/* 读取者 */
pthread_mutex_lock(&m);
while (!ready) pthread_cond_wait(&cv, &m);
read_index();
pthread_mutex_unlock(&m);

/* 制作者 */
pthread_mutex_lock(&m);
build_index();
ready = 1;
pthread_cond_signal(&cv);
pthread_mutex_unlock(&m);
再想一步

等待终止、并回收 joinable 线程时可直接用 pthread_join。自制 ready 标志适合表达“某个阶段已完成”，它与线程终止及资源回收有不同的生命周期。条件变量可用 PTHREAD_COND_INITIALIZER 或 pthread_cond_init 初始化，全部使用者离开后再 destroy。

有界队列怎样做到不覆盖也不读空

麦克风生产音频片段，编码线程消费片段。它们速度不同，内存只准保留三个待编码片段。

有界缓冲区（bounded buffer）用容量限制生产者超前的距离。队列拥有读位置 r、写位置 w 和有效项数 n。初始化均为 0。生产者须等 n < 3，在 w 写入后令 w=(w+1)%3，n 加一；消费者须等 n > 0，在 r 取走后令 r=(r+1)%3，n 减一。整次检查与修改都在同一把锁下完成。管道的写端和读端也面对缓冲容量，只是那里的缓冲由内核管理。

使用两个条件变量 not_full 与 not_empty。生产者在 while(n==3) 中等 not_full，每次放入后 signal(not_empty)；消费者在 while(n==0) 中等 not_empty，每次取走后 signal(not_full)。消费者取得自己可安全持有的音频片段后，可释放队列锁，再花时间做音频编码；队列状态和读写下标的更改始终在锁内。容量为 1 时，这套协议就是一格交接；容量较大时，生产者可在消费者暂时忙碌时接连放入多项。

唤醒哪一个等待者才有人能继续

即使用 while 每次醒来重查，如果生产者和消费者全睡在同一个条件变量上，所有人仍可能睡着。

设只有一个槽、一个生产者 P 和两个反复取数据的消费者 C、D。P 放入物品叫醒 C，接着因槽满也上同一条队列等。C 取走物品，本应唤醒能填空槽的 P；signal 如果挑中 D，D 唯一能做的是重新等物品，C 也会在下一轮等待。程序保持了“读空前要检查”的安全性，却丢失了继续运行的机会。

两个明确的等待队列可在取物后定向唤醒生产者。另有一些情况，同一类线程的条件也各不相同，例如等待不同额度的内存。可用同一覆盖条件配合 pthread_cond_broadcast 唤醒全部，再让每个请求持锁用自己的谓词筛选。代价是额外调度和锁竞争。

再想一步

历史辅导 T05（2025T2）还讨论屏障。举例：三个线程分轮计算，每次到达时持锁增加 arrived。保存本轮 generation；最后一个到达者把 arrived 清零、generation 加一后广播，其余人在 while(自己的轮号 == generation) 中等。轮号让立即投入下一轮的快线程不会使上一轮的慢线程误等。

用初值表达可用名额与完成事件

两台机器共用一座机房，三条任务都申请开机。怎样既限制最多两条运行，又让迟到者看到早已发生的释放？

计数信号量（semaphore）记录可取走的许可。sem_wait 原子地取一份，若暂无许可便等待。sem_post 交出一份，可能让一个等待者完成 wait。无等待者时交回的许可会留下，供未来的 wait 取走。在 <semaphore.h> 中用 sem_t 声明，sem_init(&s, 0, 2) 的 0 表示同进程线程共享，2 表示一开始有两份。

初值为 1 并按取得一次、归还一次的协议使用，可保护排他资源。信号量没有 mutex 的线程所有权要求：另一线程也能 post，这使初值为 0 的信号量可以表达一次完成事件。若 worker 先 post，主线程随后 wait 直接取走；若主线程先 wait，就等 worker 的 post。一次许可只能满足一次 wait。

历史辅导 T06（2025T2）把场景延伸到独立进程。两个进程各自在私有内存中 sem_init，只会得到两个计数器。可让二者 sem_open 同一个名字；进程完成后 sem_close 自己的引用，约定的管理方 sem_unlink 名字，最后一个引用关闭后对象才会消失。已有名字用 O_CREAT 重新打开时，新的初值不会重置旧对象。无名对象跨进程共享则需要把同一 sem_t 放进共享内存，并将 pshared 置为非零。

再想一步

课件把这个自制信号量称为 Zemaphore。可用一把 mutex、一个条件变量与非负整数 credits 实现该语义。wait 持锁，在 while(credits==0) 中执行 cond_wait，之后减一并解锁；post 持锁加一，signal 后解锁。保存 credits 使先来的 post 也有效。用 POSIX sem_wait 时要检查失败，若遭信号中断可按意图在 EINTR 时重试；sem_* 一般以 −1 和 errno 报错。 sem_trywait 无可用许可时立即以 EAGAIN 失败。通过 sem_init 创建的无名对象在所有使用者离开后调用 sem_destroy。

队列需要两类许可和一把锁

缓冲区有两格，两个生产者各拿到一份空位许可。这样能保证它们写不同的位置吗？

空位许可只声明“有足够空位”，没有分配具体下标。多名生产者若同时读到 w=0，仍会覆盖同一格。设 empty 初值 N，full 初值 0，gate 是初值 1 的互斥信号量或等价 mutex。生产者先 wait(empty)，再取 gate，更新槽和写位置，放开 gate，最后 post(full)。消费者先 wait(full)，在 gate 内取物并移读位置，离开后 post(empty)。

反过来先拿 gate 再等 full 会卡住空队列：消费者持有 gate 睡眠，生产者必须拿 gate 才能填入第一项，从而永远发不出 full。sem_wait 睡眠时只等自己的信号量，不会自动释放无关的锁。与条件变量的 wait 会释放传入的 mutex 相比，这里获取顺序承担了避免闭环的责任。

/* 每一行是一项伪代码操作，假设取得许可成功。 */
produce(x):
    wait(empty)
    lock(gate)
    put(x)
    unlock(gate)
    post(full)

consume():
    wait(full)
    lock(gate)
    x = get()
    unlock(gate)
    post(empty)
    return x

允许一组读者并行，写者怎样入场

归档目录常被查询，偶尔更新。两个查询可以同时扫描目录，但改目录时不能有查询走到改了一半的节点。

读写锁的准入规则是：读者可有多名，写者入场时必须独占。用 readers 记录读者人数，用小锁 m 保护人数变化，用初值 1 的信号量 room 管理整个目录。第一个读者在 m 内把人数从 0 加到 1，并 wait(room)；其余读者增数后即可加入。每人读完再在 m 内减数，最后一个读者从 1 减到 0 时 post(room)。写者独自 wait(room)，改完 post(room)。

第一个读者申请 room 时仍持有 m，可阻止后续读者误以为已经获准而提前进入；正在写的线程不需要 m 就能释放 room。room 可能由首位读者取得、末位读者归还，正好利用信号量的无所有权特性。用 pthread_rwlock_rdlock、pthread_rwlock_wrlock 和 pthread_rwlock_unlock 可以直接表达读、写两种进入模式。

给两把叉子排顺序，为什么能破环

五名哲学家围坐，五把叉子编号 0 至 4。第 i 人进餐须同时持有 i 与 (i+1)%5 两把。怎样允许相隔的人一起吃？

每把叉子都可以看作一个初值 1 的信号量。若人人按“先取左，再取右”，可能恰好每人都先得到自己的左叉。此时 0 等 1，1 等 2，直到 4 等 0；每人都在等别人吃完，而无人可以开始吃。一个足以说明故障的执行顺序就能推翻这个协议。

统一改成先取编号较小的叉，再取较大的。前四人的次序没变；第 4 人改为先取 0 再取 4。若有环，从某把已持有的叉沿“还要取”一直走，编号必须严格递增，却还要回到起点，这是不可能的。相隔的两人仍能拿到不重叠的叉；这个证明只排除了循环等待，公平进餐还取决于机会如何分配。

程序没有卡死，结果照样会错

目录服务有两种偶发故障。一种在检查到条目有效后仍取到空值，另一种在初始化尚未结束时就开始查询。该给哪几步加约束？

第一种是原子性违例：代码需要把几个访问视为一笔操作，实际却容许别的线程插入中间。若检查与使用之间允许删除者清掉条目，两步各自单独加锁也不够。须让检查和使用共享一个临界区，删除同样持这把锁；若要把指针带到锁外，另需确保对象寿命。

第二种是顺序违例：查询必须在初始化完成之后。如果两个线程只是各持同一把锁访问，查询者仍可能先得到锁并读到未初始化状态。制作者在锁内填好数据后发布 ready，读取者在锁内等到 ready，再使用数据，就加入了所缺的先后关系。另一种办法是先初始化，再创建查询线程。

自己试一次

把 ready 定义成受锁保护的布尔量，但查询线程看到 false 仍立即取数据。修复缺少什么？

从一张等待图找到死锁的四个条件

两个归档操作都要改标签库和文件库。甲先拿到标签锁，乙先拿到文件锁。它们为何再也不能只靠调度器解开？

在资源分配图中，画线程 → 资源表示正在等待，资源 → 线程表示当前持有。现在是甲 → 文件锁 → 乙 → 标签锁 → 甲。每种锁只有一个实例，所有相关线程都停在阻塞式取锁处，谁也到不了 unlock。此时轮换 CPU 不能移动任何一条边。

一般要出现这种资源死锁，需要四个条件同时存在。互斥使同一份资源不能并用；占有并等待使线程握着已有资源申请下一份；不可剥夺表示持有的资源不会被强行撤走；循环等待使等待链首尾相接。系统支持这四种条件提示有风险，是否当下卡死仍需看具体分配。资源有多份可替代实例时，仅凭有环未必足以判定。

再想一步

这一问题常藏在封装边界里：copy(from,to) 内部先锁 from 再锁 to，另一个调用者传入相反对象。单看任意一次调用都合理，组合便能闭环。给所有对象固定排序，并让内部被调用的方法也遵守该次序。

B · 等待时间很长或暂时阻塞不足以构成死锁。必须检查有没有一组参与者只能互相等、无人能向前。

拿第二把锁失败以后怎么办

两个批处理器都需要扫描头与校准器，但不同模块的自然调用顺序恰好相反。除了让其中一方永远等，还能如何改变协议？

可以为所有资源指定全局顺序，使每次新增等待都指向更大的序号。也可以事先知道所需的整组资源，通过统一分配器一次获准全部，若不足就一件也不占；这样破坏占有并等待。代价是预先申报和更少并行机会。若用总入口锁串行各次取锁，所有参与路径都须服从同一个入口协议，释放工作不能反过来依赖入口。

不能静态排序时，先取一把，再用 trylock 尝试第二把。若为 EBUSY，释放自己已有的那把，撤销尚未提交的工作，再从头试。系统因此不需要从别人手里强拆锁。若双方每次同步退让又同步重试，则 CPU 一直忙却没有交易完成，这叫活锁。随机退避能够打散节奏，仍不是每个参与者在有限次内成功的证明。

A · trylock 本身只是探测。失败后的释放与回退才移除已持有的资源和循环等待的条件。

用 CAS 更新链表头，要重算哪一项

两条线程已各自造好新节点，打算插到同一链表最前面。如果它们都看到了旧表头 H，哪个节点会消失？

若两人都先令自己的 next=H，再相继发布 head=A 和 head=B，那么 B.next=H，A 从表头就再也走不到。可以用互斥锁把“读旧头、写 next、公布新头”组成一个临界区，也可使用原子比较交换（compare-and-swap，CAS）。CAS 只有在 head 仍等于预期旧值时才把它替换成指定新值，并报告是否成功。

成功的那一次 CAS 就是操作对其他线程生效的时刻。失败说明假设可能已过时，必须重新读头，再填写 next。原子增量同理：若从 7 出发计划写 11，有人先加 2 写出 9，我们必须以 9 为基数重算 13。实践中共享头要用原子对象，并以适当的发布及获取语义，让读者能看见已经填好的节点。

再想一步

这里固定为只插入节点，且节点在使用期间一直有效。若同时删除和回收节点，还须另外解决对象寿命及地址重新出现等问题。伪代码写成“失败时再试”，先确定 CAS 的返回约定再写循环条件。

提前避开死锁，还是发现后回滚

两颗处理器要跑四项各耗时 1 的任务。如果在运行前就知道资源需求，哪些任务可重叠？若事先不知道，又如何处理实际发生的环？

假设甲、乙都可能以任意次序持有 X 和 Y，丙只用 Y，丁不拿锁，任务彼此无需等待其他任务的输出。已掌握这个需求表时，调度器可以让甲和乙的资源占用区间错开。让甲与丙同时获准，丙即使等 Y 也不会拿着 X 反向等甲；甲乙之间则没有同时持有相反资源的机会。仅把两人分配到同一 CPU 并不充分，切换时旧线程可能仍握着锁，必须约束真正的资源持有区间。

若丙也变成需要 X、Y 且顺序不定，保守方案可把这三人的资源阶段串行化，只让丁与其中之一重叠。已知需求的回避换来可预测的安全状态，同时可能拉长完工时间。检测与恢复选择另一条路：允许请求先发生，周期性建立等待图，找到确实闭合的一组后，选择一个可回滚的事务中止并释放资源，再重试。

再想一步

线程程序若没有事务撤销机制，随便终止持锁线程可能留下半写状态；有的系统只能重启或从一致的检查点恢复。预防是用结构排除某个必要条件，回避是按已知需求选择安全准入，检测恢复处理已经发生的等待环。

已经来过的通知，该记在哪里？

只有一个工作线程 W 和一个等待者 M。W 可能先完成，M 随后才开始等待。分别用条件变量和信号量表示这一事件，初态怎么设？

展开推导
  1. 条件变量方案另设 done = false，并用同一把锁保护。W 持锁写 true 后通知；M 持锁用 while 检查 done，只有未完成才 wait。W 先完成时，M 会直接通过。
