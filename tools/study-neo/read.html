一条加法指令怎样运行？

设内存地址 40 放着一条“把寄存器 R 加 3”的指令，初始 R=5。按下运行之后谁读它？

磁盘上的程序保存代码与静态数据。装载器为进程建立地址空间，安排代码、静态数据、供动态对象使用的堆、供函数调用使用的栈。CPU 从内存取得下一条指令。冯·诺依曼模型让指令与普通数据都可存放在内存，通过总线在处理器与内存间传送。

程序计数器 PC 给出下一条待取指令的位置；取来的指令进入指令寄存器 IR。控制单元译码决定数据从哪里来，算术逻辑单元 ALU 完成加法等运算，通用寄存器短暂保存操作数和结果。状态寄存器保存条件标志等信息，后续条件分支可以利用这些标志。

操作系统概览 03 / 07

为什么应用要向内核请求服务？

一个文本编辑器要保存文件，同时另一个进程正读取同一块磁盘。若两个程序都能随意操作设备，会发生什么？

操作系统管理 CPU、物理内存和 I/O 设备，并把资源包装成应用可用的抽象。进程获得可继续执行的指令流、独立的地址空间和可按名字访问的文件。内核是能执行特权操作的部分。应用通过系统调用（system call）给出请求和参数，内核检查访问权、协调共享资源、返回结果或错误。

以保存为例，编辑器给 write 一个已打开的文件描述符、缓冲区和字节数。内核检查描述符是否可写，随后把数据交给文件系统。普通的整数加法只需要 CPU 指令；许多 C 库函数也无需每次进入内核。设计这些边界时还要衡量软件开销、失效后的恢复、不同进程间的保护、能耗及安全性。课程把移动性也列为设计考虑，例如移动设备需要在省电与及时处理输入之间权衡。

一个核心怎样让两个进程都前进？

在只有一个核心的机器上，两个程序各打印一个不同的字母，终端却出现交错的两种字母。

分时的基本动作是先暂停 A，保存其程序计数器、寄存器等上下文，再恢复 B 先前保存的上下文。以后恢复 A 时，它从暂停点继续。内核调度器选择下一位运行者，时间片到期或程序阻塞都可能触发切换。

并发表示两段工作的生命周期重叠，都能取得进展；单个核心在这个模型中每一时刻只为一个进程执行指令。在两个核心上两者还可能并行。终端上字母的先后能展示交错，却不能单凭这串字母反推核心数量或唯一调度顺序。

两个进程中相同的地址指向哪里？

甲乙各显示“我的整数位于地址 0x1000”，随后甲把整数改为 9。乙会读到什么？

一位（bit）只有 0、1 两种取值，本书的机器用 8 位组成一字节（B），每个字节有一个地址。1 KiB 是 1024 B；1 MiB 是 1024 KiB，1 GiB 是 1024 MiB。前缀 0x 表示十六进制，每一位十六进制数恰好表示四个二进制位，所以 0x10 等于十进制 16。

内存可以想成按字节编号的大数组。load 从地址取值，store 把值写到地址。程序中显示的地址通常是虚拟地址，其含义依赖当前进程的地址空间。内核设置映射，硬件据此找到物理内存中的实际位置。

假设两个进程各有一个私有变量，初值为 2。它们可以使用相同的虚拟地址，对应不同物理位置；甲的 store 只会改变甲映射到的位置。地址空间随机化也可能让同一程序两次显示不同地址。显式共享的映射则可以让多个进程访问同一份数据。

操作系统概览 06 / 07

两次加一为什么可能只多一？

音乐播放器有两条线程，各给共享计数器加一。初始为 7，先按一台只有一颗核心的小机器来推演。

线程各有自己的控制流、程序计数器和寄存器，但同一进程中的线程可以读写同一个全局变量。把加一分解成三条简化指令：从共享内存装入本线程的寄存器、寄存器加一、写回共享内存。只有第三步才改变其他线程随后能读到的值。

假设第一条线程完成加法后被时钟中断。内核保存它的寄存器和下一条指令的位置，再恢复第二条线程。第二条线程完成整次加法后，第一条仍会继续执行自己的写回；上下文保存得完全正确，过期的数值也因此被完整保留下来。

一次“保存”穿过哪些层？

程序刚显示“保存成功”，用户就断了电。下次开机，磁盘上的字节究竟取决于什么？

DRAM 是易失存储，掉电后内容会丢失。磁盘和 SSD 提供非易失存储。文件系统用普通文件存放应用字节，用目录联系名字与对象，一些设备还能通过特殊文件访问。应用打开名字获得文件描述符，写入字节，再关闭描述符。

内核需要决定数据放在哪个块、文件有多长、目录名指向哪个对象，再安排设备请求。write 成功通常意味着内核已经接收了数据。若要在返回之后承诺持久化，要同步文件，并在涉及新建或改名时考虑目录。许多文件系统用日志或写时复制维护崩溃后的结构一致性，这与某个应用指定的保存时机是两个问题。

在用户程序中调用操作系统 01 / 13

怎样辨认正在运行的是谁？

同一用户从终端启动两次播放器。磁盘上只有一份程序，系统怎样分别管理两次运行？

程序是静态的代码和初始数据。进程是一次执行，内核为它维护标识、执行上下文、地址空间和打开的资源，线程携带一条实际推进的指令流。进程被创建时形成父子关系；父进程可以创建多个子进程。

PID 在同一 PID 命名空间中标识当前这个进程，PPID 记录当前父进程的 PID，UID 关联用户身份。getpid()、getppid()、getuid() 各自返回一个数，由应用决定是否打印。Linux 下 ps 可查看进程快照，ps -l 增加 PID、PPID、状态等列，ps -a 扩大到有终端的其他进程，通常排除会话首进程。

在 fork 的哪一边继续执行？

程序先把局部整数设为 4，再执行一次成功的 fork()。父子谁会回到 main 开头？

fork 创建子进程，父子都从调用的返回点继续。父得到子 PID，子得到 0；失败则只有原进程返回 −1。父子在逻辑上各有一份可独立修改的普通用户内存，同一打开文件的描述符则可能引用同一内核打开记录。复制了哪些状态，要逐种资源判断。

画进程树时，只对实际走到下一次 fork 的分支添孩子。若两边都继续，成功一轮后每个现有进程变成两条执行流；若只有旧父继续循环，得到扇形；若只有新子继续，得到链形。父子谁先被调度不由 fork 的返回值决定。

在用户程序中调用操作系统 03 / 13

子进程退出之后还有什么留下？

后台转换任务结束后，系统还需把成功或失败告诉它的父进程。这个状态放在哪里？

从 main 返回（走到 main 结尾相当于返回 0）或调用 exit 会走 C 库正常终止路径，运行已登记的退出处理并刷新标准 I/O；_exit 直接进入低层终止。因未处理的终止信号或 abort 引发的 SIGABRT 退出，可能生成 core dump，正常退出处理程序不会依此执行。内核释放地址空间、关闭描述符并保存终止原因等供父进程领取。约定上，正常退出的状态码 0 表示成功，非零可由程序定义失败原因。

wait(&st) 等待任意可领取的子进程，waitpid(pid,&st,0) 可指定目标。成功返回子 PID；st 是编码状态，先用 WIFEXITED 或 WIFSIGNALED 区分，再取 WEXITSTATUS 或 WTERMSIG。子已经退出时可以立即领取；没有相符的子进程会报 ECHILD，受到信号中断有时需要处理 EINTR。

已经终止但尚待领取的子称为僵尸（zombie）。父先退出而子仍运行，子成为孤儿（orphan），在 Linux 中会被相应的收养进程接管，通常是 init 或已设置的 subreaper。

在用户程序中调用操作系统 04 / 13

shell 怎样让子进程换成另一个程序？

用户输入打印一行文字的命令。若 shell 自己直接变成打印程序，提示符由谁再显示？

shell 解析命令后通常 fork 一名子进程。子用 exec 家族加载另一份可执行文件，将新程序的参数放入新地址空间，从其入口开始执行；PID 延续，原来的代码、堆和栈被替换。成功的 exec 不会回到旧函数；失败才返回 −1，子进程应报告并退出。父进程仍然执行 shell。

六个常见接口是 execl、execlp、execle、execv、execvp、execve。l 表示逐项列出参数，v 表示用向量；p 形式在程序名不含斜杠时按 PATH 搜索；e 形式显式给出环境。参数向量惯例上以程序名为 argv[0]，末尾有空指针。execve 是 Linux 的底层系统调用之一，其他常见形式由库包装。

前台命令通常让 shell 等子进程完成；以 & 提交的后台命令让 shell 先发下一次提示，仍须适时回收状态。典型开启作业控制的终端把 Ctrl-C 产生的 SIGINT 送给前台进程组。

char *args[] = {"printf", "%s\n", "ready", NULL};
execvp(args[0], args);
/* 到这里表示 exec 失败；此片段位于子进程。 */
_exit(127);

指针、数组和申请到的字节怎样区分？

要装六个 int，写 sizeof(p) 还是 sizeof(*p)？一个地址变量并不会自动带来六个可写位置。

进程可以用 malloc 从堆分配器申请一段连续可用的虚拟地址，参数以字节计，类型 size_t，失败返回 NULL。分配器向内核获取较大区域后自行分拆、复用，因而一次 malloc 未必对应一次系统调用。底层 brk 设置程序 break，sbrk 按增量调整它，mmap 可建立匿名或文件支持的映射。

指针 p 存着地址，*p 表示一个元素。固定长度本地数组 a 的 sizeof(a) 是整个数组的大小；数组作为普通函数参数时通常已调整为指针。若 int 为 4 字节、指针为 8 字节，六个 int 的数组占 24 字节，指向它的指针自身占 8 字节。sizeof 的结果以字节计，对固定类型通常在编译时已知。

/* 在包含 <stdlib.h> 的 main 函数中 */
int *p = malloc(6 * sizeof *p);
if (p == NULL) return 1;
p[0] = 12;
free(p);

如何检查一段动态内存是否还能读写？

要复制字符串“red”。三个可见字符后还需要一个位置；复制完还要决定最后由谁释放。

从三个问题检查每一次读写：指针是否指向仍然有效的对象？访问是否落在对象范围内？即将读取的值是否已初始化？只声明 char *dest 没有提供目标空间。strlen("red") 是 3，但 C 字符串以零字节结尾，保存完整内容需要 4 个字节。申请成功后 malloc 的内容尚未初始化，写入完成前不能读取其中的普通未初始化整数。

free 的对象应是分配器返回且尚未释放的首地址。一个对象可以有多个指针别名，任一别名释放对象后都失效。丢掉最后一个可管理的指针会造成泄漏，重复释放和释放后访问会带来未定义行为。free(NULL) 可以安全调用，把一个指针清空也不能修复其他悬空别名。

在用户程序中调用操作系统 07 / 13

怎样给一张堆上的表扩容？

统计表从 3 项扩为 5 项。希望旧计数保留，分配失败时也还能使用旧表。

calloc(n,s) 申请 n 个大小为 s 的元素并将各字节清零，适合普通整数计数表。realloc(old,new_size) 可在原处调整，也可分配新位置并拷贝，在两种长度重叠的范围内保留内容。新增部分需自己初始化。

当新大小大于零，失败返回 NULL，旧块仍归调用方所有。先用临时指针接收返回值，确认成功才替换旧指针；成功之后按返回的新指针使用对象，也须重新取得任何指向内部元素的指针。若要释放所有容量，直接 free 可清楚表达意图。

在用户程序中调用操作系统 08 / 13

打开文件时，返回的小整数指向哪里？

把六个字节 ABCDEF 存入文件，同一进程两次 open 它。读第一份描述符会移动第二份的读取位置吗？

普通文件是可寻址的字节序列，目录把文件名关联到同一文件系统内的 inode 编号。路径标识名字，open 将一次打开变成进程的非负文件描述符（fd）。描述符是进程表的下标，指向内核的打开记录；其中保存当前偏移与打开状态，记录继续指向文件对象。分别 open 通常生成独立记录。在课件的 Unix System V 图中，这两层分别称作进程文件描述符表（FDT）和系统打开文件表（SFT），后者再引用内存中的 inode。

open 的访问模式如 O_RDONLY 或 O_WRONLY；O_CREAT 在缺少文件时创建，需另传权限 mode，实际权限还受 umask 影响；O_TRUNC 在合适的可写打开中将原文件长度清零。read/write 指明 fd、缓冲区和请求字节数，返回实际传输量，可能短读或短写；读取普通文件遇到末尾返回 0，错误返回 −1。close 释放本进程的一个描述符。

对普通文件，成功读写会让当前位置增加实际传输量。lseek(fd,d,whence) 可将它设为 d（SEEK_SET）、当前值加 d（SEEK_CUR）或文件大小加 d（SEEK_END），成功返回新位置。管道没有这种可寻址位置。

怎样让普通程序把输出写到文件？

命令写入标准输出 1。shell 如何在启动它之前，把这一次输出送往 report？

通常 0、1、2 分别是标准输入、标准输出和标准错误。重定向只需让描述符 1 指向目标文件的打开记录。dup(fd) 把同一记录复制到当前最小空闲描述符；dup2(fd,target) 直接把指定 target 安装为副本，适合明确重定向。别名共享同一打开记录以及其中的偏移。

假设原先 0、1、2 都关联终端，打开 report 得到 3。在子进程中关闭 1 后 dup(3) 会占据 1；另一种写法是直接 dup2(3,1)。关闭多余的 3 后，1 仍指向目标。exec 成功时一般会保留未设 close-on-exec 的描述符，新程序写 1 就到 report，写 2 仍到原终端。

为什么管道已经没数据，读者还在等？

用一条管道把生产者的标准输出接到计数程序的标准输入。生产者结束之后，读者是否一定收到 EOF？

先声明 int p[2]，再调用 pipe(p)。成功返回 0，同时把读端描述符放进 p[0]、写端放进 p[1]；失败返回 −1。内核维护有容量的单向字节流，没有消息边界；一次写的内容可能分几次读。先建立管道，再 fork，可以让不同进程继承指向同一管道两端的引用。生产者把写端安到 1，消费者把读端安到 0，随后各自关闭多余端点再 exec。

假设 shell 另行创建两名子进程，它自己也要关闭原有两端，再等待两者。正常阻塞模式下，空管道只要还有写端就会等；数据耗尽且所有写端关闭，read 返回 0。满管道上的写可能阻塞；所有读端关闭后再写会触发 SIGPIPE，若忽略该信号则 write 报 EPIPE。因此要先让两端都能运行，不能先等生产者结束才启动消费者。

再想一步

以 ls -l | wc -l 为例，ls 将目录列表写到 1，wc 从 0 读取并统计换行数。课件的独立演示程序只 fork 一次，让原进程执行 ls，子进程执行 wc；交互式 shell 自己还要发下一条提示时，通常保留 shell 并另建两个命令进程。两种安排都使用相同的读写端协议。

文件的原子替换和掉电持久各靠什么？

读者正在打开一份配置。更新程序不想让读者看到只写了一半的新版本，还希望掉电后名字可恢复。

直接截断原文件再写会有一段时间让其他打开者看到短文件。可以在目标的同一目录创建独立临时文件，完整写入新内容，检查每次实际写出的字节，并完成 fsync(tempfd)。fsync 成功意味着系统按接口要求完成该文件的数据及必要元数据同步。

再用 rename 把临时名替换为正式名。在同一文件系统的这个替换操作中，按正式名打开的读者会找到完整的旧对象或新对象；早先已打开的旧描述符继续引用旧对象。若还需让目录项的更新在掉电后持久，在支持此语义的系统中再 fsync 父目录。各步骤的错误都应处理。

怎样列目录、读属性和删除目录？

对一个目录运行 ls，程序如何先找到名字，再询问其中一个文件的所有者和长度？

目录也是文件系统对象，它保存名字到 inode 的映射。. 表示当前目录本身，.. 表示父目录，在普通根目录两者都回到根。mkdir(path,mode) 建目录；rmdir(path) 要求目标除特殊项外为空。普通文件的名字用 unlink 移除。绝对路径从根开始，相对路径从进程的当前目录开始。

stat(path,&s) 通过路径查属性，fstat(fd,&s) 通过已有描述符查。st_mode 含类型和权限，st_uid 和 st_gid 为属主属组，st_dev 与 st_ino 合起来识别文件，st_size 为逻辑字节数，st_nlink 为硬链接数，在 Linux 上，st_blocks 按 512 字节单位记录已分配空间，st_blksize 给出建议 I/O 大小。特殊设备文件还可用 st_rdev 标识它代表的设备。atime 记录访问，mtime 记录内容修改，ctime 记录状态变更。

硬链接和符号链接在改名后各会怎样？

draft 和 saved 是同一个文件的两个硬链接，另有一个符号链接 current 保存字符串 draft。删除名字 draft 后还能打开谁？

同一文件系统内的硬链接是指向同一 inode 的另一个目录项。link(old,new) 建立新名字并增加硬链接数，写任一名字都改变同一对象。unlink 只删除一个名字并使计数减一；计数为零且不再有打开引用后，空间才可最终回收。通常不允许用户给目录建立硬链接，以免破坏目录树。不同文件系统的 inode 编号各自解释，硬链接无法跨越该边界。

符号链接有自己的 inode，内容是目标路径字符串，长度通常是该字符串的字节数。路径解析到它时会继续寻找目标；相对目标从链接所在目录解释。它可指向目录或跨文件系统，也能在目标消失时作为悬空链接继续存在。stat 通常跟随符号链接，lstat 可查看链接本身。若只把 draft 改名为 final，saved 作为硬链接仍指向同一 inode；符号链接 current 内保存的字节仍拼作 draft，在原位置找不到它就会悬空。

一块空盘应拿哪些块记账？

设有 32 个各为 4 KiB 的块，编号 0 到 31。用户要把一小段文字保存为 note。只把文字放到某个块里，重启后能找到它吗？

磁盘提供可定位的块，文件系统给这些块规定用途。数据块保存文件字节，也可保存目录的内容；inode（索引节点）保存一个对象的类型、大小和数据位置；目录条目把名字对应到 inode 号。还要记录哪些位置已经占用，否则下次分配可能盖住旧数据。

超级块（superblock）提供这套格式的基本参数，例如块大小、inode 表的位置与数量等。挂载时，内核从约定位置读它并校验格式，然后才知道如何解释其他块。理解一个文件系统可以分两步：先画出盘上结构，再对 open、read、write 逐个追踪它们访问的结构。

文件系统如何组织磁盘 02 / 07

从 inode 号怎样算出实际读盘地址？

沿用每块 4096 字节、inode 表从物理块 3 开始、每个 inode 占 256 字节的卷。要查按零起算的 inode 21。

inode 表是定长记录数组。在这张从 0 编号的教学表中，目标相对表首的字节位移为 inode 号乘记录大小；加上表首的盘上字节地址，得到记录的绝对位置。若设备以扇区为寻址单位，还要把要读的文件系统块起点换成扇区号。文件系统块、设备扇区和 inode 槽是三种不同单位。

加载记录后可读类型、大小、分配情况、链接数、属主属组、权限和时间，以及指向数据的索引。经典 ext2 的字段还包括删除时间、标志、版本和 ACL 等，块地址区可容纳 15 个 4 字节值。文件名属于目录记录；Unix 的 ctime 表示状态变更时间，创建时间要看文件系统是否另有字段。实际 ext2 从 inode 1 编号，分配到块组，查表时先用 inode 号减 1 分解出块组号和组内槽号，再用该组的表首地址计算。

文件系统如何组织磁盘 03 / 07

小 inode 靠什么指向巨型文件？

若一个 inode 只有十几个地址槽，只要文件变大就得改写整个 inode 表格式吗？

直接指针指向真正装文件字节的块，一级间接指针指向一个装块号的索引块。二级间接指针先指到一块一级索引块号，再分两步得到数据；三级以此类推。小文件只付直接寻址的成本，较大的文件才分配索引块。

每块 B 字节、每个块号 P 字节，索引块的分支数为 K＝B/P。配置 D 个直接加一级、二级、三级各一个时，地址结构所能表示的数据块数是 D＋K＋K²＋K³，数据字节上限再乘 B。索引块占用磁盘，但它们本身不算文件内容字节；实际文件上限还可能受大小字段与实现限制。

以 B=4096、P=4、D=12 为例，K=1024，直接部分覆盖 48 KiB，单间接额外 4 MiB，双间接额外 4 GiB。很多小文件和少数占用大量空间的大文件可以共存，这解释了分层设计的取舍。也有设计按连续范围建 extent，用“起点、长度”描述多个相邻块，例如 ext4。课件还用 ext2、ext3、WAFL 和传统 Unix 文件系统举出多级索引的应用。它引用的工作负载里，小文件数多、少数大文件占据多数数据字节，目录的条目数通常也不大；这些是选取索引结构的观测依据。

给定 offset 和 count，实际读哪些数据块？

文件有两个直接槽，后面接一级索引。设块为 1000 字节，仅为方便手算。直接槽依次是物理块 40、7，间接索引块 90 的头两项是 18、51。

从 offset 开始要 count 个字节，它们占半开区间 [offset, offset＋count)。先将结束位置截到文件大小；若区间为空就没有需要的数据块。非空时最后一个字节编号是实际终点减一。分别用首、尾字节编号整除块大小，得逻辑块范围，首字节编号取余得第一次读取的块内位移。

对逻辑块 i，若 i<2 则查 direct[i]，否则查 indirect[i−2]。问“哪些块包含请求的文件字节”时只列数据块；若问冷缓存下所需磁盘访问，才把索引块等元数据另计。逻辑上相邻的字节所属物理块可以离得很远。

内核怎样挨个解释路径里的名字？

一份训练日志名为 /runlog/day。已知根 inode 为 2，根的目录数据在块 15，runlog 的 inode 为 9，目录数据在块 20。

目录数据保存一系列名字和 inode 号的配对。变长目录项还可能包含记录长度和名字长度；沿记录长度走，才能跳过填充找到下一条。新目录含指回自己的 . 和指向父目录的 ..；在这个模型中根的 .. 指向根。目录的 inode 保存指向上述目录数据的块号。

一次创建与扩写要改哪些账本？

目录已经有空间存一个名字，新文件从零字节增长到一个完整数据块。需要分配哪些不同的资源？

inode 位图一位对应一个 inode 槽，数据位图一位对应一个可分配数据块，在本例中 0 为空、1 为已用。创建空文件先找空闲 inode，标记并初始化它，然后把名字和编号写入父目录，并维护父目录的属性。目录已有余位时可不再分配新的目录数据块。

向文件末尾第一次写入数据时，分配器才选一个数据块，更新位图，把新块号与新大小记入 inode，写入数据。预分配可以一次保留连续多个块，帮助随后顺序增长；若随后没有用到，暂时占用的空间也要处理。原位覆盖一个已有数据块则通常省去数据块分配。

为什么重读更快，而快速写完仍可能丢失？

同一进程先后两次读取 /runlog/day 的开头。第二次系统调用仍会返回字节，可是设备未必收到新的读命令。

系统可以把 inode、目录项及文件数据块留在 DRAM；命中时可从 RAM 取出，避免读盘。深路径的冷访问逐级打开目录，缓存路径和热点结构后，重复查找的物理 I/O 会大幅下降。固定划分的缓存可能一侧闲置、另一侧紧张；统一页缓存让内存可以随使用情况动态分配。

read 根据打开记录的偏移与 inode 寻到数据，将字节交给程序，推进偏移，某些策略还会更新时间戳。close 释放描述符。写则把相关缓存标为脏，延后合并多个更新、重排设备请求。最终要持久化的新内容仍须到设备，fsync 让调用者在明确的位置等待同步。直接 I/O 可绕过某些缓存，但其持久保证仍取决于所用接口。

CPU 到设备之间经过什么？

插上一块 USB 存储，CPU 怎样才能和设备说同一种“语言”？

总线是一条在硬件部件之间传递地址、数据和控制信息的通道。在简化的分层图中，CPU 经内存总线访问主存，高带宽的一般 I/O 互连可连接图形等设备，外围总线或接口再接存储和其他外设。PCI、SATA、USB 等服务的设备、带宽与连接要求不同，具体机器布线会变化。

如何和只提供几个寄存器的设备交谈？

一台标签打印设备要接收一个字节，再执行打印。驱动需要区分“可接收”“传入的数据”和“立即开始”。

状态寄存器（status）报告忙、就绪或出错等条件；数据寄存器（data）用于传入或取回数据；命令寄存器（command）指定设备要做的动作。寄存器由设备解释，对同一个地址读和写甚至可能有不同语义。必须按该设备的协议操作。

先确认设备可接受参数，再写数据，然后写命令启动，最后等待完成并检查结果。在端口映射方案中，x86 用 in/out 等专门指令访问 I/O 端口。内存映射 I/O（MMIO）把寄存器安排在地址空间里，内核可通过合适的 load/store 和平台 I/O 访问原语操作它；这些地址对应硬件而非普通 RAM。

I/O 设备与存储 03 / 07

用轮询还是中断等完成？

一次磁盘读取要等很久，CPU 还有别的工作。一旦提交请求，CPU 用这段时间做什么？

轮询（polling）由 CPU 重复读取状态寄存器，直到条件满足。控制流简单，完成时能很快发现，但轮询的时间无法同时拿去运行其他任务。中断（interrupt）由设备向处理器报告事件；内核可以先阻塞等待者，调度另一项工作，到中断时运行处理程序、确认完成并唤醒等待者。被唤醒表示重新具备运行资格。

哪种方式更省 CPU 取决于等待时长、检测延迟、是否有其他就绪任务，以及进入处理程序和调度的开销。假设一次中断路径共用 4 微秒 CPU，忙等 1 微秒可更便宜；若设备需 100 微秒，就能让大部分时间用于别的工作。真实系统还可先短暂轮询再睡眠。

I/O 设备与存储 04 / 07

中断解决了等待，谁来搬运大块数据？

控制器已经愿意接收一张图的 64 KiB。CPU 是否还要亲自把每个字搬给设备？

程序控制 I/O（PIO）由 CPU 执行读写，逐段把数据在内存与设备之间传送，字数越多越占用 CPU。DMA（直接内存访问）让 DMA 引擎或具备总线主控能力的设备按驱动设置的地址、长度、方向传输。CPU 仍负责建立请求、准备设备可访问的缓冲区并检查完成。

例如 64 KiB＝65536 字节，按每次 4 字节的简化 PIO 循环需搬 16384 次。DMA 把这些数据移动操作交给硬件，CPU 在传输期间可以处理其他进程。内存与互连带宽仍然会被消耗。传输结束后的通知能用中断；缓冲区转交、介质写完、数据跨掉电持久是可能不同的时刻。

I/O 设备与存储 05 / 07

为何文件系统无需认识每一种硬盘？

同一段读文件代码运行在使用两种不同存储控制器的机器上。到底是谁把一次 read 翻译成设备命令？

应用提交 POSIX 风格的 open/read/write/close。文件系统解释目录、inode 和文件偏移，把文件的逻辑范围转成逻辑块请求。通用块层整理请求，具体设备驱动再把“读这些块”翻译为 SCSI、ATA 等控制器能执行的协议。设备完成后，结果沿相反方向交回上层。

接口使新型号设备可以接入既有文件系统；代价是如果通用接口没有表达某种专用功能，普通请求通常用不到它。驱动需要处理不同设备的状态、错误、并发和完成顺序。运行在内核里的驱动若有错误，也可能影响整个系统的可靠性。

I/O 设备与存储 06 / 07

怎样读懂传统 IDE 的一次扇区请求？

简化 IDE 控制器要从第二个驱动器读取 LBA 0x0123456 的一个扇区。一个块号如何被写进几个短寄存器？

LBA 是逻辑块地址。传统 IDE 的示例端口中，0x1F2 接收扇区数，0x1F3、0x1F4、0x1F5 接收 LBA 的低、中、高三个字节；0x1F6 还携带高四位、设备选择及 LBA 模式。0x1F7 写入时是命令、读取时是状态；0x1F0 传数据，0x1F1 可读错误细节，设备控制寄存器在 0x3F6 可用于控制复位和中断屏蔽。

等待时须符合协议，如 BSY 清零且 DRDY 置位。发读写命令后，数据阶段看 DRQ；写入时主机在设备要求数据后通过数据口发送，读出时等待数据就绪并读取。若状态中 ERR 置位，再读错误寄存器辨别 ABRT（命令中止）、UNC（不能纠正的数据错误）等。DF 表示设备故障。一个操作也可能需要多次中断。例如状态字是 0x48（二进制 01001000），位 7 的 BSY 为 0，位 6 的 DRDY 为 1，位 3 的 DRQ 为 1，位 0 的 ERR 为 0。处于这一数据阶段时，主机按已发命令的方向传输数据。

再想一步

状态字的常见布局从高到低为 BSY、DRDY、DF、DSC、DRQ、CORR、IDX、ERR；历史设备还以 BBK、UNC、MC、IDNF、MCR、ABRT、TK0NF、AMNF 等位报告具体错误。应按目标设备版本解释。 示例驱动对 0x3F6 写 0，使屏蔽位 nIEN 清零、允许设备发完成中断。写这个控制口本身并不代表本次请求已经完成。

驱动怎样让排队、睡眠和完成配对？

甲提交读取扇区 A，乙紧接着提交写入扇区 B。简化 IDE 驱动一次只能处理队首。谁唤醒甲，又是谁开始乙的请求？

每个缓冲对象记录目标扇区、数据、队列链接以及状态。VALID 表示缓冲中有有效内容，DIRTY 表示内存中有待写出的修改。用锁保护请求队列和状态。提交者入队，若成为队首便启动设备；如果请求尚未完成就用能原子释放锁并等待的睡眠操作，醒来后重新取得锁并再检查条件。在代码里，这段入口叫 ide_rw；它在已有队首时只追加请求，第一项才调用 ide_start_request。

处理程序从设备得到中断，找回当前队首并检查设备状态。成功读需把设备数据取入该缓冲，成功写则确认先前提交完成。设置 VALID、清除 DIRTY、唤醒等待该缓冲的进程，移走队首并启动下一个。实际驱动还须把错误送回调用者，不能把失败当成有效数据。对应的完成入口叫 ide_intr。以一个 512 字节扇区为例，若端口一次传 4 字节，读数据的 insl 或写数据的 outsl 分段共传 128 个四字节单位。

进程与 CPU 调度 01 / 14

同一份程序开两次，机器要记两份什么？

在两个终端同时启动同一份计数器。左边已经数到 70，右边才数到 3。磁盘上只有一个可执行文件，两个数字藏在哪里？

磁盘文件给出指令和初始数据。一次运行还要有自己的地址空间、寄存器和身份，这个活的实例叫进程。程序计数器 PC 记录接下来从哪里取指令，栈指针 SP 指向当前栈的位置。同一段加法代码，可以在两个进程里读到不同的计数值。

创建时，操作系统登记进程，安排代码与静态数据的映射，准备用户栈，把参数个数 argc 和参数数组 argv 交给启动代码。堆提供动态分配的空间，程序可用 malloc/free 管理对象。普通终端程序通常继承已打开的标准输入、输出、错误三个文件描述符。内核把控制交给可执行文件的入口，运行库再调用 main。

可执行文件很大也能较快出现第一个提示符，因为装载可以按需进行，首次用到某页时再调入。从外部看，父进程能创建子进程、查询状态、等待退出，也能请求暂停、恢复或终止。时间共享把一个 CPU 的不同时段给两个实例，内存虚拟化让它们分别保存工作内容。

进程与 CPU 调度 02 / 14

磁盘等待期间，谁有资格上 CPU？

A 刚发出必须等结果的读盘请求，B 正在就绪队列里。磁盘和 CPU 可以分别工作，怎样记录这两个进程？

每个进程都有一份进程控制块 PCB。调度器从中或相关队列获知它在运行（running）、可运行但等待 CPU（ready），还是在等某个外部条件（blocked）。单核的一个时刻只能执行一个进程的指令，但可以同时有很多就绪或阻塞的进程。

A 发起同步读并需要等待，运行态转阻塞态。B 可被选中，由就绪转运行。设备完成传输后发出中断，内核把 A 变回就绪。A 真正拿到 CPU 还需一次调度。另有一条独立的边：时间片用完而工作没做完时，运行的进程回到就绪。

在教学内核 xv6 中，RUNNABLE、RUNNING、SLEEPING 对应这三种主要状态，还用 EMBRYO、ZOMBIE、UNUSED 记录创建、退出待收尾与空表项。进程记录还能找到 PID、父进程、打开文件、工作目录、等待通道、内核栈、陷入现场和切换上下文。队列告诉内核去哪里找人，保存的现场告诉它如何继续那个人的工作。

进程与 CPU 调度 03 / 14

一条用户指令怎样请内核读文件？

写下 read(fd, buf, 4)，应用为什么没有获得随意操作磁盘的权限？

为使普通计算够快，处理器直接执行用户程序。为保留控制权，硬件区分用户态与内核态，只允许特权代码配置设备、修改关键控制寄存器等。用户若需要这些服务，要走内核事先登记的入口。开机时内核在特权态安装陷阱表；用户不能把表项改成自己的函数。

系统调用包装函数准备调用号和参数，再执行陷入指令 trap。硬件与入口代码共同保留用户的 PC、寄存器等现场，转到受保护的内核栈与指定处理程序。内核按调用号分派，检查 fd、用户缓冲区和权限，完成服务或安排等待。返回路径恢复现场与用户权限，应用取得返回值，接着执行。

这个过程叫受限直接执行。普通函数调用也改变 PC，却不够格提高特权；一次顺利返回的系统调用可以全程属于同一进程。观察 Linux 程序时，strace 可显示一次运行实际发出的调用与信号，ausyscall 可按机器的系统调用表查名称与编号。库函数与系统调用没有一一对应关系。首次进入用户态时，内核可以先构造一份初始返回现场再沿返回路径启动程序；main 正常返回后，运行库调用退出服务，内核回收资源并保留供父进程领取的退出状态。

进程与 CPU 调度 04 / 14

时钟如何把正在循环的 A 换成 B？

A 进入一个永远不主动让出的纯计算循环。B 已经就绪。只有 A 主动调用 yield 才能切换的系统，会发生什么？

协作调度依赖程序系统调用、主动让出或产生异常时交回控制，早期 Macintosh 等系统使用过这类思路。纯计算循环可能无限占着处理器。抢占调度在启动时配置定时器，让与当前指令无关的外部时钟也能使 CPU 进入内核。每次时钟到来都是重新选择的机会，调度器仍可选择 A。

选择 B 时要照顾两层现场。第一层是 A 被中断时在用户态的位置，由硬件和陷入入口保存在 A 的内核栈上。第二层是内核自己运行到什么位置，由低层切换例程保存。恢复 B 时，先接回 B 以前暂停的内核执行路径，再在返回用户态时恢复 B 的用户寄存器与 PC。

32 位 x86 版 xv6 的 swtch 把被调用方须保存的寄存器压到旧栈，把原栈指针记入旧上下文，再把新栈指针装入 ESP。随后从新栈弹寄存器，ret 从新栈取返回地址。实际的 xv6 可以经每核调度器上下文中转。中断也可能打断内核，短暂屏蔽本核中断可守住局部操作；多核共享结构另外需要锁。

进程与 CPU 调度 05 / 14

从同一根时间轴读出周转、响应与车队效应

三份作业 A、B、C 同时到，依次入队，要用 CPU 12、2、1 秒。每份都只算一次，忽略切换开销。怎样量出排在长作业后面的代价？

先写每项的到达、第一次运行、完成三个时刻。响应时间是首次运行减到达，周转时间是完成减到达；周转含等待、运行以及可能的 I/O。全体平均时每项算一份。公平则另有含义，例如人人轮到或按契约分份额，平均周转最短不会自动满足它。

先到先服务（FIFO/FCFS）每次取队首，一次跑完。若三项同到且等长，换个次序不会改变平均值。但本题 A 跑到 12，B 到 14，C 到 15，平均周转 (12+14+15)/3 = 13.67 秒，平均响应 (0+12+14)/3 = 8.67 秒。短作业跟在长作业后面一起等，形成车队效应。

若运行时间事先知道、同时到达且只用 CPU，最短作业优先（SJF）选 C、B、A，完成时刻变成 1、3、15，平均周转 19/3 = 6.33 秒。理由可以在相邻两项上看到：长项先跑会把它的整段时间加到后一项的等待里；换短项在前，两项最后收尾的时刻相同，第一项却更早完成。

进程与 CPU 调度 06 / 14

短作业晚到时，要不要中断正在跑的长作业？

A 在 0 秒到达且需 9 秒，B 在 2 秒到达且需 3 秒，C 在 3 秒到达且需 1 秒。单核且切换无耗时。

非抢占的 SJF 只在 CPU 空出来时做决定：0 秒只有 A，于是 A 运行到 9，再选 C、B。A、B、C 分别在 9、13、10 完成，平均周转为 (9+11+7)/3=9 秒。知道后来有短作业，却不允许它打断已经获选的作业。

最短剩余时间优先（STCF，也称 PSJF）在新作业到达时重新比较剩余量。2 秒时 A 还要 7 秒，B 只要 3 秒，换 B。3 秒时 B 还要 2 秒，C 只要 1 秒，换 C。等 C 完成，先收尾 B，最后还给 A。

这次 A、B、C 分别在 13、6、4 完成，平均周转 (13+4+1)/3=6 秒。A 的周转变差，平均数却变好。持续有更短的新工作到达会使长工作长时间得不到执行；实际系统也很难预先知道工作还要多久。

进程与 CPU 调度 07 / 14

时间片多短，用户才看得到第一次回应？

三个终端各交一个需要 4 ms 的计算，均在 0 ms 到达。希望三位用户尽快都看到程序启动。

轮转调度 RR 给就绪队首一个时间片 quantum。到点还没跑完就放回队尾，完成或阻塞可提前归还。按固定时钟节拍实现时，时间片可取若干个时钟周期。在相同时间片且总有工作可做的条件下，持续就绪的任务轮流获得 CPU。

设队列初为 A、B、C，时间片 2 ms，暂不计切换。首次运行时刻为 0、2、4，平均响应 2 ms；完成时刻为 8、10、12，平均周转 10 ms。一次做完一个则首次运行在 0、4、8，平均响应 4 ms，平均周转 8 ms。二者改善的是不同体验。

若每次不同任务之间的切换要付 0.2 ms，连续满片运行时 CPU 用在任务上的比例约等于 q/(q+0.2)。q=2 时为 90.9%，q=0.2 时只剩 50%。上式是很长一串相同满片与切换的平均，第一片启动和最后一片结束应在有限时间轴里单独计。

进程与 CPU 调度 08 / 14

让 CPU 与磁盘在同一段时间各做一件事

A 要算 2 ms、读盘 4 ms、再算 2 ms；B 要连续计算 6 ms。二者同时就绪，A 先运行。

A 提交读盘后，磁盘可以独立工作。若 CPU 跟着 A 一起等，4 ms 都被浪费。将一次作业拆成 CPU 突发段与 I/O 等待段，CPU 调度器只在就绪集合里选，把设备忙碌的这段墙上时间也用于计算。

0–2 ms 跑 A，2–6 ms 磁盘服务 A，CPU 跑 B。6 ms 的设备完成中断把 A 唤醒；若它立即获选，6–8 跑完 A，8–10 补完 B 剩下的 2 ms。最终 CPU 忙 10 ms，跨度也是 10 ms，利用率为 100%。如果空等磁盘再让 A、B 完成，总长 14 ms，CPU 利用率则是 10/14≈71.4%。

设备完成只保证 A 可以被调度。让 B 在 2–8 一口气跑完再让 A 跑到 10，整体结束仍在 10 ms，A 自己的完成时间则推迟了 2 ms。提高总利用率与缩短 A 的周转时间是两个可分别计算的目标。

进程与 CPU 调度 09 / 14

不知道作业长度，怎样照顾新来的交互请求？

一个后台编译任务会跑很久。你按一次键，编辑器只需 1 ms 就能画出字符。两者都没向内核申报将来要运行多久。

多级反馈队列 MLFQ 把就绪任务放在若干优先级队列，每个就绪任务只在其中一层。永远先取最高的非空层，同层任务轮转。新任务从最高层开始，先给它一次很快响应的机会，再根据它实际用了多少 CPU 更新位置。

先用一个基础版本来观察行为。每层时间片为 4 ms，一次用完整片就降一级；若提前阻塞，回来时先保留该层。Q2 最高，Q0 最低。长作业 A 连续运行 8 ms 后从 Q2 降到 Q1 再降到 Q0。此时刚来的 B 从 Q2 开始，用 1 ms 便等待输入，后台 A 又能占用 CPU。

这里的“反馈”来自可观察的行为。连续用满片的作业很可能还要继续算；频繁短暂运行后等待外部事件的任务通常需要较短响应。这个判断可能会错，所以下一课还要让低层任务有机会重新证明自己的特征。

进程与 CPU 调度 10 / 14

用多少就记多少，为什么还要定期提升优先级？

某程序每运行 9 ms 就短暂等待 I/O，而一个时间片有 10 ms。若每次回来都把账清零，真正一直计算的程序会怎样？

基础降级规则只观察单次有没有跑满，因而这个程序每次回来还在高层。修订的规则分开一次轮转的时间片与一层允许累计使用的预算：在同一层累计 CPU 用量达到预算就降级，中途主动让出不会抹掉已经用过的时间。设预算 10 ms，它回来再用 1 ms 就该降级。

另一个问题是饥饿。连续不断的高层任务可能使底层一直轮不到。每隔 S 把所有工作提升到最高层，给长期等候者与已经从计算密集变成交互型的工作一次重新竞争的机会。S 太长，等待依旧明显；过于频繁，高低层刚分开就被重置。

高层用短片使交互请求尽早轮转，低层用长片摊薄切换成本。三层可示范为 10、20、40 ms；队列数、各层片长、预算和提升周期都是策略参数。Solaris 分时类是一个历史实例，使用 60 层、高层约 20 ms、低层可到几百 ms，提升时间约为秒量级。

进程与 CPU 调度 11 / 14

给谁多少 CPU，能用票来表达吗？

两个用户各订了一半算力，其中一人同时开了两个程序。怎么把“给用户一半”转换成每个作业的机会？

按比例分享的目标是各任务获得约定的运行份额。彩票调度给每个持续就绪任务若干张票，每个等长时间片独立抽一张。持票 3、1 的两项分别有 75%、25% 胜率。短时间内前者可以连赢或连输，比例描述的是长期趋势。

票可以有本地货币。甲乙各有 100 张全局票，甲在本地给甲一、甲二分 3∶1，就兑换为 75、25 张全局票。乙只有乙一，给它所有 100 张。也能临时转让票，比如委托另一个进程代办时；允许自行增加票数的“通胀”适合受信环境，否则会稀释其他人的份额。

实现时把就绪任务票数累加，从 0 到总票数减一均匀抽号，选第一个累计值严格大于号码的任务。一次简单的公平性测量选两个同到、同工作量、同票数的任务，以较早完成时刻除以较晚完成时刻，越接近 1 表示二者收尾越接近；若在 10、20 秒完成，指标只有 0.5。

进程与 CPU 调度 12 / 14

不用抽签，怎样让两份算力固定按二比一分？

A 拿 2 张票、B 拿 1 张票，短短六个时间片也想看得出差别。

步幅调度（stride scheduling）用一个足够大的共同常数除以票数，得到 stride；每个任务有一笔 pass，表示到目前为止按份额折算的进度。每次选 pass 最小者，用完一个相同时间片就把自己的 pass 加上 stride。票多，步子小，更快再次变成最小。

用常数 6，A 的步幅为 3、B 为 6，初值都为 0，同值时选 A。前六片依次 A、B、A、A、B、A，累计 4∶2。这个规则不要求六片里每个前缀都已精确按 2∶1，追踪的是长期累计差距。

新任务的初值影响很大。若两个老任务 pass 都到 600，新任务从 0、步幅 3 开始，它会接连被选约 200 次才追到同一水平。采用接近当前竞争者进度的新起点可以避免把入场前的时间也当成欠账。

进程与 CPU 调度 13 / 14

多一个核，为什么仍然需要锁？

一张任务链表同时有两个核在取队首。就算两个核最后都能看到同一个 head 值，它们会不会取走同一个节点？

单片芯片里可以有多个核心。单条不能拆开的执行流，同一时刻只能占一个核；要加速那个程序，需要把工作拆成可并行的线程或任务。每个核有小而快的缓存，重复读同一数据利用时间局部性，扫描邻近地址利用空间局部性。把进程留在用过的核，可能省掉再把热数据装入另一份缓存的开销，这叫缓存亲和性。

两个缓存若都保存旧值 D，核 0 改为 D′ 后，核 1 不能无限沿用旧副本。一种一致性实现是总线监听：观察其他核对同一缓存行的写入，使本地旧行失效或更新。它解决同一位置的副本怎样协调。

链表取头含读旧头、读后继、改头、释放旧节点多个动作。两个核哪怕每一次读写都看到了合法的值，仍可能在任何一个改头之前同时读到旧头 X。给整个摘除操作加同一把互斥锁，只让持有者走完这一串动作，才能防止重复摘除或释放。

进程与 CPU 调度 14 / 14

空闲的核怎样找到另一个核积压的工作？

双核机器上，0 号核的队列只有 A，1 号核的队列有 B、C。三者一直就绪。每核内部等额轮转，谁得到的 CPU 最多？

一个全局就绪队列叫 SQMS：任何核都从同一处取活，较易分配全部就绪任务，但大家争同一把队列锁，且任务可能反复跨核，损失缓存亲和性。可以尽量让固定任务回原核，只让多出的任务轮流迁移，代价是选择逻辑更复杂。

每核独立排队叫 MQMS。本地调度减少争锁并自然保留亲和性，上述三任务却分别得每单位时间 1、0.5、0.5 个核的运行量。若 A 完成，核 0 甚至可能完全空闲。迁移 B 或 C 可立即填满两核；若三者长期都活跃，还可轮换迁移对象，让每项的长期份额接近 2/3 个核。

工作窃取让空闲或负载低的核偶尔查看别人的队列，取走可运行任务。检查过勤会增加跨核同步和迁移成本，过疏又让 CPU 闲置。历史上的 Linux 调度设计有不同组合：O(1) 以多队列动态优先级照顾交互，CFS 以确定性的比例分享配合每核队列，BFS 则使用单全局队列与虚拟截止时间思路。判断一种设计要同时看选谁与队列放在哪里。课程将 BFS 的历史设计与 EEVDF（Earliest Eligible Virtual Deadline First）联系起来。“合格”指按份额进度已轮到参与竞争，“虚拟截止时间”给这些候选排执行顺序。

内存管理 01 / 17

程序打印出来的地址属于谁？

运行两份相同的程序，两边都打印某个全局变量的地址。假使它们打印出相同数字，改写甲的变量会不会动到乙？

可以把物理内存先想成从 0 开始编号的一长排字节。早期只装一个程序时，程序闲等也会占住整片机器。把多个程序都留在内存、轮流给它们 CPU，利用率会提高，但必须防止一个错误的地址改坏别人的数据。操作系统让每个进程使用自己的编号系统，叫虚拟地址空间。

普通指令写出的地址是虚拟地址 VA。硬件结合当前进程的映射寻找物理地址 PA 后，才去真正的内存取字节。每个进程拥有一套映射，于是相同的 VA 可以落在不同 PA。这既方便程序装载，也使未经授权的内存访问有机会被拦下。

一个 C 程序里，指令在代码区，全局或静态变量在数据区，malloc 返回的对象来自动态分配区，函数调用的局部对象及返回信息通常在栈上。栈里的指针变量可以指向堆里的对象。Linux 下 /proc/PID/maps 和 pmap -x PID 可看某个进程的映射范围与权限；打印的函数地址、分配结果和局部变量地址都要按该进程的 VA 解读。

内存管理 02 / 17

一次加法怎样支持重定位，边界又挡住了什么？

甲、乙各有 1024 字节的地址空间，分别从物理字节 1024、4096 开始。两者都读取虚拟地址 100。硬件怎样选中正确的字节？

基址寄存器 base 装有当前进程那块连续物理内存的起点。程序运行时，每次取指、读或写均可由内存管理硬件执行 PA = base + VA，实现动态重定位。甲读 100 到 1124，乙读 100 到 4196；改变放置位置不必改写程序里的每一个指针。

加法本身不提供保护。甲若写 VA=3072，光做加法会算到 1024+3072=4096，恰是乙的开头。给硬件加一条 bounds=长度 的检查：单字节访问只允许 0≤VA<1024，越界先产生异常，这次写不产生效果。长度为 1024 时，最后一个字节是 1023。

有的示意把上界存成物理区间排他终点。甲的同一段可写为 base=1024、end=2048，要求 base≤PA<end；长度 bounds=1024 和终点 end=2048 不能互换。以下容量用二进制单位，1 KiB=1024 B。

内存管理 03 / 17

谁分给一个进程内存，又在切换时记住它？

机器空闲区是 [16,32) 和 [48,64) KiB，A 占 [32,48) KiB。现在要创建同样大的 B，再让 CPU 从 A 切给 B。

基址与界限是硬件执行每次访问的依据，但硬件本身不知道哪块内存空着。内核用空闲列表登记尚未分配的物理区间。创建进程时，它寻找足够大的连续洞，划给进程并登记映射。退出时归还原区间，可把物理上相邻的空闲区合在一起。

假设给 B 选 [48,64) KiB。A 运行时硬件 base=32 KiB，切给 B 时需先把 A 的配置信息记在 A 的 PCB，再把 B 的 base=48 KiB 与长度 16 KiB 装入受保护寄存器。进程的寄存器现场和地址空间规则都必须跟着身份换。

现在两者访问同一 VA 1 KiB 分别落在 33 和 49 KiB。等 A 退出，[32,48) 并入原来 [16,32) 后变成 [16,48)，恰好可以装下一个 32 KiB 的新进程。整个过程中 B 的字节无需搬动。

内存管理 04 / 17

相距很远的堆和栈，需要连同中间的空洞一起分配吗？

一个 16 KiB 虚拟空间里，代码从 0 开始、堆从 4 KiB 开始，堆暂只用 2 KiB，栈靠高地址。整块连续分配会为中间的空白付出物理内存。

分段将代码、堆、栈这些逻辑上连续的区域分别放置。每段有自己的物理基址、界限和属性，不同段之间没有物理相邻的要求。访问先确定段，再用段内偏移算物理地址。段内仍要求连续，段大小可各不相同。

以堆段物理基址 34 KiB 为例，VA=4200 不是偏移，因为堆在虚拟空间从 4096 开始。偏移=4200−4096=104，小于 2048，PA=34×1024+104=34920。若访问 VA=7168，偏移是 3072，已经越过段尾。代码若从虚拟地址 0、物理 32 KiB 起，VA 100 的结果则是 32868。

一种显式硬件布局用 14 位 VA 的高 2 位选段、低 12 位取段槽内位置。段号=(VA & 0x3000) >> 12，低位=VA & 0x0FFF。4200=0x1068，高位 01 选堆，低位 0x068=104。每槽可表示 4096 个位置，某个堆是否实际长到该处还要看该段界限。

内存管理 05 / 17

向下增长的栈，怎样从顶端数出偏移？

把某个虚拟栈槽设为 [12,16) KiB，物理顶端为 28 KiB，暂时只分配了栈顶以下 2 KiB。读 VA 15 KiB 应该向哪个方向走？

向低地址增长的段用一个方向位与长度描述。为避免差一，我们把虚拟、物理栈顶都定义成排他终点。VA 15 KiB 距离虚拟顶端 16 KiB 的有符号位移是 −1 KiB，所以物理字节落在 28−1=27 KiB。当前有效区是虚拟 [14,16) KiB，对应物理 [26,28) KiB。

使用固定 4 KiB 槽时可先取槽内低位，再减槽大小得到负位移。本题低位为 3 KiB，3−4=−1 KiB。检查 −长度≤位移<0，才把位移加到物理顶端；正向堆的 0≤偏移<长度 不能原样套给负位移。这里栈槽的位置是本例约定，段号与槽位对应由具体布局规定。

段还有读、写、执行权限。多个进程可以把各自代码段映到同一只读可执行物理区，私有堆栈则映到各自可读写区。少量大段用几组寄存器即可；细粒度分段让更多对象独立受保护或共享，却需段表管理更多描述符。

内存管理 06 / 17

明明还有 12 KiB，为什么放不下 8 KiB？

三处空洞分别是 4、5、3 KiB，彼此隔着运行中程序的段。新来的进程需要一个连续的 8 KiB 段。

总空闲量为 12 KiB，但最大的连续洞只有 5 KiB。分配器找不到长 8 KiB 的区间，这叫外部碎片：空闲空间散在已分配对象之间。只有物理地址紧挨着的空闲区才可直接合并，不能凭空把不相邻的字节放在同一段内。

一种补救叫紧凑化（compaction）。内核暂停有关执行，把各段实际字节搬到更紧密的位置，并改好其基址。假设所有活动段都能移动，整理后 12 KiB 聚成一个洞，划走 8，还有 4 KiB。搬运大段和同步更新映射都要付费。

另一条思路是把虚拟与物理都切成等大的格子。一项请求若可以用多个页框，就不再需要一块容得下整段的大洞。代价会转移到格子内部：页为 4 KiB 时，一份 5 KiB 的独立对象若单独从整页分配，需 2 页、占 8 KiB，末页有 3 KiB 未使用，这叫内部碎片。

内存管理 07 / 17

一张表如何让相邻虚拟页住进相隔很远的物理页框？

把 64 B 虚拟空间切成四个 16 B 页，把 128 B 物理内存切成八个同样大的页框。若页号 0、1、2、3 各装在页框 3、7、5、2，VA 21 在哪里？

虚拟页号 VPN 回答“哪一页”，页内偏移回答“那页第几个字节”。用 VA 除以页大小，商是 VPN，余数是偏移。21=1×16+5，所以去当前进程的页表找第 1 项，得到物理页框号 PFN=7。目标物理字节为 7×16+5=117。

因为 16=2⁴，低 4 位原样保留。64 B 空间用 6 位 VA 表示，21 写成 01｜0101；换成三位物理页框号后是 111｜0101。数值跨度可改变，页内字节排列不会改变。若下一字节并未跨页，只要让偏移加一即可。

每个进程有自己的页表。例如另一套 4 B 页模型中，甲的表为 [0,7,5,6]，乙为 [1,2,3,4]。同样访问 VA 6，VPN=1、偏移=2，甲得到 7×4+2=30，乙得到 2×4+2=10。虚拟连续不要求物理连续；分配器只需寻找空闲同尺寸页框，也不用预测堆栈将怎样增长。

内存管理 08 / 17

页表也在内存里，怎样找到存着答案的那一格？

看到 PTBR=4，容易把它当成目标数据所在的页框。现在每页 4 B，每项 1 B，物理地址 4–7 依次存着 0、7、5、6。请跟踪 VA 14 的一次读。

页表是每进程的映射数据，线性页表就是按 VPN 编号的数组。“页表基址寄存器”PTBR 记整张表起始的物理字节地址。查表地址=PTBR+VPN×每项字节数。14=3×4+2，先访问物理字节 4+3×1=7，从中读到 PFN=6，再访问 6×4+2=26 才取得程序想要的数据。

普通页表项 PTE 除页框号还记性质：valid 表示映射是否合法，present 表示合法页当前在不在 RAM，读写执行权限规定可做什么，accessed/reference 标记近期访问，dirty 表示自装入或写回以来有修改。先做合法性与权限检查；合法但不在场可能要调页，非法映射或不准写的映射不能照此处理。

以 32 位 x86 页表项的布局为例，除了高位的页框号，还可看到 P、R/W、U/S、A、D 等位，分别用于在场、写权限、访问特权、访问和修改记录。不同体系的编码有差异。无翻译缓存且一层表时，一个数据读取包含一次 PTE 读取和一次目标读取，指令取址若计入工作负载得另算。图中还标出 PWT、PCD、PAT 等缓存策略字段和 G（全局）位。它们控制这份映射的使用方式，不参与这里的页框号乘法。

内存管理 09 / 17

读十个整数，为什么只需三次慢查表？

每页 16 B，每个整数 4 B，从某页的偏移 4 开始顺序读十个整数。初始 TLB 为空，容量足够，只统计数组数据的地址翻译。

处理器的内存管理单元 MMU 中可以放一个小型翻译后备缓冲器 TLB，保存最近常用的 VPN→PFN 和权限。命中时核对权限、拼上原偏移即可访问数据；未命中时查询页表，获得合法在场映射后填入 TLB，重试原指令。TLB 缓存的是转换结果，数据值本身是否在数据缓存是另一件事。

第一页还放得下偏移 4、8、12 的三个元素，第二页放四个，第三页放三个。每页第一次进入都未命中，余下元素沿用同一翻译，故 3 次未中、7 次命中，命中率 7/10=70%。访问相邻地址体现空间局部性，稍后再读同一页则体现时间局部性。

谁处理未命中取决于硬件设计。硬件管理型由页表遍历器按已知格式取 PTE；软件管理型触发专门的异常，让内核例程检查页表、填入条目、恢复原指令。前者可见于 x86，后者可见于经典 MIPS；两者都可能在页已驻留 RAM 时就完成，无需磁盘。小型全相联 TLB 可并行比较表项，常见教学容量如 32、64 或 128 项。

内存管理 10 / 17

换进程以后，TLB 中的旧翻译还能认得主人吗？

甲上次访问 VPN 10 查得 PFN 100，现在切换到乙。乙的 VPN 10 实际映到 PFN 170。仅用 VPN 10 作查找键会发生什么？

若沿用甲的条目，乙可能读到甲的内容。简单做法是换地址空间时使旧条目失效，再让新进程慢慢填满；更有区分力的做法是在 TLB 条目里加地址空间标识 ASID，用 (ASID, VPN) 查找。切换后硬件使用乙的当前 ASID，甲的结果仍留在缓冲器却不会被误用。

不同的键也可以有相同的 PFN。这就是有意共享：甲的 VPN 18 与乙的 VPN 50 若都映到 PFN 101，双方通过各自的映射权限访问同一物理页，只占一个数据页框。是否共享要看最终映射和权限，单看虚拟页号相等不足以判断。

经典 MIPS R4000 条目示意还展示全局标记 G、ASID、有效位 V、缓存属性 C、与写入相关的 D 位及 PFN。全局映射可按架构规则跨地址空间匹配。若框号有 24 位、页为 4 KiB，则可编号 2²⁴ 个框，能表示 2²⁴×2¹²=2³⁶ B，即 64 GiB 物理空间。

内存管理 11 / 17

只容得下三份翻译，第四份进来时丢哪份？

TLB 仅有三项，全相联，从空表开始；所有页本身都在物理内存。连续引用 VPN 7、0、1、2、0、3，该丢哪个条目？

最近最少使用 LRU 记录最后使用顺序。每次命中，把该页移到最新一端；未命中且容量已满时，去掉最久没碰的那一个，再插入新条目。记录可以画成从最老到最新的一行。命中也要挪位置，否则误做成“最早进入先出”。

依次读前三页后顺序是 7、0、1；读 2 时驱逐 7，变为 0、1、2。再读 0 是命中，顺序变为 1、2、0；此时读 3 应淘汰 1。前六次一共五次未命中。在本题全都驻留的前提下，这五次都能通过页表重新取得映射，不会造成五次换入。

继续输入 0、4、2、3、0、3、2、1、2、0、1，逐项标记得到整串 17 次中的 11 次未中、6 次命中。一次换走的是 TLB 中关于某页的翻译，页表和该页的数据依然存在。

内存管理 12 / 17

页表本身要吃掉 4 MiB，哪些位置其实不值得记？

32 位字节地址的进程只用了代码、堆顶和栈顶各几页，却给每个可能的虚拟页准备一项。这个数组到底多大？

虚拟空间有 2³² B，页为 4 KiB=2¹² B，共 2²⁰ 个虚拟页。每个 PTE 为 4 B，则一张线性表有 2²² B=4 MiB。即使绝大多数项无效，固定数组也占同样空间。1024 个这样的进程仅页表就需 4 GiB，这笔账不含它们的代码或数据。

把页长改成 16 KiB=2¹⁴ B，项数降为 2¹⁸，总表缩为 1 MiB。代价是按整页分配时，小区域末端可能浪费更多。比如只需一个独立的 1 KiB 区域，4 KiB 页余 3 KiB，而 16 KiB 页余 15 KiB。大页也没有去掉“虚拟区从未使用”的概念。

段页结合让每段拥有一张页表，段基址指向该段页表的物理起点，界限限定表的范围。于是段与段之间没有条目；若某一大堆段内部仍极稀疏，表内仍有许多空项。可变长而连续存放的段页表本身还会带来外部碎片。进一步的想法是连表也切成定长页，只建真正需要的部分。

内存管理 13 / 17

用两层索引，怎样跳过成片不存在的页？

16 KiB 虚拟空间、64 B 页、目录项和页表项都占 4 B。只有起始和末尾的若干页在用，怎样不为中间的空洞建整张表？

把线性页表切成一页大小的二级表。一页能装 64/4=16 项；16 KiB/64 B=256 个虚拟页需要 16 组，每组 16 页。第一级目录存 16 个目录项 PDE，每项记录二级表是否存在及其页框。整组从未映射时，目录写无效即可，省掉那一页二级表。只有两组被使用时共占目录 1 页+叶表 2 页=192 B，完整线性表则为 256×4=1024 B。

地址共 14 位，低 6 位做页内偏移，VPN 的高 4 位为目录索引、低 4 位为叶表索引。另取一张同规格、目录项 2 有效的页表，以 VA=0x0A53 即 2643 为例，拆成目录 2、叶项 9、偏移 19。假设目录物理基址 640，目录项 2 指到框 20，叶项 9 指到数据框 50，各级均有效且可读。

无 TLB 命中时，先读物理 640+2×4=648 处的目录项，再读 20×64+9×4=1316 处的页表项，最后读 50×64+19=3219 处的目标。目录无效则可以提前停止；二级表可以占任一空闲框，无需同目录相邻。省去许多未使用的表页，代价是在未命中时走更多级；较密地址空间还可能让目录本身成为额外负担。

内存管理 14 / 17

合法的一页为什么眼下没有物理页框？

四个活跃进程有些页很久没用，物理内存只剩四个框。能不能让它们仍各自看见完整的地址空间？

寄存器、缓存、主存、辅助存储的容量和访问时间不同。CPU 执行指令或获取数据前，相应字节必须能在主存中取得；磁盘可以比较便宜地保存目前不用的页。交换空间 swap space 以页为单位记录暂时离开 RAM 的内容，OS 还需要知道每个 (进程, VPN) 对应的交换槽。

于是“这页属于进程吗”和“这页现在住在 RAM 吗”分成两个问题。教学模型里 valid=1 表示映射合法，present=1 时可以取 PFN；合法且 present=0 时，内核可通过 PTE 或相关数据找到磁盘位置。另一个未映射地址 valid=0，即使有空闲框也不能擅自把它变成合法数据。

换出要在复用页框之前保存必要的新内容、改好旧映射并使过期的翻译失效。换入为合法缺页找一个框，读回数据并建立映射。进程随后仍使用原来的 VPN，页内偏移也不变。管理很多进程时，同号 VPN 必须带上地址空间身份。

内存管理 15 / 17

一条 load 缺页后，究竟要从哪里继续？

A 要读 VA 130。页长 64 B，VPN 2 合法且允许读，但目前只在磁盘槽 9。假设物理框 11 可用，数据最终从哪个物理字节送入寄存器？

先拆出 VPN=2、偏移=2。TLB 命中且权限合适，可以直接取数。未命中则查 PTE：映射无效应报地址错误，访问违背权限应报保护错误；合法但不在场才触发这里讨论的需从交换区取回的缺页。仅仅 TLB 未命中并不说明要读磁盘。

内核的异常处理程序选框。若无空闲框，则按置换策略选一个牺牲页，必要时写回并处理旧映射。这里拿框 11，从槽 9 读入整页；A 可以阻塞，CPU 先运行其他就绪进程。I/O 完成后，内核更新 A 的 PTE，将 PFN 设为 11、present 置为 1，A 回到就绪集合。

等 A 再次获选，应重试原来的 load，因为它在陷入前未取得数据。新翻译得到 11×64+2=706，读物理字节 706 的值交给目的寄存器。若简单跳到下一条指令，寄存器仍是旧值，程序算出的结果就错了。

内存管理 16 / 17

什么时候回收一页，回收哪一页？

系统保持一小批空闲框待用。设低水位 LW=3、高水位 HW=6，现在有 2 个空闲框。怎样避免把所有回收工作都压到下一次缺页上？

后台页守护线程监视空闲框数。低于 LW 时开始回收，达到 HW 时停下来；用两个阈值可减少在同一临界点频繁启停。在本例其他活动不变的条件下，要回收 6−2=4 个框。空闲框有 3 个时，按“低于 3”这一规则本身不会启动。

选哪页是另一个问题。LRU 倾向于淘汰最长时间没访问的页，希望近期使用习惯持续。若近期顺序从旧到新为 P、Q、R，就先考虑 P。干净且有有效后备副本的页可以直接丢弃 RAM 中副本；若改过而后备副本仍是旧的，就需要保存最新内容，才能复用框。

盘很慢，即使低缺页率也能支配平均时间。设每次访问都付 RAM 成本 Tm，未命中再付额外磁盘成本 Td，平均访问时间 AMAT=Tm+p×Td。若 Tm=100 ns、Td=5 ms=5,000,000 ns、p=0.0001，平均是 100+500=600 ns。若题目给的是未命中路径总成本而非附加成本，应用各路径总成本按概率加权。

内存管理 17 / 17

磁盘一直忙，为什么反而应该少跑一个程序？

一台机器能给用户页留 10 个框。A、B、C 近期分别反复访问 4、4、5 个互不共享的页。把三项都调得更勤，是否能提高吞吐量？

一个程序在当前阶段反复需要的那组页常称为工作集。三个工作集共 13 页，容不进 10 框。如果刚被换走的页马上又要读，缺页接连发生，程序把时间耗在等盘上，CPU 利用率可能随并发度增加而下降，这叫抖动（thrashing）。超过容量说明有压力；是否已经抖动还要看实际重用与缺页频率。

若暂时只让 A、B 运行，工作集共 8 页，能同时驻留；也可以先运行 A、C 的 9 页。此时尽管排队作业多了一个，单位时间内完成的有效计算反而可能增加。恢复另一个程序要重新考虑它当前的工作集和可用框。

还有两种针对 I/O 的手段。预取猜测后续会需要哪页：顺序扫描时调入页 1 的同时先读页 2，若猜中可避免下次同步等待；猜错则占框和带宽。聚簇或分组写把多次待写页合成较大的一次 I/O，摊薄每次请求的固定开销。它们分别改变读入时机与写出的批量，持续工作集超载时仍须面对容量限制。

线程 01 / 07

一个进程怎样同时做两件事

播放器一边等下一块音频到达，一边把手头这块变成波形图。等待输入时，计算还能向前走吗？

进程提供运行程序所需的一组资源，包括虚拟地址空间和打开的文件。线程（thread）是其中一条能被调度的执行路径。取样线程等输入时，绘图线程若已就绪，就能接着用处理器；两者也能调用同一个函数，却分别停在函数的不同位置。

在这一核只提供一个硬件执行线程的教学模型中，任一瞬间只运行一条这样的路径，任务的执行区间交错，称为并发。两颗核可以在同一瞬间各跑一条，称为并行。并发问题只要求执行交错，单核就足以出现。

线程 02 / 07

切换时，哪部分状态跟着线程走

两名工人都在函数 paint 中循环。再次轮到甲时，CPU 怎样知道该从第几条指令继续？

程序计数器 PC 指向即将取的指令，通用寄存器存着临时操作数，栈指针定位当前调用栈。每个线程都需要独立保存这些值；同一进程的两个线程可以有相同的 PC 地址，同时拥有完全不同的寄存器和调用者。

线程控制块（TCB）及其相关保存区记录线程状态。切出时系统保存当前执行上下文，选定就绪线程后，恢复它的 PC、寄存器与栈指针。两个线程属于同一进程时仍使用同一份虚拟地址映射。切换不复制共享内存，也不会把共享变量恢复到切出前。

线程 03 / 07

从一个指针找到真正共享的对象

两个线程各有变量名 cursor。它们会不会互相覆盖？先找出 cursor 和它指向的数据分别住在哪里。

代码区保存指令，静态存储区保存全局量和静态局部量，堆保存动态申请的对象。每个线程还有自己的栈，容纳活动调用所需的局部对象、参数或返回信息，具体哪些值留在寄存器由编译器决定。线程能访问同一地址空间中的这些区域。

局部指针是一个对象，指针指向的对象是另一个。两个函数调用各有一个 cursor，若两个 cursor 都指向同一个缓冲区，它们仍在读写同一块数据。把一条线程栈里的地址交给另一条线程也能形成共享；此时必须保证原调用仍然活着，且访问有适当同步。

线程 04 / 07

把一份工作交给新线程

要统计录音块中大于零的样本。主线程怎样说明处理范围，并在工作线程读取之前把数据准备好？

pthread_create 的四个参数依次是线程标识的输出位置、线程属性、入口函数和一个传给入口的参数。pthread_t 是线程标识；属性传 NULL 表示使用默认值，专门的属性对象还可以描述栈大小，也能配置适用的调度策略与优先级。入口的类型是 void *(*)(void *)，可以接收指向任务结构的地址。

在 create 前填好参数。成功后，创建者和新线程都可能先执行下一步，因此主线程不能随意修改 worker 正要读的输入。下面是一个完整的单任务程序；任务结构一直活到 join 之后。把它保存为 peaks.c，在支持 Pthreads 的环境中用 cc -Wall -Wextra -pthread peaks.c -o peaks 编译。

#include <pthread.h>
#include <stdio.h>
typedef struct { int sample[3]; int count; } Job;

static void *count_positive(void *p) {
    Job *j = p;
    for (int i = 0; i < 3; i++)
        if (j->sample[i] > 0) j->count++;
    return NULL;
}

int main(void) {
    Job job = {{3, -2, 7}, 0};
    pthread_t t;
    if (pthread_create(&t, NULL, count_positive, &job)) return 1;
    if (pthread_join(t, NULL)) return 1;
    printf("%d\n", job.count);
    return 0;
}

pthread_create 成功返回 0，失败返回错误号，这种情况下不能用未成功创建的标识做 join。一个任务创建一条线程的模式有启动成本，小工作通常需要分成较大的批次。

线程 05 / 07

线程结束以后，谁还拥有结果

甲算出一段录音的长度后返回，主线程刚从 join 醒来。它怎样拿到仍然有效的长度？

pthread_join(t, &raw) 等待指定的、可 join 的线程结束，并将入口返回的指针值写进调用者的 void *raw，所以函数需要的是 void **。只等结束可传 NULL。若对方已经结束，join 也可成功回收其资源；顺次 join 甲、乙不会规定二者原先的执行先后。

线程入口 return ptr 或调用 pthread_exit(ptr) 都可交回一个指针值。工作线程自己的自动局部对象寿命止于调用结束，传出地址也无法延长它的寿命。可让调用者提供结果槽，也可由工作线程分配堆对象并把释放责任交给接收者。main 提前返回会结束整个进程，包括尚在运行的线程。

/* worker 内：包含 <stdlib.h>，分配失败时返回 NULL。 */
int *duration = malloc(sizeof *duration);
if (duration) *duration = 24;
return duration;

/* main 内：t 已成功创建；这里只有这个 join 接收者。 */
void *raw = NULL;
if (pthread_join(t, &raw) != 0 || raw == NULL) return 1;
int *duration_ms = raw;
printf("%d ms\n", *duration_ms);
free(duration_ms);
线程 06 / 07

把一次丢失更新拆到每条指令

两条线程都把录音总时长增加 3，初值 12。程序明明执行了两次加法，为什么有一次运行最后停在 15？

在这个简化的机器上，把一次更新翻成三条指令：地址 40 的 LOAD 从共享内存读入寄存器 R，44 的 ADD 只改 R，48 的 STORE 才把 R 写回。CPU 按 PC 把指令取入指令寄存器 IR，译码后执行，并转至下一条。表中每次写出的 PC 都是下一条地址。真实编译器和指令集可以产生不同序列。

甲完成 ADD 后时钟触发切换。系统完整保存了甲的 R=15 和 PC=48；这正好意味着甲恢复后会写出先前的 15。乙即便在间隙完成自己的更新，甲也不会重新 LOAD。所谓丢失更新来自这种合法的机器指令交错。

再想一步

这个轨迹针对明确的 LOAD、ADD、STORE 教学机器。C 里两个线程以非原子方式无同步读写同一位置且至少一方写，会产生 data race，程序行为未定义。volatile 不能提供线程间互斥或原子读改写；偶尔测到预期总和也无法证明正确。

选择临界区，守住整条规则

作业队列只剩一个名额。两个提交线程各看到“还有一个”，随后分别登记。即使登记动作本身有锁，会发生什么？

临界区是为维持共享状态的一条规则而需要互斥执行的代码段。这里的规则是“每次成功登记必须消耗一个尚未分配的名额”。检查名额、扣除名额、登记都要在同一把锁内完成，所有竞争者也要遵守这项协议。

互斥让拿同一把锁的观察者只能见到某次完整操作之前或之后的状态。持锁者仍可能被调度器暂停，临界区也仍然是多条机器指令。另一种减少冲突的方法是先各自累加局部计数，再由主线程在 join 后合并结果。

用互斥锁保护同一笔状态

售票记录同时有“剩余张数”和“已售张数”。把每个整数分别锁起来，报表能读到一笔完整的售票吗？

假设座位固定为 8，正确状态必须满足“剩余＋已售＝8”。若只分别保护两个数，报表可能在卖票线程扣掉余票、尚未增加已售时读到一笔不完整的交易。让售票和报表都在同一把互斥锁（mutex）内接触这两个字段，即可维护这条跨字段的规则。

pthread_mutex_lock 成功后调用者是持有者，其他竞争者须等到锁可得。持有者调用 pthread_mutex_unlock 释放；后续成功取得同一把锁的线程能观察到释放前受保护的写入。两场无关演出可以各带一把锁，从而独立售票。跨场次操作要同时考虑两场状态和取锁顺序。

再想一步

使用前可静态初始化 pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER，或对未初始化的对象调用 pthread_mutex_init(&m, NULL)。选其中一种。检查这些函数直接返回的错误号，检查也可封装成函数。所有使用者结束且锁未被持有后，动态锁可 pthread_mutex_destroy。不要把有副作用的调用藏进可能被编译掉的 assert。

为什么锁本身需要原子操作

给锁一个标志位，0 表示空闲，1 表示占有。两个线程先读标志，再写 1，谁赢？

若测试和置位是两次独立访问，甲可在读出 0 后暂停，乙读出 0 并写 1，甲恢复后也写 1。两者都认为自己成功。让硬件把“写新值、返回旧值”实现成一个不可分的交换，所有对同一标志的交换就会排成一个顺序。初始为 0 时，当中只有第一人会取得旧值 0。

把原子交换放进循环，看到旧值 1 就重试，就得到自旋锁（spin lock）。实际实现还需要内存顺序保证，令成功获取具备 acquire 语义，释放具有 release 语义。只把几条普通 C 赋值包进名叫 TestAndSet 的函数并不能产生这种硬件保证。

/* C11，自旋锁的最小示意。 */
#include <stdatomic.h>
static atomic_flag occupied = ATOMIC_FLAG_INIT;

void take(void) {
    while (atomic_flag_test_and_set_explicit(
               &occupied, memory_order_acquire)) { }
}
void give_back(void) {
    atomic_flag_clear_explicit(&occupied, memory_order_release);
}

等待一把锁，究竟该占着 CPU 吗

单核上甲持锁时被抢占，还差 1 毫秒完成。若乙接下来忙等 5 毫秒，甲会提早解锁吗？

评价一把锁至少要分开问三件事：临界区是否始终至多一人进入，每个等待者有没有机会进入，以及空闲或争用时各付多少代价。原子交换能给出互斥；总被新人抢先的线程仍可能饥饿。单核若缺少抢占或主动让出，忙等者甚至能一直挡住持锁者运行。

多核且持锁者仍在另一核执行时，短时间自旋可以省掉睡眠和唤醒的开销。yield 把竞争者从运行态放回就绪态，调度器以后还能立即选中它。队列锁可登记等待者并 park 使它睡眠，释放者再 unpark 指定线程；登记、释放与入睡要配合好，否则唤醒可能抢在入睡前丢失。两阶段锁先短暂自旋，仍未得到锁就入队休眠。

条件变量等的是哪一句话

必须等音频索引制作完成才可读取它。若制作者比读取者先跑完，一次唤醒能留到以后使用吗？

把“索引可读”写成共享布尔式 ready，这种可检查的判断叫谓词。互斥锁 m 保护索引的发布和 ready；条件变量 cv 提供等待队列。读取者持锁检查，发现为假便调用 pthread_cond_wait(&cv, &m)。它把加入等待与放开 m 做成一个对通知方不可插入的过程，醒来后重新取得 m 才返回。

制作者持 m 填好索引、置 ready，再发 signal 并解锁。在一个等待者的场景，制作者先到时没有线程接收信号，但 ready 留下了完成的事实；读取者先到时会睡眠。若不保存 ready，迟到者可能永远睡下；若先自行解锁再去睡，中间又会留下“已经通知却无人接收”的窗口。

/* m、cv 已初始化；ready 初值为 0。单个读取者。 */
/* 读取者 */
pthread_mutex_lock(&m);
while (!ready) pthread_cond_wait(&cv, &m);
read_index();
pthread_mutex_unlock(&m);

/* 制作者 */
pthread_mutex_lock(&m);
build_index();
ready = 1;
pthread_cond_signal(&cv);
pthread_mutex_unlock(&m);

有界队列怎样做到不覆盖也不读空

麦克风生产音频片段，编码线程消费片段。它们速度不同，内存只准保留三个待编码片段。

有界缓冲区（bounded buffer）用容量限制生产者超前的距离。队列拥有读位置 r、写位置 w 和有效项数 n。初始化均为 0。生产者须等 n < 3，在 w 写入后令 w=(w+1)%3，n 加一；消费者须等 n > 0，在 r 取走后令 r=(r+1)%3，n 减一。整次检查与修改都在同一把锁下完成。管道的写端和读端也面对缓冲容量，只是那里的缓冲由内核管理。

使用两个条件变量 not_full 与 not_empty。生产者在 while(n==3) 中等 not_full，每次放入后 signal(not_empty)；消费者在 while(n==0) 中等 not_empty，每次取走后 signal(not_full)。消费者取得自己可安全持有的音频片段后，可释放队列锁，再花时间做音频编码；队列状态和读写下标的更改始终在锁内。容量为 1 时，这套协议就是一格交接；容量较大时，生产者可在消费者暂时忙碌时接连放入多项。

唤醒哪一个等待者才有人能继续

即使用 while 每次醒来重查，如果生产者和消费者全睡在同一个条件变量上，所有人仍可能睡着。

设只有一个槽、一个生产者 P 和两个反复取数据的消费者 C、D。P 放入物品叫醒 C，接着因槽满也上同一条队列等。C 取走物品，本应唤醒能填空槽的 P；signal 如果挑中 D，D 唯一能做的是重新等物品，C 也会在下一轮等待。程序保持了“读空前要检查”的安全性，却丢失了继续运行的机会。

两个明确的等待队列可在取物后定向唤醒生产者。另有一些情况，同一类线程的条件也各不相同，例如等待不同额度的内存。可用同一覆盖条件配合 pthread_cond_broadcast 唤醒全部，再让每个请求持锁用自己的谓词筛选。代价是额外调度和锁竞争。

用初值表达可用名额与完成事件

两台机器共用一座机房，三条任务都申请开机。怎样既限制最多两条运行，又让迟到者看到早已发生的释放？

计数信号量（semaphore）记录可取走的许可。sem_wait 原子地取一份，若暂无许可便等待。sem_post 交出一份，可能让一个等待者完成 wait。无等待者时交回的许可会留下，供未来的 wait 取走。在 <semaphore.h> 中用 sem_t 声明，sem_init(&s, 0, 2) 的 0 表示同进程线程共享，2 表示一开始有两份。

初值为 1 并按取得一次、归还一次的协议使用，可保护排他资源。信号量没有 mutex 的线程所有权要求：另一线程也能 post，这使初值为 0 的信号量可以表达一次完成事件。若 worker 先 post，主线程随后 wait 直接取走；若主线程先 wait，就等 worker 的 post。一次许可只能满足一次 wait。

历史辅导 T06（2025T2）把场景延伸到独立进程。两个进程各自在私有内存中 sem_init，只会得到两个计数器。可让二者 sem_open 同一个名字；进程完成后 sem_close 自己的引用，约定的管理方 sem_unlink 名字，最后一个引用关闭后对象才会消失。已有名字用 O_CREAT 重新打开时，新的初值不会重置旧对象。无名对象跨进程共享则需要把同一 sem_t 放进共享内存，并将 pshared 置为非零。

再想一步

课件把这个自制信号量称为 Zemaphore。可用一把 mutex、一个条件变量与非负整数 credits 实现该语义。wait 持锁，在 while(credits==0) 中执行 cond_wait，之后减一并解锁；post 持锁加一，signal 后解锁。保存 credits 使先来的 post 也有效。用 POSIX sem_wait 时要检查失败，若遭信号中断可按意图在 EINTR 时重试；sem_* 一般以 −1 和 errno 报错。 sem_trywait 无可用许可时立即以 EAGAIN 失败。通过 sem_init 创建的无名对象在所有使用者离开后调用 sem_destroy。

队列需要两类许可和一把锁

缓冲区有两格，两个生产者各拿到一份空位许可。这样能保证它们写不同的位置吗？

空位许可只声明“有足够空位”，没有分配具体下标。多名生产者若同时读到 w=0，仍会覆盖同一格。设 empty 初值 N，full 初值 0，gate 是初值 1 的互斥信号量或等价 mutex。生产者先 wait(empty)，再取 gate，更新槽和写位置，放开 gate，最后 post(full)。消费者先 wait(full)，在 gate 内取物并移读位置，离开后 post(empty)。

反过来先拿 gate 再等 full 会卡住空队列：消费者持有 gate 睡眠，生产者必须拿 gate 才能填入第一项，从而永远发不出 full。sem_wait 睡眠时只等自己的信号量，不会自动释放无关的锁。与条件变量的 wait 会释放传入的 mutex 相比，这里获取顺序承担了避免闭环的责任。

/* 每一行是一项伪代码操作，假设取得许可成功。 */
produce(x):
    wait(empty)
    lock(gate)
    put(x)
    unlock(gate)
    post(full)

consume():
    wait(full)
    lock(gate)
    x = get()
    unlock(gate)
    post(empty)
    return x
竞态、锁与信号量 09 / 15

允许一组读者并行，写者怎样入场

归档目录常被查询，偶尔更新。两个查询可以同时扫描目录，但改目录时不能有查询走到改了一半的节点。

读写锁的准入规则是：读者可有多名，写者入场时必须独占。用 readers 记录读者人数，用小锁 m 保护人数变化，用初值 1 的信号量 room 管理整个目录。第一个读者在 m 内把人数从 0 加到 1，并 wait(room)；其余读者增数后即可加入。每人读完再在 m 内减数，最后一个读者从 1 减到 0 时 post(room)。写者独自 wait(room)，改完 post(room)。

第一个读者申请 room 时仍持有 m，可阻止后续读者误以为已经获准而提前进入；正在写的线程不需要 m 就能释放 room。room 可能由首位读者取得、末位读者归还，正好利用信号量的无所有权特性。用 pthread_rwlock_rdlock、pthread_rwlock_wrlock 和 pthread_rwlock_unlock 可以直接表达读、写两种进入模式。

给两把叉子排顺序，为什么能破环

五名哲学家围坐，五把叉子编号 0 至 4。第 i 人进餐须同时持有 i 与 (i+1)%5 两把。怎样允许相隔的人一起吃？

每把叉子都可以看作一个初值 1 的信号量。若人人按“先取左，再取右”，可能恰好每人都先得到自己的左叉。此时 0 等 1，1 等 2，直到 4 等 0；每人都在等别人吃完，而无人可以开始吃。一个足以说明故障的执行顺序就能推翻这个协议。

统一改成先取编号较小的叉，再取较大的。前四人的次序没变；第 4 人改为先取 0 再取 4。若有环，从某把已持有的叉沿“还要取”一直走，编号必须严格递增，却还要回到起点，这是不可能的。相隔的两人仍能拿到不重叠的叉；这个证明只排除了循环等待，公平进餐还取决于机会如何分配。

程序没有卡死，结果照样会错

目录服务有两种偶发故障。一种在检查到条目有效后仍取到空值，另一种在初始化尚未结束时就开始查询。该给哪几步加约束？

第一种是原子性违例：代码需要把几个访问视为一笔操作，实际却容许别的线程插入中间。若检查与使用之间允许删除者清掉条目，两步各自单独加锁也不够。须让检查和使用共享一个临界区，删除同样持这把锁；若要把指针带到锁外，另需确保对象寿命。

第二种是顺序违例：查询必须在初始化完成之后。如果两个线程只是各持同一把锁访问，查询者仍可能先得到锁并读到未初始化状态。制作者在锁内填好数据后发布 ready，读取者在锁内等到 ready，再使用数据，就加入了所缺的先后关系。另一种办法是先初始化，再创建查询线程。

从一张等待图找到死锁的四个条件

两个归档操作都要改标签库和文件库。甲先拿到标签锁，乙先拿到文件锁。它们为何再也不能只靠调度器解开？

在资源分配图中，画线程 → 资源表示正在等待，资源 → 线程表示当前持有。现在是甲 → 文件锁 → 乙 → 标签锁 → 甲。每种锁只有一个实例，所有相关线程都停在阻塞式取锁处，谁也到不了 unlock。此时轮换 CPU 不能移动任何一条边。

一般要出现这种资源死锁，需要四个条件同时存在。互斥使同一份资源不能并用；占有并等待使线程握着已有资源申请下一份；不可剥夺表示持有的资源不会被强行撤走；循环等待使等待链首尾相接。系统支持这四种条件提示有风险，是否当下卡死仍需看具体分配。资源有多份可替代实例时，仅凭有环未必足以判定。

再想一步

这一问题常藏在封装边界里：copy(from,to) 内部先锁 from 再锁 to，另一个调用者传入相反对象。单看任意一次调用都合理，组合便能闭环。给所有对象固定排序，并让内部被调用的方法也遵守该次序。

拿第二把锁失败以后怎么办

两个批处理器都需要扫描头与校准器，但不同模块的自然调用顺序恰好相反。除了让其中一方永远等，还能如何改变协议？

可以为所有资源指定全局顺序，使每次新增等待都指向更大的序号。也可以事先知道所需的整组资源，通过统一分配器一次获准全部，若不足就一件也不占；这样破坏占有并等待。代价是预先申报和更少并行机会。若用总入口锁串行各次取锁，所有参与路径都须服从同一个入口协议，释放工作不能反过来依赖入口。

不能静态排序时，先取一把，再用 trylock 尝试第二把。若为 EBUSY，释放自己已有的那把，撤销尚未提交的工作，再从头试。系统因此不需要从别人手里强拆锁。若双方每次同步退让又同步重试，则 CPU 一直忙却没有交易完成，这叫活锁。随机退避能够打散节奏，仍不是每个参与者在有限次内成功的证明。

用 CAS 更新链表头，要重算哪一项

两条线程已各自造好新节点，打算插到同一链表最前面。如果它们都看到了旧表头 H，哪个节点会消失？

若两人都先令自己的 next=H，再相继发布 head=A 和 head=B，那么 B.next=H，A 从表头就再也走不到。可以用互斥锁把“读旧头、写 next、公布新头”组成一个临界区，也可使用原子比较交换（compare-and-swap，CAS）。CAS 只有在 head 仍等于预期旧值时才把它替换成指定新值，并报告是否成功。

成功的那一次 CAS 就是操作对其他线程生效的时刻。失败说明假设可能已过时，必须重新读头，再填写 next。原子增量同理：若从 7 出发计划写 11，有人先加 2 写出 9，我们必须以 9 为基数重算 13。实践中共享头要用原子对象，并以适当的发布及获取语义，让读者能看见已经填好的节点。

这里固定为只插入节点，且节点在使用期间一直有效。若同时删除和回收节点，还须另外解决对象寿命及地址重新出现等问题。伪代码写成“失败时再试”，先确定 CAS 的返回约定再写循环条件。

提前避开死锁，还是发现后回滚

两颗处理器要跑四项各耗时 1 的任务。如果在运行前就知道资源需求，哪些任务可重叠？若事先不知道，又如何处理实际发生的环？

假设甲、乙都可能以任意次序持有 X 和 Y，丙只用 Y，丁不拿锁，任务彼此无需等待其他任务的输出。已掌握这个需求表时，调度器可以让甲和乙的资源占用区间错开。让甲与丙同时获准，丙即使等 Y 也不会拿着 X 反向等甲；甲乙之间则没有同时持有相反资源的机会。仅把两人分配到同一 CPU 并不充分，切换时旧线程可能仍握着锁，必须约束真正的资源持有区间。

若丙也变成需要 X、Y 且顺序不定，保守方案可把这三人的资源阶段串行化，只让丁与其中之一重叠。已知需求的回避换来可预测的安全状态，同时可能拉长完工时间。检测与恢复选择另一条路：允许请求先发生，周期性建立等待图，找到确实闭合的一组后，选择一个可回滚的事务中止并释放资源，再重试。

再想一步

线程程序若没有事务撤销机制，随便终止持锁线程可能留下半写状态；有的系统只能重启或从一致的检查点恢复。预防是用结构排除某个必要条件，回避是按已知需求选择安全准入，检测恢复处理已经发生的等待环。

已经来过的通知，该记在哪里？

只有一个工作线程 W 和一个等待者 M。W 可能先完成，M 随后才开始等待。分别用条件变量和信号量表示这一事件，初态怎么设？

  1. 条件变量方案另设 done = false，并用同一把锁保护。W 持锁写 true 后通知；M 持锁用 while 检查 done，只有未完成才 wait。W 先完成时，M 会直接通过。

  3. 若扩展为多个等待者，单个许可只能交给一个等待者，必须重新规定唤醒人数和共享状态。
