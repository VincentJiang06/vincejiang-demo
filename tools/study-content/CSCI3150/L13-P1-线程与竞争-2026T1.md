## 从内存虚拟化走向并发（p.1–3）

p.1 是本讲标题，分为线程基础与线程 API。前面多讲保护了不同进程的地址空间；这里主动让同一进程内的多个执行流共享内存，方便协作，也带来新的正确性问题。

p.2 课程图将位置移到 Concurrency，线程是下一步锁、信号量等同步机制的基础。并发首先是一种执行关系：多个执行流的步骤可能交错；多核同时运行只是其中一种情况。

p.3 为 Part I 分节页，后续先解释线程是什么，再通过一个共享计数器展示为何需要互斥。

## 共享一份地址空间，各自保留执行位置（p.4–6）【延伸 L13 p.4–6（2022未核版）】

> **p.4** They share the same address space.

p.4 的 thread 是进程内部的执行流。多线程程序有多个执行点，每个执行点都要知道接下来执行哪条指令，因此有各自的 PC（Program Counter）。两个线程可以同时运行同一个函数，却处在函数的不同循环次数、不同语句位置；函数代码只需一份，不必每线程复制一份。

p.5 解释上下文切换：暂停 T1 时把它的 PC、寄存器等状态保存到线程控制信息中，再恢复 T2 的状态。同一进程内切换时地址空间仍是那一个，所以 T2 可以看到 T1 在共享内存中写过的值。TCB（Thread Control Block）保存的是某个线程的运行状态；保存寄存器并不等于保存或回滚整个共享内存。

p.6 图从一份栈变成两份栈。每个线程调用函数都有自己的返回位置、参数和局部变量，需要各自的栈来管理调用过程。代码与堆仍处在共同地址空间内。图的地址由上方0 KB向下增加，因此堆画成向下延伸，栈画成向上延伸；这里是图上方向，换成数值说法就是堆往较高地址、栈往较低地址增长的示意。

**补充（通识）**：“每线程一份栈”描述使用归属，不是硬件隔离权限。一个线程把自己的局部变量地址交给另一线程，后者也可能访问到；随之必须保证对象还活着、读写有正确同步。Part II 的传参和返回值错误就与这件事有关。

## 两个 worker 与一次看似正确的输出（p.7–9）

p.7 对照单线程和多线程图：代码、数据、文件资源在进程层共享，寄存器和栈跟随每条线程。即便只有一个 CPU，线程也可能在一次共享更新的中间被换走，稍后另一线程继续执行。因此“我的机器同一时刻只跑一条指令”不能证明共享更新安全。

**题面块｜L13 p.8 · Concurrency Example（原代码关键部分）**

```c
volatile int counter = 0;
int loops;
void *worker(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}
```

p.8 中 `counter` 与 `loops` 位于函数外，两个 worker 都用同一份。局部循环变量 `i` 则属于各次函数调用。`arg` 预留给线程传参，本例未使用。每个 worker 企图把共享 counter 增加 loops 次；问题集中在 `counter++` 是否能作为一个不可分割步骤完成。

p.9 的 main 先要求一个命令行参数，再用 `atoi` 读到 loops，创建 p1、p2 两个线程，最后分别 join 后打印 counter。先创建两者再 join，两个 worker 可以重叠执行；先 join p1 再 join p2，并不强制 p1 先运行或先结束，等待顺序只是 main 的顺序。两个 join 的用途是确保 main 打印时两线程已结束，不是保护 worker 内部每一次加法。

讲义代码省略了 `atoi` 的严格输入检查和 pthread 返回码处理，是教学示例。实际运行还要检查线程创建是否成功；创建失败后不能无条件使用未取得的线程标识。

## 输出数字与三条机器指令（p.10–12）

**题面块｜L13 p.10 · 原输出片段**

```text
loops: 1000
Final value : 2000
loops: 1000000000
Final value : 1997974414
Final value : 1997940107
```

p.10 中每个 worker 加1000次，数学期望是 $2\times1000=2000$，某次运行确实打印2000。扩大到每线程十亿次，串行期望是20亿，示例却出现两个不同且偏小的值。一次得到期望数只说明那次没暴露问题，不能证明所有交错都正确；这些数字是课件中的运行记录，本篇没有伪称重新跑出了相同结果。

**补充（语言规则）**：`volatile` 不提供原子性或线程间同步。本例无同步地并发读写普通整型对象，在 C 的数据竞争规则下属于未定义行为；下面的“丢失一次更新”是解释风险的教学执行模型，不能把真实 C 程序的全部可能结果限制成若干个整数。[C11 委员会草案 N1570 §5.1.2.4¶25](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) 给出数据竞争与未定义行为的关系。

p.11 将一次递增展开为 load、add、store。load 把内存 counter 复制进寄存器；add 只改寄存器；store 才把寄存器写回共享内存。这三步没有天然组合成一个原子操作，切换可能发生在它们之间。即使单次 load 或 store 不会写半个整数，也不能推出整个“读旧值再加一再写回”不可分割。

**题面块｜L13 p.12 · 两线程例子**

> **p.12** counter = counter + 1 (initial value: 50)

> **p.12** We expect the result is 52. However,

p.12 原轨迹中 T1 先读取50、算成51，但尚未写回；OS 换去 T2，T2 仍读到内存中的50，算成51并写回；再恢复 T1，它把自己先前算好的51写回。两次加一最终只留下51。这不是加法算错，而是两个线程都基于同一个旧值50做更新。

以下 p.13–35 按原图逐页展开。同一地址 `0x8049a1c` 是 counter 的位置，100、105、108 是指令地址；PC 不等于 counter 的地址。课件采用“取指—译码执行—更新 PC”的分阶段示意，图下表的 `after instruction` 表示整条指令结束后的状态，与页中正在演示的微步骤可能不是同一时点。

## T1：初值、取指和读出50（p.13–15）

p.13 初始 CPU 的 PC=100，`%eax`=0，内存 counter=50。T2 保存的初始上下文是 PC=100、`%eax`=0；T1 正占用 CPU。寄存器0不意味着 counter 也为0，因为寄存器和内存是两个独立存储位置。

p.14 从 PC=100 所指位置取出 `mov 0x8049a1c, %eax`，放入 IR（Instruction Register）。此时只是知道“接下来要从哪个数据地址加载”，还没执行这次数据加载，所以 `%eax` 仍为0、counter仍为50。取指访问代码，load 执行访问数据，这两种读取不能合成一步来理解。

p.15 译码并执行这条 load，从数据地址读取50，存入 `%eax`。内存原值不因读取被消耗或清空，因此状态变为寄存器50、内存50。图此阶段 PC 仍画100；下一页才单独推进到105。

## T1：推进到加法，只改寄存器（p.16–18）

p.16 将 PC 更新为105，指向 `add $0x1, %eax`；`%eax`=50，counter=50。PC 从100到105不是“每条指令统一加5”的通则，而是本例下一条指令的位置；再下一条在108，间隔就不同。

p.17 从105取出 add 指令到 IR。取到加法并不等于已经加完，所以仍是寄存器50、内存50。原图让这两个阶段分开，是为了看到一条高级语句内部也有尚未提交的结果。

p.18 ALU 执行加一，`%eax` 从50变成51，内存 counter仍为50。到这里 T1 已经“算出”结果，但另一个线程读取共享内存时还看不到这个51。后面的中断恰好利用了这段窗口。

## T1 被保存，T2 被恢复（p.19–21）

p.19 PC 推进到108，下一条是 store：`mov %eax, 0x8049a1c`。此时 T1 的待恢复位置应是108，不能保存成100然后让它从头重算。CPU寄存器51，内存50。

p.20 中断发生，OS 保存 T1 的 PC=108 与 `%eax`=51。图把这两个值写进内存中的线程状态区域；这个区域不是 counter。保存现场不会顺便执行 T1 尚未执行的 store，所以 counter仍为50。

p.21 恢复 T2 的 PC=100 与 `%eax`=0到 CPU。T1 的51还安全地存在保存区，却不再占着当前 CPU 的 `%eax`。共享地址空间不变，因此 counter依然是50。图中旧 IR 的残留文字不是即将执行的决定因素；恢复的 PC 决定下一次取指位置。

## T2 再读到同一个旧值（p.22–24）

p.22 T2 从100取出 load 指令，CPU当前寄存器仍为0。代码可以与 T1 共用同一条指令，但执行上下文是 T2 的，不会自动继承 T1 尚未写回的51。

p.23 执行 load，读到共享内存中的50，故 T2 的 `%eax`=50。这里是丢失更新的关键：T1已经算出51不重要，T2看到的是未写回的旧 counter值。

p.24 PC移到105，准备加法。T1保存区仍为 `(108,51)`，T2当前状态是 `(105,50)`，共享counter=50。要复述这个图，至少同时维护这三类状态；只有一个“当前值”变量会把线程私有寄存器与共享对象混淆。

## T2 算出51并准备写回（p.25–27）

p.25 T2取出105处的 add。取指结束尚未执行，寄存器50，内存50。

p.26 加法执行后，T2的寄存器也变成51。它是对自己读到的50加一，不是对T1寄存器中的51再加一。两个线程都得到51完全符合各自的局部计算。

p.27 PC移到108。到这里 T2准备store，T1也停在自己的108处准备store。相同PC只说明两者下一条指令相同，不说明它们是同一个线程，也不说明两次更新已经串行化。

## T2 完成第一次实际写入（p.28–30）

p.28 T2从108取出 `mov %eax, 0x8049a1c`。AT&T语法这里是源在前、目的在后：从寄存器写到counter，而p.14的mov方向相反。取指阶段counter仍为50。

p.29 执行store，counter从50变成51。这是本轨迹第一次改变共享counter的步骤；T1和T2之前的两次add都只改了各自寄存器。

p.30 PC推进到113，T2这轮递增完成。此刻当前CPU `(PC=113, eax=51)`，共享counter=51；T1保存的 `(108,51)` 没有因为共享内存更新而自动变成52。

## 切回 T1，它恢复的是自己的旧计算（p.31–33）

p.31 再次中断，保存T2的113与51。共享counter仍为51，保存现场没有复制或撤销共享写入。

p.32 恢复T1的108与51。恢复的是T1暂停时的寄存器，而不是重新执行counter的load；所以它仍准备写51。这里并没有OS“忘记同步寄存器”的错误，OS正确恢复现场正是应有行为；需要同步的是应用的共享更新协议。

p.33 T1从108取出store。此时待写值51、当前内存值51。指令没有附加“若内存已变，就重新加一”的逻辑；普通store只忠实地写出寄存器内容。

## 第二次 store 没有带来第二次增量（p.34–35）

p.34 T1执行store，把51再写到counter。内存仍是51，丢失的是一个更新的效果，而不是某个线程被跳过：两个线程都运行了自己的load、add、store。

p.35 PC推进到113，T1这一轮也结束。最终相对初值50只增加1，串行应得52。若想让第二个线程读取到51后再算52，需要禁止这两次完整更新相互穿插，不能只要求“最终都join了”。

把原轨迹压缩为指令级状态，可得到：

| 阶段 | 正在执行 | PC（整条指令后） | 当前 eax | counter |
|---|---|---:|---:|---:|
| 初始 | T1 | 100 | 0 | 50 |
| load完成 | T1 | 105 | 50 | 50 |
| add完成 | T1 | 108 | 51 | 50 |
| 切到T2 | T2 | 100 | 0 | 50 |
| load完成 | T2 | 105 | 50 | 50 |
| add完成 | T2 | 108 | 51 | 50 |
| store完成 | T2 | 113 | 51 | 51 |
| 恢复T1 | T1 | 108 | 51 | 51 |
| store完成 | T1 | 113 | 51 | 51 |

**考试角度**：（C 级 通识）常见考法是给定中断点，填写每线程保存的PC、寄存器与共享内存；答案要区分微步骤状态与整条指令完成后的状态。

## 临界区与锁的保护范围（p.36–37）【延伸 L13 p.36–37（2022未核版）】

p.36 把访问共享变量、不能让多个线程不受约束地并发执行的代码段称为 critical section。这个例子的临界区是完整的读—改—写序列；mutual exclusion（互斥）要求参与者中同一时刻只有一个进入相关区段。原子性在这里表示对其他遵守同一协议的线程而言，整段更新像一个不可分割动作。

p.37 使用教学接口 `lock(&mutex)`、`balance = balance + 1`、`unlock(&mutex)`。加锁在读取旧balance之前，解锁在写回之后；两个线程必须使用**同一把**锁。若每人有自己的锁，两人都能各自“成功上锁”，仍会竞争共享balance。若只锁store，两个线程仍可能先各自读到50并算51，锁内依次写51也无济于事。

**算一遍（沿原p.12数字，添加p.37的互斥协议）**：T1先取得锁，读50、算51、写51、释放；T2才能取得，读到51、算52、写52。即使T1持锁时被CPU调度器切走，T2也不能绕过同一锁进入临界区。因此“锁保护临界区”不要求持锁线程永远不被中断，也不把高级语句真的变成一条机器指令。

## 本讲核心考点

- 同进程线程共享地址空间，各自保留PC、寄存器和栈（p.4–7，C 级 通识）。
- join等待完成，不替代共享更新中的同步（p.8–10，C 级 通识）。
- load、add、store分开；寄存器改变不等于共享内存已变（p.11–18，C 级 通识）。
- 上下文切换保存恢复线程状态，不回滚共享内存（p.19–33，C 级 通识）。
- 根据原轨迹解释50→51而非52，分清指令地址与数据地址（p.12–35，C 级 通识）。
- 同一锁覆盖完整读改写；只锁store或每线程不同锁均不够（p.36–37，C 级 通识）。

## 附录

### A1 用另一条合法交错检查理解（通识补充）

如果T1先完成load、add、store，再切到T2，第二次load读到51，第二次store写52。这说明在课件的指令交错模型中，结果依赖执行次序；不能只看每线程源码都写了“一次加一”就推断总效果。语言层面仍须使用正确同步，使真实C程序具有定义良好的行为。
