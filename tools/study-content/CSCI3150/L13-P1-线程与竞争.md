## 逐页伴读

p.1是讲题；p.2把线程放在内存与并发控制之间；p.3是Part I标题。

### p.4–6：共享地址空间，分别保存执行位置

> **p.4** They share the same address space.

一个进程可有多个执行流，每个线程有自己的PC和寄存器。切换线程时保存T1、恢复T2的状态，通常不必更换同进程的地址空间。TCB保存线程状态，不能把TCB和共享堆数据混为一物。

图p.6左侧单栈，右侧两栈共享代码和堆。每线程的函数调用、局部变量、返回地址需要各自栈，但“有自己的栈”不表示其他线程绝对不能通过指针访问它；生命周期与同步仍须正确。

**补充：线程私有的是执行状态，不是一个隔绝的“小进程”。** 同一进程的两个线程能通过共享指针访问同一个堆对象，也可以访问另一个线程仍然有效的栈对象。各有一份栈的意义是调用链互不覆盖，不是硬件按线程把栈地址全部隔离。把局部变量地址传给线程时，必须保证原函数未返回、对象仍有效，并避免并发无同步修改。

对比fork：两个普通进程的同名局部变量通常是私有副本；两个线程通过同一个对象地址访问的则是同一存储。做题先画“对象有几份”，再画“执行流有几个”。只数函数被调用几次却不确定它们在访问哪份数据，无法判断有没有共享竞争。

### p.7–9：两个worker同时改一个counter

原例的共享变量是 `volatile int counter=0; int loops;`，每个worker执行：

```c
for (i = 0; i < loops; i++) {
    counter++;
}
```

main从参数读取loops，创建p1、p2，分别join后输出counter。创建让两个worker有机会交错；join仅保证main打印前它们已结束，不保证worker之间互斥。`volatile`也不会把“读、加、写”合成原子更新。

### p.10–12：理想计数与观测值为何不同

原课件输入1000时观测2000；输入1,000,000,000时两次观测1,997,974,414和1,997,940,107。顺序原子累加的数学目标是2,000,000,000，分别少2,025,586和2,059,893。这些是课件记录，不是所有机器的确定输出。

下面用课件的简化机器指令模型解释一次丢失更新：初值50，T1读50加到51但未写回；切到T2，T2仍读50、加到51并写回；切回T1，它把自己寄存器里的51写回，最终51而非52。**语言层补充**：对普通共享C整数进行无同步并发读写属于数据竞争，不能把这个教学模型的数值范围当作C程序的完整保证。

### p.13–15：T1取指与读取共享值

图p.13初始PC100、eax0、内存counter50。p.14把地址100的load取进指令寄存器，这一步还没有修改counter。p.15执行load，eax变50，内存仍50。要分别看“指令从哪里取”和“数据读到哪里”。

### p.16–18：T1加的是寄存器

p.16 PC前进到105；p.17取出加一指令；p.18执行后eax51而counter仍50。源码看起来已经做了 `++` 的一部分，另一个线程却还看不到新值，因为store没有发生。

### p.19–21：保存T1，恢复T2

p.19 PC变108，下一条应是store。p.20中断把T1的PC108与eax51存到线程状态区。p.21恢复T2的PC100、eax0；**共享counter没有随上下文一起回滚或复制**，它仍是50。

### p.22–24：T2读到旧counter

p.22 T2从100取load，p.23读到仍未更新的50，p.24 PC变105。T1保存区里的51不会自动传给T2的eax，这正是把寄存器与共享内存分开看的理由。

### p.25–27：T2独立算出51

p.25取add，p.26使T2的eax50→51，p.27 PC走到108。现在两个线程各自持有一个51，但共享counter还是50；没有哪个操作计算过52。

### p.28–30：T2率先写回

p.28取store，p.29把T2的51写入counter，p.30 PC前进113。一份共享状态完成了一次递增。图中靠近代码地址的额外“113”属于执行位置注记，不能读成counter的新数值。

### p.31–33：切回T1时，旧寄存器值仍在

p.31保存T2的113和51；p.32恢复T1的108和51；p.33取T1尚未执行的store。图p.33部分T2保存区又显示初始100/0，与前一页保存值不一致；实际因果链应保留p.31的113/51，该图错置不影响T1即将覆盖counter的关键状态。

### p.34–35：最后的store覆盖同一个51

p.34 T1执行store，counter从51写成51；p.35 PC变113，两次递增都完成，但共享结果只有51。若从T1的load到store期间不允许另一个线程进入相同更新区，第二次就会读51并写52。

### p.36–37：临界区应包住整个不变量维护过程

> **p.36** Need to support atomicity for critical sections (mutual exclusion)

课件用 `lock(&mutex); balance=balance+1; unlock(&mutex);` 表达互斥。不能只锁store，因为读和计算仍可基于旧值；也不能让两个线程各锁一把不同的锁。所有竞争访问必须遵守同一保护协议，才能让这段更新对其他线程表现得不可分割。

### 用不变量选择临界区，而非看到赋值就加锁（补充）

自取一个两账户例子：A=10、B=20，把3从A转给B，需要先A减3再B加3。若要求任何观察者都看到总额30，两个更新必须作为一个整体保护；仅分别锁住两个赋值，会允许观察者在中途看到A=7、B=20，总额27。并发错误可以发生在多个变量的关系上，不只是单个counter自增。

锁本身也属于共享协议：写者和需要一致视图的读者都须遵守相同规则。持锁期间可以被OS暂停，另一个线程甚至可以在别核运行；只是它不能越过同一锁进入受保护区域。因此“临界区原子”指其他遵约访问看不见其部分状态，并不等于CPU关闭一切中断。

:::hint 自测：把balance声明为volatile，能否让两账户转账不可分割？

不能。volatile不提供互斥，也不把多次访问合成一次事务。需要先说明不变量、有哪些参与者及它们用什么同步关系，再证明所有观察都在正确边界上发生。

:::endhint
