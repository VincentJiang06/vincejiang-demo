## 2. PA3 与 HW3：算法相近，但关键规则不同

它们都处理多个优先级队列、round robin、累计 allotment、降级和周期性 boost。因此，HW3 的手算方法可以帮助理解 PA3；PA3 则把手算过程变成可反复执行的算法。

但是两份题目不是逐字同一份规则：

|规则|书面 HW3|PA3|
|---|---|---|
|同刻新到达|PID 升序入最高队列|PID 升序入最高队列|
|boost 的排列|PID **降序**，最大先运行|PID **升序**，最小先运行|
|新到达能否打断当前片|不能|不能|
|boost 能否打断|能|能，输出区间在 boost 时刻结束|
|allotment 非时间片整数倍|原题给出的有限 allotment 均可整除，没有触发这个边界|明确要求不截短时间片；累计达到或超过 allotment 后降级|
|最低队列 allotment|给定为无限|配置文件可给有限值，用完仍留 Q1 队尾|
|队列和进程数量|题目固定|读取文件，不固定为三个队列或六个进程|

例如，之前 HW3 在 t=400 时未完成的任务是 57、143、233、333、444。书面题要求排成 **444、333、233、143、57**；PA3 要求排成 **57、143、233、333、444**。两份答案不同正是遵守了各自题目，不能把其中一份排序拿来“纠正”另一份。

本次用 HW3 的数据作了额外程序测试，PA3 规则下 t=440 的 Q3 顺序是 **444、57、233、366**，因为之前四个时间片顺序已变：400–410 为 57，410–420 为 143，420–430 为 233，430–440 为 333。此时新到达的 366 仍然只加入队尾，并不会触发第二次 boost。

## 3. PA3 与 Project：训练方式相通，代码没有直接接入关系

Project 原题 p.1 明确要求：

> **p.1** Implement two functions for a simple file system (SFS): open_t() and read_t(). SFS is stored inside the supplied regular file HD. Your program reads this simulated disk to resolve pathnames and retrieve file contents.

两个接口是：

```c
int open_t(char *pathname);
int read_t(int i_number, int offset, void *buf, int count);
```

Project 的输入不是 `process.file`、`queue.cfg`，输出也不是 MLFQ 调度日志。它读取一个普通宿主文件 `HD`，把文件中的字节解释成 SFS 的元数据和内容。Project 的正式规格、FAQ 和页面没有要求加载 PA3 的调度器；也没有要求把 `scheduler-impl.c` 改名成 `call.c`。

可迁移的是以下工程方法，而不是具体调度函数：

|PA3 的练习|Project 中对应的做法|
|---|---|
|把题目规则落实为事件处理顺序|把“路径分量 → 目录项 → inode → 数据块”落实为读取步骤|
|区分 remaining、used、time slice|区分 inode 号、数据块号、文件内偏移、HD 内偏移|
|正确处理时间片终点、到达和 boost 边界|正确处理跨块、直接/间接块边界、文件尾 EOF|
|保留教师接口与 Makefile|保留 open_t/read_t 签名与教师头文件、磁盘格式|
|将程序日志逐行对照参考|将返回字节数及每一个字节与参考数据对照|
|把全部实现放入唯一提交文件|将全部实现和 helper 放入 call.c|

两者都使用 C 和现有课程 Linux 环境，都要遵守接口和数据约定。但 PA3 是 CPU 资源分配模型，Project 是持久数据寻址模型。完成 PA3 不代表已经完成任何 Project API。

## 4. Project 真正接在哪些已学内容后面

### 4.1 HW2 的目录查找，对应 open_t()

HW2 已经做过“从根 inode 开始，读取目录数据块，按名字找下一层 inode”的手算。Project 的 `open_t()` 要把这个过程写成循环。

以 FAQ 中明确给出的 `/dir5/dir1/file1` 为例：先取得根目录的 inode，读其目录项，找到名字 `dir5` 对应的 inode；再在该目录中找 `dir1`，最后找 `file1`。FAQ p.2 给出了这条路径应返回 **inode 13**，这是一个可以直接拿来验证的结果。后续官方测试已确认 dir5 对应 inode 1、dir1 对应 inode 5；不能把 HW2 图上的 inode 数字搬过来。

返回值 13 是 **SFS 文件身份**，不是宿主 Linux `open("HD", ...)` 返回的文件描述符。宿主描述符用于读取 HD；SFS inode 号用于定位 HD 里面的某个文件。混淆两者会使看似合法的整数被用于完全错误的位置。

目录项类型是 `DIR_NODE`，包含 `f_name[20]` 与 `i_number`。题目 p.3 指出 `sub_f_num` 是目录项数，包括 `.` 和 `..`；应用 `f_type` 区分目录和普通文件。Project 允许假设输入路径有效、存在且为绝对路径，不需要凭空扩大成完整的文件系统创建或路径修复项目。

### 4.2 HW2 的直接/间接块读取，对应 read_t()

Project 的一个数据块是 **4096 字节**，inode 有两个直接指针，后面通过一个间接块存放更多数据块号。因此逻辑块 0、1 走 `direct_blk[0]`、`direct_blk[1]`；逻辑块 k≥2 时查间接块的第 k−2 个整数。这与 HW2 的计算方法直接对应，但实际物理块号必须从 Project 的 HD 中读取。

**自编说明例子，非指定测试数据**：要从 offset=6000 读取 count=5000，并假设文件至少有 11000 字节。

- 6000÷4096 的整数商为 1，余数为 1904，所以起点在逻辑块 1 内的第 1904 字节。
- 逻辑块 1 余下 4096−1904=2192 字节，先通过第二个直接指针读完这 2192 字节。
- 还需 5000−2192=2808 字节，接着进入逻辑块 2，通过间接块的第 0 项取得其实际数据块号，再读 2808 字节。
- 两次内容拼接到同一个 `buf`：前一段放 `buf[0..2191]`，后一段接在 `buf[2192..4999]`。

这里“逻辑块 2”是文件内第三个块，不是 HD 数据区的物理块 2。先查到物理块号 b，再计算 HD 中的字节位置：**数据区起点 + b×4096 + 块内偏移**。Project p.2 的数据区起点为 10 MiB，即 10,485,760；不能直接把 b 当作 `lseek` 的字节偏移。

图（Project p.2）：HD 区域布局。
元素：Boot sector 为 [0,1024)，Superblock 为 [1024,2048)，Inode region 为 [2048,10 MiB)，Data region 为 [10 MiB,110 MiB)；图示已视觉核对。
看什么：inode 记录和文件内容位于不同区域；范围的右端点不包含在本区域内，所有偏移均从 HD 起点算起。

### 4.3 Lab 2 的文件 I/O、Lab 3/4 的元数据读取，提供实现手段

Lab 2 中的文件打开、读取、缓冲区和字节数概念，是操作 HD 的基础。Lab 3 的 Superblock reader 已在本课程资料中验证过，它帮助理解如何从磁盘指定偏移读取元数据。Project 规格与页面明确允许复用有帮助的 Lab 3/4 代码；本次没有读取当期 Lab 4 原件，所以不假称已确认某个 Lab 4 函数能原样粘贴。

复用前必须以 Project 自己的头文件、HD 和测试为准。当前 Project 规定整数为小端四字节，inode 的 `c_time` 必须保留 `int`；改成 `time_t` 会改变结构体布局，使字段与磁盘字节对不上。历史代码中的块大小也不能替代本次的 4096。

## 5. Project 比 HW2 手算多出的关键责任：EOF 与真实字节

普通宿主 `read()` 只知道 HD 文件整体的末尾，不知道 HD 中某一个 SFS 文件的末尾。`read_t()` 必须读取该文件 inode 的 `f_size` 来限制返回长度。

Project FAQ p.1 的原例：文件长度为 **1,239,081** 字节。

|请求|实际结果|原因|
|---|---:|---|
|offset=1,239,031，count=10,000|50|仅剩 1,239,081−1,239,031=50 字节|
|offset=1,239,131|0|非负偏移已超过文件长度|
|offset 恰好等于文件长度|0|已到文件尾|

因此每次读取前先确定真正允许的长度，再逐块读取。到达一个数据块的边界不等于 EOF；宿主 HD 仍有数据也不代表该 SFS 文件还有内容。

`read_t()` 处理的是字节，不是 C 字符串；题目不要求也不保证字符串结尾的 NUL。比较时必须核对返回字节数和字节内容，不能仅凭 `%s` 打印“看起来正确”。这也解释了教师为什么要求 `./read_test > test_result.txt` 后用 `cmp` 比较。

## 6. 最终项目以后怎样推进

根据已读取的正式要求，后续 Project 的工作顺序应当是：

1. 取得同一套 `Prog.zip` 与 `test-cases.zip`，保留其原始 HD、call.h、inode.h、superblock.h（现已完成下载和解压）。后续复核已收齐两个 ZIP，独立工作区位于 `课程工作目录/CSCI3150-Lab1/Project`，目录入口见 [Project 资料入口](../项目/Project/README.md)。
2. 在独立 Project 工作目录解压并核对头文件布局，先实现基本的元数据和数据块读取 helper。
3. 实现 `open_t()`，先验证 `/dir5/dir1/file1` 得到 inode 13，再验证其他提供的路径。
4. 实现 `read_t()`，按逻辑块切分请求，完成直接/间接寻址和 EOF 截断。
5. 按原规格在 Prog/ 中编译 open_test、read_test；公开测试包含五条路径和十次读取，继续补测跨块与 EOF 边界。
6. 最终只把 `call.c` 放进 ZIP；PA3 代码、HD、头文件、测试代码和二进制不放入提交包。

Project 指定 Lab 1 环境：XUbuntu 20.04（64 bit）、GCC 9.4.0。本机课程容器现为 Ubuntu 20.04.6 / ARM64 / GCC 9.4.0；工具链版本已核实，CPU 架构和桌面发行版不能被描述成完全一致。到实际做 Project 时仍需结合其包核对兼容性。

**当前完成边界**：PA3 实现与测试完成；Project 的要求、API、知识联系与后续步骤已经明确，Project 两个函数尚未在本次实现。
