## 直接执行为什么还需要限制

### 性能与控制必须同时满足（p.17）【新】

**题面**（L07-CPU虚拟化-进程-2026T1.pdf · 无编号开放问题 · p.17）

> **p.17** Performance: How can we implement virtualization without adding excessive overhead to the system?

> **p.17** Control: How can we run processes efficiently while retaining control over the CPU?

这两个要求互相牵制。程序若每做一次普通加法都要内核代做，管理成本就会很高；但如果程序可以无限制使用所有硬件，还能决定何时才把 CPU 还给 OS，内核便无法保护其他程序，也无法保证别人取得进展。

本讲的答案分两段逐步建立：**普通指令直接由 CPU 执行，以减少管理开销；敏感操作与控制权转移受到硬件和内核约束，以保持控制。**“直接”描述指令由谁执行，“受限”描述程序拥有什么权限、何时必须交回控制权。它们不是互相否定。

### 无限制的直接执行为什么失去控制（p.18）

**补充：反例执行轨迹。**若第七步进入一个不断重复普通计算的循环，且没有任何外部机制打断，程序就永远不走第八步。OS 并不是还在旁边用同一个核心执行一个监控循环：该核心此刻已在跑应用指令。于是这张朴素表没有让 OS 再获得执行机会的保证，这就是页末“OS 会变成 just a library”的含义。

图中的 `call main()` 是未加保护的说明模型，不是完整的真实启动协议。下一节用用户态和陷入机制补上权限边界；再下一节用时钟中断补上抢回 CPU 的能力。

## 把敏感操作关进受保护的入口

### 用户态与内核态解决哪一个问题（p.19）【新】

**题面**（L07-CPU虚拟化-进程-2026T1.pdf · Problem 1 · p.19）

> **p.19** What if a process wishes to perform some kind of restricted operation such as …
>
> Issuing an I/O request to a disk
>
> Gaining access to more system resources such as CPU or memory

p.19 给出 protected control transfer（受保护的控制权转移）。普通应用运行在 user mode（用户态），不能任意访问所有硬件资源；OS 在 kernel mode（内核态）执行管理操作。需要读磁盘并不等于应用可以直接操作磁盘控制器或修改别人的数据，它必须先提出请求。

**补充：为什么“受保护”比“跳过去”多一层。**普通函数跳转只改变执行位置，不能让调用者随意获得更高权限。否则用户自己跳到某段内核代码中间就能绕过检查。受保护入口需要由可信一方事先设定，进入过程按硬件规则完成，并由内核验证请求是否合法。应用有“请求服务”的能力，不等于有“决定请求必获批准”的权力。

因此本题的答案是：把敏感操作留在内核，通过受控制的入口处理应用请求。限制的是权限，而不是禁止用户代码直接执行普通计算。

### 系统调用是一组可检查的服务（p.20–21）

p.20 列出的系统调用服务包括文件访问、创建和销毁进程、进程间通信、申请更多内存。系统调用是内核选择对外暴露的功能边界：程序描述需求，内核结合权限与资源状态处理，之后向程序交代结果。

p.21 用 trap instruction（陷入指令）表示进入内核的受控动作：控制转向内核入口，同时提升到内核权限；return-from-trap 则恢复用户执行环境，并降回用户权限。这里的两个英文名称是机制层面的通称，不必理解成所有 CPU 都用同一个指令助记符。

**补充：一次不换进程的服务路径。**A 在用户态请求服务，进入内核后仍然是为 A 执行这次请求；完成后回 A 的用户态继续运行。模式发生了两次变化——用户态到内核态，再到用户态——但整个过程中运行者不一定改为 B。**发生系统调用不等于必然发生进程切换。**如果服务需要等待，内核才可能将 A 阻塞并调度其他进程。

PC 和寄存器不能任意丢掉：应用请求服务后仍需要知道回哪儿、继续使用哪些值，所以跨边界时必须保留返回所需现场。权限控制与现场保存共同构成“安全地进去，还能正确地回来”。

**考试角度**：（C 级 通识）这类知识点常见考法是判断“每次系统调用都切换到另一个进程”是否成立，并画出没有换进程时的用户态—内核态—用户态路径。

### strace：看见程序实际请求过什么（p.22）【新】

图（p.22）：终端中执行 `strace ls` 的截图，图片正文经视觉读取。  
元素：顶端为命令，随后依次出现 `execve`、`brk`、`arch_prctl`、`access`、`openat`、`fstat`、`mmap`、`close`、`read`、`pread64` 等调用及其返回值；一些调用显示 `ENOENT` 或 `EINVAL`。  
看什么：用户眼里的“列目录”在实现中还伴随程序装入、库文件读取、内存映射等活动。截图不是 CPU 每条指令的清单。

讲义命令（Linux 截图中的操作，本次未在本机执行）：

```sh
strace ls
```

**思路分析（逐步读）**：`strace` 是追踪工具，`ls` 是它要启动并观察的程序；每行通常先给调用名和参数，再在等号后给返回结果。它让你观察用户与内核的交互，而不是打印应用内部的每次加法或普通函数调用。

以截图中的两条可见调用为例：打开 `/etc/ld.so.cache` 的 `openat` 返回 3，表示获得文件描述符 3；之后的 `close(3)` 返回 0，表示这次关闭成功。后面再打开某个库文件也返回 3，并不矛盾：前一个引用已经关闭，描述符编号可以重新使用。

截图的 `access("/etc/ld.so.preload", R_OK)` 返回 `-1 ENOENT`，表示该次访问检查遇到了不存在的路径。仅凭某一行失败不能断言整个 `ls` 执行失败：程序可能在探测可选文件后继续。相反，读取到 832 的 `read` 行表示那次实际返回 832 字节，不是固定规定“所有读取都必须 832 字节”。

**补充：读取范围。**截图展示的是轨迹前段；没有展示完整终止输出，所以不能从这张图推算整个命令总共调用多少次内核。命令与输出只作来源解释，本次不安装或启动 Linux 环境。

### 启动与第一次进入用户态（p.24）

p.24 的协议分成 OS @ boot 与 OS @ run。boot 表示系统启动时的全局准备；run 表示启动某个程序时的准备。区分这两层，才能理解为什么用户程序不能临时指定“这次请求请跳到我提供的内核地址”。

表（p.24）：启动阶段的协议。

| OS（内核态） | 硬件 |

| 初始化陷入表 | 记住系统调用处理程序的地址 |

陷入表给受保护的入口提供定位信息。表由内核初始化，硬件记住相应入口；用户触发请求时通过约定路径进入，而不是任意传入一个内核执行地址。

| OS（内核态） | 硬件 | 程序（用户态） |
|---|---|---|

最容易卡住的是“第一次运行为什么也叫 return”。这里关键不在于历史上有没有真的陷入过，而在于内核先构造一个满足恢复格式的初始现场，再复用返回路径完成降权和跳转。于是新程序第一次开始，也能走与普通恢复一致的受保护机制。

**补充：模型边界。**表中“硬件恢复全部寄存器”“跳到 main”把体系结构细节与启动代码压缩在一起。真实实现可由硬件与入口/返回汇编分担保存恢复；不能由概念表推出每个寄存器都由硬件自动处理。本讲需要掌握的是参与方、权限和现场之间的顺序关系。

|---|---|---|

沿一次正常服务走：A 发起请求，保存 A 的用户现场，进入内核做服务，随后从 A 保存的现场恢复，回到请求之后继续。这解释了为什么不能简单“跳回 main 开头”：那会把已经执行过的用户逻辑重做。系统调用结果需要按约定交给程序；恢复现场并不意味着把本次服务的返回结果也抹掉。

## 即使程序不合作，OS 也要能回来

### 为什么光有系统调用还不够（p.26–27）【新】

**题面**（L07-CPU虚拟化-进程-2026T1.pdf · Problem 2 · p.26）

> **p.26** How can the OS regain control of the CPU so that it can switch between processes?

p.26 提出两条路线：合作式等待程序主动交回控制权；非合作式由 OS 借助硬件重新取得控制。前面的特权边界只保证“程序不能随意做敏感事”，还没有保证“它总会停下来让别人执行”。

p.27 的 cooperative approach 依赖进程周期性进行系统调用，例如 `yield` 主动让出执行机会。程序触发非法内存访问或除零等异常时，内核也会获得处理机会，但不能把“程序总会出错”当成调度保证。

**补充：按本页模型推演。**A 反复执行合法的加法和跳转，从不请求服务，也不主动让出。它既没有跨权限边界，也没有错误触发异常，因此 OS 没有从这两条路重新取得 CPU 的理由。若系统只有合作式机制，其他 Ready 进程可能持续等不到 CPU。讲义以“无限循环 → 重启机器”强调这个失控风险，这是对该机制的局限说明，不是说现代系统遇到任意死循环都需要重启。

`yield` 与阻塞也要分开：一个仍然能继续计算的进程主动让出 CPU，可以回 Ready；它没有因为礼让就凭空产生必须等待的 I/O 事件。

### 时钟中断提供不依赖程序意愿的入口（p.28）【新】

> **p.28** A timer interrupt gives OS the ability to run again on a CPU.

OS 在启动时配置 timer（定时器），定时器经过设定时间产生 interrupt（中断）。中断到来后，当前用户执行被暂停，必要现场被保存，控制转到事先配置好的内核处理程序。这个事件由硬件时间源触发，不要求应用调用 `yield`。

**补充：执行轨迹示例**（数字是我为演示取的，讲义没给）。设定时器每 5 ms 给内核一次处理机会：A 在 0 ms 开始死循环，5 ms 时中断到达，内核得以执行并检查是否改跑 B。A 没有合作，内核仍能回来；但“回来”本身还没有决定一定选 B。

要把三个动作分清：定时器**触发事件**，中断路径**进入内核并保留现场**，调度器**决定接下来运行谁**。缺少第一步，合作式死循环可能不交权；具备第一步，也不代表每次事件都必须换进程。

**考试角度**：（C 级 通识）这类知识点常见考法是给出永不系统调用的计算循环，说明合作式调度为何失去控制，以及时钟中断解决的是哪一个缺口。

### 调度决策与切换动作是两件事（p.29–30）【新】

p.29 先讲 scheduler（调度器）作决定：继续当前进程，还是改跑另一个？只有选择后者，才需要执行进程上下文切换。策略回答“选谁”，机制回答“怎样让所选者正确继续”。本讲着重机制，不预设公平份额或最短任务优先等策略。

p.30 的 context switch（上下文切换）由低层代码完成：保存当前执行需要保留的寄存器和续执行位置；找到下一个进程先前保存的现场；切到它的内核栈并恢复。kernel stack pointer（内核栈指针）很关键，因为调用链、保存值与返回地址都与当前栈绑定。

**补充：为什么不把整个地址空间复制一遍。**暂停进程的内存内容可以留在原来的存储位置；CPU 切换主要需要更换正在使用的执行现场，并在相应实现中切换必要的地址空间配置。不能把“上下文切换”理解为每次都重新从磁盘加载程序或复制全部内存。本讲 p.30 聚焦寄存器与内核栈，其他体系结构状态没有在这张列表中展开。

一个最小辨析：A 的中断处理完后仍选 A，会发生中断进入和返回，却不发生 A → B 的进程切换；若选 B，才要把当前内核执行现场交给 B 的现场。接下来两页把这个差别画成完整协议。

这里 X 是配置的时间间隔；讲义没有给具体数值，不能据此推断课程系统实际的时间片长度。

| OS（内核态） | 硬件 | 程序（用户态） |
|---|---|---|
| | | Process A 正在运行 |
| | timer interrupt | |

**补充：硬件与软件分工。**与 p.24–25 一样，协议表把入口保存现场概括放在硬件列；真实入口代码可能继续补存寄存器。这里强调保存的是被中断的 A，而非“中断一来就自动选定 B”。

| | 跳到 B 保存的 PC | |
| | | Process B 继续运行 |

这里有**两层不同目的的保存恢复**。第一层是“用户态 ↔ 内核态”的边界现场，使某个进程能回到它被中断的用户位置。第二层是“内核中的 A 执行路径 ↔ 内核中的 B 执行路径”的切换现场，使内核可以沿 B 的栈继续处理返回过程。

为什么不能用 A 的 trapframe 返回 B？因为 A 的用户 PC、栈、寄存器属于 A，B 必须恢复自己的那一份。为什么切换汇编结束后还需要 return-from-trap？因为切栈只是让内核在另一份内核现场上继续，尚未完成降权与恢复 B 用户现场。

**补充：地址演示**（数字是我为演示取的，讲义没给）。A 被打断时用户 PC 是 0x400120，B 先前暂停时用户 PC 是 0x500080。切换后返回 B，应继续 0x500080；A 的 0x400120 保留到下次 A 被选中时再用。二者都不是 `swtch` 自己执行的内核指令地址。

讲义将切换压成 A → B。具体内核可以经调度器自己的上下文中转；理解本表不需要假定“所有 OS 都由 A 直接跳进 B”。p.33 展示的是其中低层“切到另一份内核上下文”的动作。

**考试角度**：（C 级 通识）这类知识点常见考法是沿时钟中断画出保存 A、切到 B、恢复 B 的顺序，并说明 trapframe、内核 context 与内核栈之间的区别。

### swtch 为什么只换一个栈指针就能沿另一条调用链返回（p.33）

p.33 的关键声明是 `void swtch(struct context **old, struct context *new);`。`old` 指向一个存放“旧上下文地址”的槽，`new` 是已准备好的新上下文地址。双重指针的意义在于：函数需要修改调用者保存的那个指针，而不只是修改自己的一份参数副本。

以下抄出 p.33 的实际指令，省去原注释与行号；本次作静态讲解和栈模型核验，未在真实 x86 内核执行。

```asm
.globl swtch
swtch:
    movl 4(%esp), %eax
    movl 8(%esp), %edx
    pushl %ebp
    pushl %ebx
    pushl %esi
    pushl %edi
    movl %esp, (%eax)
    movl %edx, %esp
    popl %edi
    popl %esi
    popl %ebx
    popl %ebp
    ret
```

**思路分析（逐步读）**：

1. **先认语法和调用布局。**这里是 32 位 x86 的 AT&T 语法，操作数顺序是“来源、目的”。`%esp` 是当前栈顶指针，`4(%esp)` 表示读取地址 ESP+4 的内存；函数刚进入时，栈顶是调用者的返回地址，因此两个参数分别位于 ESP+4 与 ESP+8。前两条把 `old` 放入 EAX、把 `new` 放入 EDX，必须在改变 ESP 前拿到它们。
2. **把旧内核现场摆成 context。**四条 `pushl` 依次压入 EBP、EBX、ESI、EDI。32 位压栈每次先将 ESP 减 4，再写入值；压完后从新栈顶向高地址读，顺序成为 EDI、ESI、EBX、EBP、原先的返回地址，正好对应 p.14 的结构顺序。返回地址由调用本函数时留下，不需要再显式 `push eip`。
3. **保存地址，接管新栈，沿新路径返回。**`movl %esp, (%eax)` 把旧栈顶地址写进 old 指向的槽；括号说明写的是内存，而非只把 EAX 改成 ESP。`movl %edx, %esp` 是转折点，从此后续弹栈都读新栈。四次 `popl` 取出新进程保存的寄存器，`ret` 再从新栈取出返回地址作为 EIP，于是控制流沿另一份内核调用链继续。

`ret` 在这里不是“返回用户态”的指令。它只是使用当前栈中的返回地址；新的栈让同一条 `ret` 走到 B 的内核续执行位置。之后还需陷入返回路径才能回到 B 的用户程序。

**补充：为什么没有把所有寄存器都 push。**本页标的是 callee-saved registers（被调用方负责保持的寄存器），调用约定要求保留这部分。其他现场的责任由调用者、陷入入口或其他代码承担；只看这一段不能断言 EAX、EDX 等用户寄存器在整个切换中会丢失。相反，若在这里无依据增加或调换压栈字段，就会破坏与 context 布局的对应关系。

**算一遍**：用具体地址走完每条指令，验证旧栈保存了什么、新栈恢复后 ESP 与 EIP 是多少，<a name="r-a1"></a>[见附录 A1](#a1)。原件没有数值输入，附录的地址与寄存器值均为自取演示。

**考试角度**：（C 级 通识）这类知识点常见考法是给出 ESP 和新栈内容，要求追踪四次 push、两次 mov、四次 pop 与 ret，特别检查 `(%eax)` 的间接写入以及 ret 使用的是哪一份栈。

### 内核处理中断时再来一个中断怎么办（p.34）

**题面**（L07-CPU虚拟化-进程-2026T1.pdf · Concurrency Problems? · p.34）

> **p.34** What happens if, during interrupt or trap handling, another interrupt occurs?

内核也会修改共享数据结构，例如进程状态、队列和保存现场。如果一个更新尚未完成，就被另一个也访问同一结构的执行路径插入，后者可能看到半更新状态。问题不只在用户程序，内核本身也必须保护自己的管理数据。

p.34 给出两类手段：中断处理期间暂时禁止中断；通过锁保护内核内部数据结构的并发访问。它们不是两句可以无条件互换的口号。

**补充：具体交错。**设某路径正将 A 从等待队列移到就绪队列，先写了“可运行”状态，但还未完成队列链接，另一条路径便遍历队列调度。若没有保护，状态与成员关系可能暂时不一致。保护的目标是使其他相关执行者看到一个自洽的更新结果，而不是只让某个赋值语句变快。

暂时关中断可以避免本 CPU 在敏感区间被相应中断处理路径打断；**补充（通识）**：它不能单凭本 CPU 的动作阻止另一 CPU 同时访问共享数据，多核共享状态通常还需要锁等协调。关中断也不是永远关闭定时器，否则又破坏了前面建立的控制能力。具体锁与中断规则后续学习；本页能得出的结论是内核必须把嵌套与并发访问纳入设计。

### A1 用具体地址跑完 swtch（非讲义内容）

<a name="a1"></a>以下数字是我为演示取的，讲义没给。模型严格沿 p.33 的指令，不模拟整个内核；所有地址按字节编址，十六进制地址前缀为 `0x`，每次 push/pop 为 4 字节。

**初始输入**：A 刚进入 `swtch`，ESP=0x1000；内存 0x1000 存 A 的内核返回地址 0xAAAA；0x1004 存参数 old=0x3000；0x1008 存参数 new=0x2000。A 的 EBP=44、EBX=33、ESI=22、EDI=11。地址 0x3000 是供写入“旧 context 地址”的槽，不是旧寄存器对象本身。

B 的新 context 已准备如下，表内寄存器值为十进制：

| 地址 | 保存的意义 | 内容 |
|---|---|---|
| 0x2000 | B 的 EDI | 101 |
| 0x2004 | B 的 ESI | 102 |
| 0x2008 | B 的 EBX | 103 |
| 0x200C | B 的 EBP | 104 |
| 0x2010 | B 的内核返回位置 | 0xBBBB |

**逐指令执行。**

| 指令 | 执行结果 | ESP |
|---|---|---|
| `movl 4(%esp), %eax` | EAX 取得 old 的值 0x3000 | 0x1000 |
| `movl 8(%esp), %edx` | EDX 取得 new 的值 0x2000 | 0x1000 |
| `pushl %ebp` | 先减 4，再将 44 写到 0x0FFC | 0x0FFC |
| `pushl %ebx` | 再减 4，将 33 写到 0x0FF8 | 0x0FF8 |
| `pushl %esi` | 再减 4，将 22 写到 0x0FF4 | 0x0FF4 |
| `pushl %edi` | 再减 4，将 11 写到 0x0FF0 | 0x0FF0 |
| `movl %esp, (%eax)` | 内存 0x3000 收到 0x0FF0，记住 A 的 context 起点 | 0x0FF0 |
| `movl %edx, %esp` | 从此改用 B 的栈 | 0x2000 |
| `popl %edi` | 取出 101，再加 4 | 0x2004 |
| `popl %esi` | 取出 102，再加 4 | 0x2008 |
| `popl %ebx` | 取出 103，再加 4 | 0x200C |
| `popl %ebp` | 取出 104，再加 4 | 0x2010 |
| `ret` | EIP 取得 0xBBBB，再加 4 | 0x2014 |

**核对结果**：A 的旧 context 从 0x0FF0 起依次为 11、22、33、44、0xAAAA，字段顺序对应 EDI、ESI、EBX、EBP、EIP。B 最后得到 EDI=101、ESI=102、EBX=103、EBP=104、EIP=0xBBBB，ESP=0x2014。A 的值仍留在旧栈，且可由内存 0x3000 中保存的指针找到。

反向恢复也能检查：以后若 new 指向 0x0FF0，四次 pop 恢复 A 的四个寄存器，使 ESP 回到 0x1000；ret 再读出 0xAAAA，ESP 变成 0x1004。参数槽的后续处理依调用约定由调用路径负责。两次返回都回到对应的**内核**续执行点，不直接回到 A、B 的用户 PC。

以上保存布局、正向恢复和反向恢复已用独立 Python 栈模型执行断言核对；这只验证本例数据流，不等于在真实 xv6 内核执行过汇编。
