## 从资源管理进入进程

### 本讲放在课程的什么位置（p.1–3）【延伸 L01 p.8–11】

p.1 是标题页，主题是 CPU 虚拟化中的进程。

图（p.2）：课程由下至上的组织结构。  
元素：底部为课程概览与系统调用，上面依次是持久化、虚拟化、并发；红框标出虚拟化中的 Process and CPU Scheduling，其右侧标 HW#3。  
看什么：前面从用户程序调用 OS 服务，到文件系统与设备；现在转向 OS 如何安排执行程序的 CPU。本页的 HW#3 标签只说明课程组织关系，不是具体题目的考试证据。

p.2 所解决的问题是“接下来到底换了哪种资源”。文件系统决定文件如何组织，设备管理决定如何发起和完成 I/O，而这里要问：即使只有一个执行核心，为什么可以同时开着 shell、编辑器和其他程序？这不是给每个程序复制一颗物理 CPU，而是给每个执行实例保存状态，轮流让它使用 CPU。

> **p.3** The OS manages resources such as CPU, memory and disk via virtualization.

图（p.3）：Unix 系统结构示意。  
元素：上方用户程序与库通过系统调用接口进入内核；内核中有文件子系统、进程控制、调度和内存管理，下方经硬件控制连接硬件；图中区分用户层、内核层与硬件层。  
看什么：用户程序提出请求，内核管理共享资源；应用看到的接口与底层物理资源之间隔着一层管理机制。

p.3 将三种共享并列：很多程序分享 CPU，很多进程各自访问指令和数据却共享物理内存，很多进程访问设备却共享磁盘。这里的“虚拟化”是把有限的物理资源组织成便于程序使用的抽象，并不专指安装虚拟机软件。CPU 这一条主线可以先记成：**每个进程有自己的执行状态，CPU 在不同状态之间轮换。**

### 分时为何能制造“多颗 CPU”的观感（p.4–5）

p.4 为 Part I 分节页：The Abstraction: The Process。

> **p.5** Time sharing: Running one process, then stopping it and running another

p.5 的 time sharing（分时）表示把 CPU 的使用时间分给不同进程。这里“停止”指暂停执行，而不是销毁进程：只有把它暂存的执行位置与数据保留下来，之后才有可能接着做。

**补充：执行轨迹示例**（数字是我为演示取的，讲义没给）。设单核上 A、B 都持续需要 CPU，暂不计切换成本：0–5 ms 运行 A，5–10 ms 运行 B，10–15 ms 再运行 A。到 15 ms 时，A 得到 10 ms CPU 时间，B 得到 5 ms；两个程序都前进了，但没有任意一个瞬间是这两个进程同时在该核心上执行。第二段 A 没有运行，不代表 A 的代码或变量被删掉。

这也解释 p.5 的性能代价：每个进程不能独占全部 CPU 时间，切换本身还要做保存和恢复。分时提供的是多程序都能推进的能力，不会凭空增加物理计算能力。多核上的真正同时执行是另一个层面的并行，不要和这里的单核分时混为一谈。

## 把程序变成可管理的进程

### 进程不只是代码，还包括执行到哪一步（p.6）【延伸 L02 p.4】

> **p.6** A process is a running program.

程序是磁盘上的静态描述；进程是它的一次执行实例。这里 running program 是“处于执行生命周期中的程序”，不意味着它每一刻都占有 CPU。后面的 Ready、Blocked 仍然是进程。

p.6 列出两大组成部分。**地址空间**（address space）保存指令与数据：指令决定做什么，数据记录计算使用和产生的值。**寄存器**保存 CPU 当前正在使用的少量状态：program counter（PC，程序计数器）记录执行位置；stack pointer（SP，栈指针）标出当前栈顶位置，使函数调用、局部数据和返回路径能被正确找到。

**补充：暂停时究竟丢不得什么。**设进程已算到某条加法之前，某寄存器里放着中间值 7。如果只记住“它正在运行这个可执行文件”，恢复时就不知道从哪条指令继续，也不知道加法的输入。若只保存 PC，却没有恢复栈指针，下一次函数返回可能从别处取返回地址。因而“让进程继续”不是重新从文件第一条指令启动，而是恢复足够的执行现场。

同一程序可以形成多个进程。它们可以执行相同代码，却有不同参数、数据与执行位置；不要把程序文件名当成进程唯一身份。

**考试角度**：（C 级 通识）这类知识点常见考法是区分“两个进程运行同一程序”和“一个进程被暂停后恢复”，并指出恢复时为什么不能只保存代码。

### 进程 API 是能力清单，不是五个固定函数名（p.7）

p.7 列出 Create、Destroy、Wait、Miscellaneous Control 和 Status。它们分别回答：如何产生新执行实例，如何终止失控实例，如何等它停下，如何暂停与恢复，以及如何查询状态。不同 OS 可以用不同接口提供这些能力。

以已学概念作最小回顾：`fork()` 创建子进程；`exec` 替换当前进程运行的程序映像；`wait` 让父进程等待并取得子进程终止信息。三者的作用不能互换——换一个程序执行不必等于又创建一个进程，等待子进程也不等于父进程持续占住 CPU 检查它。

**补充：接口层与实现层。**本讲先列“OS 对外允许你做什么”，接下来追问“为了实现这些操作，OS 内部要准备哪些资源”。因此不要把 p.8–9 的通用启动步骤机械理解为每次 `fork()` 都必须从磁盘重新加载整个程序。

### 创建进程：装入代码，准备栈（p.8）【新】

> **p.8** Loading pieces of code or data only as they are needed during program execution.

p.8 的第一步是把可执行程序的代码装入进程地址空间。原件强调 lazy loading（按需装入）：程序逻辑上拥有可访问的代码与数据，不意味着每一字节都要在启动瞬间读入物理内存。先把运行所需的映射与状态准备好，用到某个部分时再将它取入，可以避免为尚未用到的内容付出读盘成本。

第二步是准备 run-time stack（运行时栈）。讲义列出局部变量、函数参数和返回地址：函数被调用后需要知道参数是什么、自己的临时数据放在哪，以及结束后回到调用方什么位置。栈把这类与调用嵌套相关的数据组织起来。

**补充：启动参数示例**（自编，非原题）。启动 `./sum 3 4` 时，用 C 的常见约定理解：`argc` 为 3，`argv[0]` 是程序名字符串，`argv[1]` 是字符串 `3`，`argv[2]` 是字符串 `4`，`argv[3]` 是空指针。参数字符串还不是整数，程序要自己转换。讲义说初始化栈中的参数，是在说明程序开始前必须有一个可供启动代码使用的参数环境；具体体系结构还会规定参数经哪些寄存器或内存位置传递。

易错点是把栈说成“保存所有程序数据”。代码、全局数据和动态分配的数据各有角色，栈主要承担这里所讲的调用相关状态。

### 创建进程：堆、标准输入输出与开始执行（p.9）

p.9 的第三步是准备 heap（堆），供程序显式请求动态存储。讲义使用 `malloc()` 和 `free()` 举例：申请后对象可以在函数返回后继续存在，直到被释放；这与随函数调用组织的栈不同。

第四步是其他初始化，特别是 I/O。讲义列出的三个默认描述符分别服务标准输入、标准输出、标准错误。**补充（通识）**：Unix 的常用编号为 0、1、2；它们并不必然都连接终端，也可以由 shell 重定向或继承其他连接。内核准备的是可访问对象的引用关系，而不是给每个进程复制一套键盘和屏幕。

最后才是将 CPU 控制权交给新程序。原件把入口称为 `main()`，且把最后一步也标成了“4”；这里保持动作顺序，将它理解为“启动用户程序”，不把重复编号当成额外算法分支。

**补充：讲义模型与实际启动的边界。**讲义说入口是 `main()`；通常的 C 运行环境会先执行运行时启动入口，再调用 `main()`。这里的重点是必须先准备环境再开始用户执行，不应从简化图推断内核在内核权限下直接调用任意用户 `main()`。Part 2 会补上受保护的进入用户态过程。

### 从磁盘文件到运行时地址空间（p.10）

图（p.10）：Loading: From Program To Process。  
元素：CPU、Memory 和 Disk 接到同一条示意总线；磁盘上的 Program 框通过红色虚线箭头指向内存中的 Process 框，后者标出 code、static data、heap 和 stack。  
看什么：装入把磁盘上可执行文件所描述的内容转为进程可使用的运行时环境；图中没有表示所有进程共享同一份可写栈。

代码区决定执行什么，静态数据为全局或静态对象提供存储，堆支持动态申请，栈支持调用过程。装入不是仅复制一个文件名，也不是把 CPU 永久交给它。

**补充：读图边界。**原图在磁盘 Program 框中也写了 heap，这是概念示意，不应据此认为程序未来通过 `malloc()` 创建的全部堆对象已经存在于可执行文件中。结合 p.8 的按需装入与 p.9 的运行时申请，应该把“文件提供的初始内容”和“执行时产生的状态”分开。

到这一步，进程具备了运行所需环境，但“准备好了”和“此刻真的在 CPU 上执行”仍是两回事。下一页正是为此引入状态。

## 暂停、等待与内核记录

### 三种状态分别缺少什么（p.11）【新】

> **p.11** A process is ready to run but for some reason the OS has chosen not to run it at this given moment.

**Running（运行）**：当前正占有处理器执行。**Ready（就绪）**：条件已经满足，只差被分配 CPU。**Blocked（阻塞）**：正在等待某件事完成，例如磁盘读请求的结果；即使 CPU 此刻空闲，进程也不能继续越过这次等待。

用“缺少什么”判断最稳妥：Ready 缺 CPU，Blocked 缺所等待的事件。一个进程并不是因为“没在运行”就一定 Blocked；被调度器暂停而且仍能继续计算的进程属于 Ready。

**补充：等待 I/O 的例子。**A 需要读盘上的数据再计算，如果数据尚未到达，让 A 继续执行后续计算就没有所需输入。OS 将它记为 Blocked，转而运行 B；这样等待外设的时间才有可能被其他有用计算覆盖。这里讨论会阻塞的请求，不是声称所有 I/O 调用都一定使进程阻塞。

### 四条转换边逐条走一遍（p.12）

图（p.12）：三状态转换图。  
元素：Running、Ready、Blocked 三个圆；Running → Ready 标 Descheduled，Ready → Running 标 Scheduled，Running → Blocked 标 I/O: initiate，Blocked → Ready 标 I/O: done；图中没有独立初态或终态标记。  
看什么：I/O 完成只使进程有资格重新竞争 CPU，不会跳过调度自动获得执行权。

四条边各有一个具体触发事件：

| 起点 | 事件 | 终点 | 为什么 |
|---|---|---|---|
| Ready | 调度器选中 | Running | 原先只缺 CPU，现在得到它 |
| Running | 被取消调度 | Ready | 暂停执行，但仍有运行条件 |
| Running | 发起需等待的 I/O | Blocked | 下一步依赖尚未到达的数据或结果 |
| Blocked | 等待的 I/O 完成 | Ready | 等待条件消失，重新具备运行资格 |

**补充：手工执行轨迹**（自编，非原题；按原图四条边展开）。

| 时点 | 事件 | A | B |
|---|---|---|---|
| 1 | A 正在计算，B 等 CPU | Running | Ready |
| 2 | A 发起阻塞读盘；调度器选 B | Blocked | Running |
| 3 | A 的读盘完成，暂不换人 | Ready | Running |
| 4 | B 被取消调度，再选 A | Running | Ready |

逐步检查：时点 2 包含两个动作，A 阻塞与 B 被调度；时点 3 只恢复 A 的资格，所以 B 可以继续运行；时点 4 才发生一次实际的运行者更换。四个时点均只有一个 Running，符合单核示例假设。

本图没有 Blocked → Running 的直接边，也没有 Ready → Blocked 的边。解这张图的题时按图走；现实 OS 可以有更丰富的状态，不应把这张三状态图说成全部实现的唯一模型。

**考试角度**：（C 级 通识）这类知识点常见考法是给出时间片结束、发起阻塞读、读完成等事件，要求标注每个进程状态，并解释为何“读完成”不等于“立即运行”。

### PCB 是进程在内核中的记录（p.13）【新】

> **p.13** An in-memory data structure that contains information about each process.

这句描述 PCB（Process Control Block，进程控制块）。OS 要能找到哪些进程 Ready、哪些 Blocked，以及当前执行者是谁，就不能只依赖 CPU 此刻那一组寄存器：寄存器只反映当前使用者，其他进程的信息需要保留在内存数据结构中。

p.13 的 process list 是“内核追踪进程的组织方式”；PCB 是“某个进程的记录”。实现可以使用表、链表或多种队列，不必把讲义的 list 理解为所有 OS 都只有一条单链表。

**补充：如何使用记录。**若 A 等待某个读盘请求，内核需要记住 A 的状态和等待对象；完成事件到来后，才能找到对应 A，将其改为 Ready。若只知道“存在一个阻塞进程”而没有身份与等待关系，就无法正确唤醒。进程地址空间存放程序内容，PCB 则为内核管理这个执行实例服务；两者不是同一块东西。

### xv6 用具体字段表达“以后还能恢复”（p.14）

p.14 给出教学用 xv6 的 x86 结构，保存的上下文字段顺序为 `edi`、`esi`、`ebx`、`ebp`、`eip`。这些是特定体系结构的寄存器名；`eip` 是该架构的指令指针。这里的 context 表示切换代码需要恢复的那部分执行现场，并非整个进程的全部内容。

p.14 的状态枚举比 p.11 多：

| 讲义字段 | 含义与三状态模型的关系 |
|---|---|
| UNUSED | 表项尚未供有效进程使用 |
| EMBRYO | 创建中的过渡状态 |
| SLEEPING | 对应等待事件的 Blocked |
| RUNNABLE | 对应 Ready，有资格运行 |
| RUNNING | 对应 Running |
| ZOMBIE | 已结束执行，保留终止信息等待回收 |

后面三种之外的状态并不推翻三状态模型，而是增加创建和退出阶段。特别是 ZOMBIE 不能当作“睡得很久的进程”：它已经结束，不是在等事件后继续计算。

**补充：与 Part 2 的联系。**p.33 的切换汇编压入 `ebp`、`ebx`、`esi`、`edi`，由于栈向低地址增长，压完后从栈顶向上恰好是 `edi`、`esi`、`ebx`、`ebp`，后面接调用时保存的返回地址。这解释了结构字段顺序不是随意排列；详细地址演算留在 Part 2。

### 逐个读懂 struct proc 的管理责任（p.15）

p.15 将这些信息装进 `struct proc`。下表保留全部字段，按讲义顺序解释；它是字段阅读表，不是可以直接编译的完整内核源码。

| 原字段 | 内核需要知道什么 |
|---|---|
| `char *mem` | 该讲义简化结构中的进程内存起点 |
| `uint sz` | 进程内存大小 |
| `char *kstack` | 该进程的内核栈所在位置 |
| `enum proc_state state` | 进程当前状态 |
| `int pid` | 进程身份编号 |
| `struct proc *parent` | 指向父进程记录，用于表示父子关系 |
| `void *chan` | 等待通道；非零时表示正在等哪个通道的事件 |
| `int killed` | 终止请求相关标志 |
| `struct file *ofile[NOFILE]` | 打开文件对象的引用数组 |
| `struct inode *cwd` | 当前工作目录的 inode 引用 |
| `struct context context` | 内核切换所需的寄存器上下文 |
| `struct trapframe *tf` | 当前陷入或中断对应的保存现场 |

按一次进程执行过程读这些字段：创建时分配身份与资源并关联父进程；运行中通过 `ofile` 与 `cwd` 解释文件访问；等待时通过 `state` 与 `chan` 说明为什么不能运行；进入内核与切换时通过 `tf`、`context`、`kstack` 保留继续执行的条件。`killed` 是一个标志，不要把“标志被设了”直接等同于全部终止和资源回收已经完成。

**补充：用户栈与内核栈。**用户栈服务应用自己的函数调用；内核栈服务进入内核后执行的内核代码与现场保存。字段 `kstack` 指向后者，不是 p.8 初始化 `argc`、`argv` 时所讲用户运行环境的简单别名。

**源代码版本边界。**p.15 写内嵌的 `struct context context`，而 p.33 的 `swtch` 参数是 `struct context **old` 与 `struct context *new`，其代码将栈地址写入一个上下文指针槽。两页是讲义展示的结构与汇编片段，不能未经适配拼成一份源码；本笔记分别按各页语义解释，不冒充已经在某版 xv6 上编译验证。

## 本讲核心考点

- 程序是静态文件，进程还需要地址空间与寄存器现场；p.5–6，C 级通识考法。
- 进程创建要准备代码、栈、堆和 I/O 环境，再交出执行权；p.8–10，C 级通识考法。
- Ready 缺 CPU，Blocked 缺事件；p.11–12，C 级通识考法。
- I/O 完成先回 Ready，调度后才 Running；p.12，C 级通识考法。
- PCB、内核栈、context、trapframe 各有不同职责；p.13–15，C 级通识考法。

1. A 等磁盘，B 正在执行；磁盘完成通知到来后，能否只凭这个事件断定 A 已 Running？
2. 同一个可执行文件启动两次，为什么只记录文件路径不足以区分两份执行现场？
3. 将 Blocked 的进程放到就绪队列但不满足其等待条件，为什么不能让计算凭空继续？

先自行说明原因，再看[参考解释](#selfcheck)。

<a name="selfcheck"></a>**参考解释（非讲义内容）**：第 1 题不能，只能推出 A 的阻塞条件解除，按本讲模型回 Ready；还要调度器真正选中才 Running。第 2 题两份执行有不同参数、变量、PC 与栈，因此文件路径不包含足够状态。第 3 题队列身份不会生成所缺的数据，内核必须按真正的等待条件管理可运行资格。
