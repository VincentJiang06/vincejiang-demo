## 每个进程为什么看到自己的内存

### 虚拟内存的三个目标（p.5–6）【延伸 L01 p.12–16】

> **p.5** What is memory virtualization?
>
> OS virtualizes its physical memory.
>
> OS provides an illusion memory space per each process.
>
> It seems to be seen like each process uses the whole memory .

> **p.6** Ease of use in programming
>
> Memory efficiency in terms of time and space
>
> The guarantee of isolation for processes as well as OS
>
> Protection from errant accesses of other processes

p.5的“illusion”指每个进程使用自己的地址视图，不必知道真实物理布局。它不是保证每个进程随时独占全部实际RAM。p.6列易用性、时空效率和隔离：程序易于管理自己的对象；实现不能为每次访存付出过高代价；出错进程不应任意破坏别人或内核。

隔离是需要检查与权限支持的目标，不会仅因把地址叫“virtual”自动出现。下一Part从最简单的加基址与界限检查解释这种支持。

### 从单程序到多程序驻留（p.7–8）

> **p.8** Load multiple processes in memory.
>
> Execute one for a short while.
>
> Switch processes between them in memory.
>
> Increase utilization and efficiency.
>
> Cause an important protection issue.
>
> Errant memory accesses from other processes

图（p.7–8）：同一物理内存的两种安排
元素：p.7低0–64KB为OS，余下只有当前程序；p.8同样保留OS，再分布进程C、B、A与空闲区，其中A在320–384KB。
看什么：多个进程同时驻留后，切换可直接选择另一个已驻留进程，但错误地址也可能落入他人的区域。

p.7只有一个用户程序时，等待I/O容易浪费CPU。p.8让多个程序留在内存以配合分时；“驻留多个”不等于单核“瞬间执行多个”。**算一遍**：图中A占384−320=64KB，B占256−192=64KB，C占192−128=64KB。三个用户区域合计192KB，而空闲区仍散布其间，不能把空闲总量当成一个连续区域。

### 代码、静态数据、堆和栈（p.9–11）【新】

> **p.9** OS creates an abstraction of physical memory.
>
> The address space contains all about a running process.
>
> That is consist of program code, data, heap, and stack

> **p.10** Code
>
> Where instructions live
>
> Data
>
> Global or static local variables
>
> Heap
>
> Dynamically allocate memory.
>
> malloc in C language
>
> new in object-oriented language
>
> Stack
>
> Store return addresses or values.
>
> Contain local variables arguments to routines.

p.9在16KB虚拟空间中把代码/数据放低端，堆从较低位置增长，栈在高端；中间留空以便增长。p.10逐一解释：code存指令；data存全局或静态局部变量；heap承载malloc等动态分配；stack存返回地址、调用参数和局部执行状态。变量在函数里声明不保证都属于栈，static局部变量就是本页特别指出的区别。

p.11的Linux图进一步列Text、Data、BSS、Heap、MMAP、Stack，左侧task_struct关联mm_struct，后者描述各范围，页表再把虚拟范围连接到物理内存。**补充**：BSS通常表示未显式初始化的静态存储区域；图画的是概念布局，现代程序的实际位置要现场查映射，不能背一个固定绝对地址。

图（p.11）：进程内存描述与映射
元素：task_struct→mm_struct，多个虚拟区域经page table→physical memory；heap与stack有相反增长箭头。
看什么：虚拟区域的连续排列不证明它们在物理内存中也连续。

**p.11 的完整区域与标记。** 从低地址向高地址，原图列出 Text、Data、BSS、Heap、MMAP、Stack。Text 的界限标为 start_code/end_code，Data 标为 start_data/end_data，堆的起点和当前边界为 start_brk/brk；mmap_base 标记映射区域基准，栈图标出 stack_start/stack_end。图中堆箭头向高地址、MMAP 和栈箭头向低地址。右侧简图把 data 标为 initialized data、bss 标为 uninitialized data，中间留白供堆与栈增长。箭头说明这一概念布局的增长方向，不能推出两者最终可以安全碰到一起；地址空间还有映射、保护和容量约束。

**补充：按生命周期给变量分类，而非只看声明位置。** 在一个函数中，`int x=1` 是自动存储期局部对象；`static int y=1` 的名字也只在该函数范围可见，但对象跨调用持续存在；`int *p=malloc(16)` 同时涉及局部指针 p 和另一个动态分配对象。p 的保存位置与它所指对象的位置不是同一个问题。

函数返回后，普通局部 x 的生命周期结束，不能把 `&x` 交给调用者当长久有效对象；动态对象则不会因为保存它的局部指针离开作用域而自动 free。若唯一指针丢失，会泄漏；若明确把所有权交给调用者，则由调用者在用完后释放。代码、静态数据、堆、栈的图帮助理解常见实现，但 C 对象存储期才是判断“现在还能不能用”的语义依据，编译器优化也可能把局部值保留在寄存器中。

:::hint 自测：malloc(1) 返回地址比映射起点大16字节，能否断定前16字节全是本次对象内容？

不能。返回对象保证的是请求的可用范围；映射包含分配器管理的区域，可能有元数据、对齐或其他对象。地址差只说明位置关系，不能从中反推出完整分配器布局，也不能授权访问 p 前面的16字节。

:::endhint

### 打印地址能观察到什么（p.12–14）

> **p.12** Every address in a running program is virtual.
>
> OS translates the virtual address to physical address

**课件程序与接口（p.12，原页片段）**

```text
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[]){

    printf("location of code  : %p\n", (void *) main);
    printf("location of heap  : %p\n", (void *) malloc(1));
    int x = 3;
    printf("location of stack : %p\n", (void *) &x);

    return x;
}
```

> **p.14** cat  /proc/\<pid\_number\>/maps                                                              pmap -x \<pid\_number\>

p.12分别打印main函数、malloc(1)返回指针和局部变量x的地址；三者对应代码、堆、栈。p.13示例为0x40057d、0xcf2010、0x7fff9ca45fcc，它们全是该进程所用虚拟地址，不能据此直接定位RAM芯片位置。

**算一遍**：图中的代码范围0x400000–0x401000，main偏移0x57d=1405字节；堆起点0xcf2000，返回地址0xcf2010距离起点0x10=16字节。这个差值告诉你返回对象在映射中的位置，不能证明分配器只消耗了1字节物理内存。

p.14演示`cat /proc/<pid>/maps`和`pmap -x <pid>`，用于查看映射范围、权限及映射对象。图中的地址是旧示例运行结果；代码地址高低、堆位置可能因平台与运行配置变化。此处不执行命令，重点是知道“进程映射”和“物理地址”是不同观察层次。

**考试角度**：（C 级 通识）常见考法是把某变量或打印地址归入代码、静态数据、堆或栈，并解释两个进程地址相同为何不代表数据共享。

**读数含义（补充）。** Kbytes 是映射大小，RSS 是当时驻留部分，Dirty 是相应脏页统计；原图总计分别为 2236、904、56 KiB，三列回答不同问题，不能把 2236 当成全部已占用物理页。以 libc 第一段为例，`0xb7f68000−0xb7d93000=0x1d5000`，除以 1024 得 1876，而 RSS 仅 688。截图中的权限和地址是例子的观察结果，不是所有 Linux 进程都应输出的固定模板。

**补充：虚拟范围、驻留量与实际使用量不是同一个尺寸。** 映射表的一行先描述进程能以哪些地址和权限访问某段范围；它不直接证明范围中的每个字节都已经对应一份独占的物理 RAM。文件映射、共享页和暂未驻留页都使“把虚拟区间长度相加”与“本进程独占了多少 RAM”不同。反过来，只看 malloc 请求的字节数，也看不到代码、栈、映射和管理结构等其他占用。

读本页 maps/pmap 输出时，先逐列写单位：起止地址相减得到字节范围，权限说明读写执行许可，Resident 表示当前驻留统计，Dirty 表示修改状态。两个进程映射了同一共享对象，分别统计时可能各自显示它；把两份进程统计简单相加未必等于系统实际占用翻倍。这里不需要猜一个真实地址，只需知道每一列回答的问题，才能避免拿地址空间图当 RAM 实物清单。

## 本讲核心考点

- 虚拟化追求易用、效率与隔离（p.5–6，C 级通识考法）。
- 虚拟布局不等于物理布局（p.7–11，C 级通识考法）。
- 指针打印的是虚拟地址，maps观察的是映射（p.12–14，C 级通识考法）。
