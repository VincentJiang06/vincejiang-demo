## 这次要突破物理内存的容量（p.1–3）

p.1 标题 Swapping 表明本讲讨论页面在内存与后备存储之间的移动。L11 已解决快速查映射和压缩页表，但一个有效虚拟页不一定要一直占用物理页框。

p.2 的课程图仍处在 Memory Management。它与上一讲是同一层的连续问题：地址映射提供独立的虚拟视图，换页则使活动程序的全部虚拟页不必同时常驻 RAM。图中 HW#4 没有具体题面，本篇不把它当作作业考点证据。

p.3 再画出 OS、系统调用、资源管理和硬件。一个用户态 load 本身不是磁盘读取函数；当该访存需要的页面不在内存，硬件异常才让 OS 有机会把磁盘中的页调回来，然后恢复原来的 load。理解这种透明性，是后面“重试指令”的前提。

## 后备层、虚拟空间和交换区（p.4–6）【延伸 L12 p.4–6（2022未核版）】

> **p.4** Require an additional level in the memory hierarchy.

p.4 的金字塔从寄存器、cache、main memory 到 mass storage。运行时不常用的页面可以留在下层存储，腾出快而有限的物理内存。图以硬盘为后备设备示例，重点是这一层容量与延迟的差别；不能据此把磁盘上的页面当作 CPU 能像普通 RAM 一样直接访问的页框。

p.5 强调，调用函数前需要相应代码可取指，访问数据前需要相应数据在内存。虚拟地址空间可以很大，但当某页真正被使用时，仍须安排物理驻留。多个进程还可以各自拥有较大的虚拟空间；这不保证它们所有页面同时访问时仍有足够 RAM，后面的 thrashing 正是资源需求失衡的后果。

p.6 把交换区画成以页为单位的磁盘块。原图中四个物理框与八个交换块如下，两个地址域各自编号，Block0 不是 PFN0：

| 物理页框 | 当前内容 |
|---:|---|
| PFN0 | Proc0 的 VPN0 |
| PFN1 | Proc1 的 VPN2 |
| PFN2 | Proc1 的 VPN3 |
| PFN3 | Proc2 的 VPN0 |

| 交换块 | 当前内容 |
|---:|---|
| Block0 | Proc0 的 VPN1 |
| Block1 | Proc0 的 VPN2 |
| Block2 | Free |
| Block3 | Proc1 的 VPN0 |
| Block4 | Proc1 的 VPN1 |
| Block5 | Proc3 的 VPN0 |
| Block6 | Proc2 的 VPN1 |
| Block7 | Proc3 的 VPN1 |

例如 Proc1 访问 VPN2 时，数据已经在 PFN1；访问 VPN0 时，则要根据交换位置 Block3 调入。不能因为“都是0”而去 PFN0，那里属于 Proc0。交换块内也以页保存内容，页内偏移在换入后仍保留；OS 需要记录的是这一虚拟页当前在哪里，以及是否已驻留。

## 内存已满和缺页不是同一个判断（p.7–9）【延伸 L12 p.7–12（2022未核版）】

p.7 问“内存满了怎么办”：选一个当前页换出或释放，以容纳新页。这种选择叫 page-replacement policy，机制负责执行搬运，策略决定牺牲谁。PTE 加上 present 信息：1表示页在物理内存，0表示当前不在；本讲专门采用“有效页已经换到磁盘”的简化模型。

p.8 在程序访问一个不驻留的页时引出 page fault。合法页暂时不驻留，可以调回来继续执行；非法地址却不能靠随便读一块磁盘修好。**补充（通识）**：真实系统的 not-present 不一定都对应交换区中的旧页面，也可能需要按需分配或从文件加载。本讲题目若明确给了交换区，就按图中的 swap-in 路径分析，不把所有异常一律叫磁盘缺页。

> **p.9** When the OS receives a page fault, it looks in the PTE and issues the request to disk.

p.9 的六条箭头把一次异常串起来：

1. **Reference**：用户指令访问虚拟地址，通过页表发现不驻留。
2. **Trap**：硬件转入 OS 的缺页处理，保存恢复程序所需的现场。
3. **Issue disk read**：OS 从页表或相关元数据取得磁盘位置，发起读取。
4. **Get the page**：内容读入为它准备的物理页框；尚未读完时不能让用户使用半页数据。
5. **Reset page table**：更新映射与 present 状态，使下一次转换能找到新页框。
6. **Reinstruction**：回到原指令重新执行，而不是跳过这次访问。

原文说可用 PTE 中原本容纳 PFN 的字段记录磁盘地址。含义是：当 present=0 时，OS 可以用另一个解释读取这些位；不是 CPU 把磁盘块号直接左移后就得到内存地址。必须结合状态解释字段。

## 硬件先分清 TLB、合法性与驻留（p.10–11）

p.10 是 TLB hit 分支，顺序与 L11 一样：从 VA 取 VPN → 查 TLB → 检查保护位 → 用 PFN 与 offset 拼成 PA → 读写内存。如果权限不符，报 protection fault；命中只是找到了翻译，不保证当前操作允许。

p.11 是 miss 分支。先用 PTBR 与 VPN 读出 PTE，再按原代码的顺序分岔：

| 已知状态 | 原伪代码下一步 | 为什么 |
|---|---|---|
| Valid=False | SEGMENTATION_FAULT | 虚拟页不合法，不能继续当作已有页 |
| Valid=True，权限不允许 | PROTECTION_FAULT | 页属于地址空间，但本次操作不允许 |
| 合法、权限允许、Present=True | TLB_Insert，RetryInstruction | 只缺缓存翻译，数据已在内存 |
| 合法、权限允许、Present=False | PAGE_FAULT | 需要 OS 准备页面内容 |

所以一次 TLB miss 最终可能很轻，也可能引发磁盘 I/O；不能把 miss 次数直接当作磁盘访问次数。课件以不同异常名区分逻辑原因，实际机器的异常编码未必照这个伪代码命名。

**算一遍（数字是我为演示取的，讲义没给）**：若 VPN5 的 PTE 合法、可读、present=1、PFN=20，而 TLB 没有5，那么只需补入 `5→20` 后重试；若其 present=0 且交换位置为 Block7，才进入软件换入。若 valid=0，Block7 这个字段即使碰巧有比特，也不能作为合法换入依据。

**考试角度**：（C 级 通识）常见考法是给同一地址的 TLB 和 PTE 状态，要求判定“补 TLB、权限异常、非法地址、换入”中的正确路径。

## 软件怎样恢复一条失败的访存（p.12）

p.12 的 `FindFreePhysicalPage()` 先找空闲页框。找到就直接使用；返回-1表示没找到，要执行 `EvictPage()` 取得一个可复用框。随后 `DiskRead(PTE.DiskAddr, pfn)` 将目标页读入这个框。请求线程可能等待 I/O，CPU 可以调度其他可运行线程；“等待磁盘”不等于整台 CPU 必须停住。

读取完成后，PTE 的 PFN 改为新框号，present 设为 true，最后重试指令。原伪代码把这些步骤压缩得很短，大小写 `PFN/pfn` 也只是示意；实现必须保证页内容、PFN、可见状态一致。不能先公开 present=1，再让别的执行者看到尚未完成的内容。

**补充（通识）**：若牺牲页被修改过且没有别的有效副本，复用该框前还必须保存修改；否则换入新页会永久覆盖旧进程的数据。后面的批量写回是在优化这种工作，不能把“Evict”简单理解成不问内容地清空框。

沿 p.6 的图作一条明确的**演示选择**：让 Proc1 的 VPN0（Block3）换入，假设策略选择 PFN0 的 Proc0 VPN0，且需要把它保存到原图空闲 Block2。先保存旧内容并使 Proc0 VPN0 不驻留，再把 Block3 读入 PFN0，更新 Proc1 VPN0 的 PTE 后重试。选择 PFN0 和 Block2 是本篇补充的动作，原图本身没有指定牺牲页。最终 Proc1 VPN0 的 offset 不变，只是映射到的新框为0。

## 低水位启动，高水位停止（p.13）【延伸 L12 p.13（2022未核版）】

p.13 说“等到完全满了才回收”不现实：缺页时才找牺牲页、写回、再读入，延迟会叠在一条请求上。系统可以让后台 swap/page daemon 提前维持一小批空闲页。

LW 是 Low Watermark，HW 是 High Watermark，二者计量的是**空闲页数**。空闲页少于 LW 时唤醒回收者；持续回收直到空闲页达到 HW。高低两个阈值留下缓冲区，避免空闲数在一个阈值附近变化就反复启停。

**算一遍（数字是我为演示取的，讲义没给）**：设 LW=10、HW=20，当前空闲9页触发回收。若期间没有新分配，至少回收11页才能达到20；若回收过程中程序又用了3页，则净需求变成14页。不能看到“达到10”就停止，也不能把 HW 误认成已使用页数的上限。

## 置换策略与平均访问时间（p.14）【延伸 L12 p.14（2022未核版）】

p.14 用 AMAT 衡量代价。公式按讲义原数学对象重排；派生 PDF 同页表格中的符号已修复显示：

$$
AMAT=T_M+P_{Miss}\cdot T_D.
$$

$T_M$ 是内存访问代价，$T_D$ 是这个简化模型中的额外磁盘代价；$P_{Miss}$ 是需要下层存储的概率，$P_{Hit}=1-P_{Miss}$。这里 miss 指内存层未命中、需要处理页面，不是前面的 TLB miss。公式来自按概率加权：命中耗时 $T_M$，未命中耗时 $T_M+T_D$，所以：

$$
P_{Hit}T_M+P_{Miss}(T_M+T_D)
=(P_{Hit}+P_{Miss})T_M+P_{Miss}T_D.
$$

概率之和为1，得到原式。实际缺页还可能有软件处理、写回等额外费用；使用原式算题时，先确认这些费用是否已包含在给定的 $T_D$ 中。

**算一遍（数字是我为演示取的，讲义没给）**：$T_M=100$ ns，$T_D=10$ ms=$10^7$ ns。即便 $P_{Miss}=10^{-4}$，也有 $AMAT=100+10^{-4}\times10^7=1100$ ns，是纯内存时间的11倍。若希望 AMAT 不超过200 ns，则 $P_{Miss}\le(200-100)/10^7=10^{-5}$。很小的缺页比例仍可能昂贵，关键是磁盘项远大于内存项。

本页接着列出 LRU：淘汰最久未访问的页，利用访问历史预测近期需求。算法的“最近使用”与 L11 相同，但对象变为驻留数据页框；L11 淘汰 TLB 项只丢翻译，而这里可能触发保存页面内容。不要把同名策略的两种成本等同。

## 提前读与合并写（p.15–16）【延伸 L12 p.15–16（2022未核版）】

p.15 的 prefetching 图中，Page1 被调入时，OS 猜测 Page2 很快也会访问，于是提前读入。若程序确实顺序扫描，访问 Page2 时它可能已经驻留，减少等待。代价是预测错误时白读一页，还占用本可留给别人的页框。因此 prefetch 是把“等需要才读”变成“基于预测先读”，不是免除 I/O 成本。

p.16 的 clustering/grouping 从写入方向减少开销：先收集多个 pending writes，再以较大批次写出。图中 Page1–4 待写，汇集后一次较大写入替代多次小写入。相同数据量下，合并可摊薄每次请求的固定开销、改善连续访问；收益取决于存储布局与设备，不代表任何四页都能无条件拼成一个物理连续请求。还没安全写出的脏页不能因“已加入队列”就马上丢弃内容。

## 需求过量为何使 CPU 反而闲下来（p.17–18）【延伸 L12 p.17（2022未核版）】

> **p.17** Memory is oversubscribed and the memory demand of the set of running processes exceeds the available physical memory.

p.17 的 thrashing 图横轴是多道程序程度，纵轴是 CPU 利用率。初期增加进程可填补某进程等待 I/O 的空隙，利用率上升；若同时活动的工作集已经放不下，页面刚被调入又被别的需求挤出去，程序不断缺页、等待，利用率反而陡降。工作集可先理解为某一阶段频繁需要的那批页，而不是进程虚拟地址范围的全部页。

讲义提出暂不运行一部分进程，让剩余工作集能放进 RAM。**算一遍（数字是我为演示取的，讲义没给）**：可用数据页框100个，三个活动进程各需45页且没有共享，共135页；暂停一个后需求90页，才可能同时容纳。是否真正避免抖动仍取决于访问模式和其他内存开销，但这说明“再增加进程补 CPU 空闲”在抖动阶段可能适得其反。

p.18 将本讲合为两层：交换机制负责保存、调入、更新映射与重试；置换管理回答何时回收（LW/HW）以及选谁（如 LRU）。然后课程进入并发：多个线程共享地址空间时，页面已经在内存也不代表共享变量能安全更新。

## 本讲核心考点

- 分清 VPN、PFN、交换块号三个编号域（p.6，C 级 通识）。
- TLB miss、地址无效、权限错误与不驻留缺页的路径不同（p.7–11，C 级 通识）。
- 缺页处理必须准备框、完成读取、更新映射并重试（p.9、12，C 级 通识）。
- LW/HW 基于空闲页数，启动与停止条件不同（p.13，C 级 通识）。
- AMAT 统一时间单位，概率指对应存储层 miss（p.14，C 级 通识）。
- 预取依赖预测，合并写回减少请求开销（p.15–16，C 级 通识）。
- 抖动来自活动工作集竞争，降低并发活动需求可能改善利用率（p.17，C 级 通识）。
