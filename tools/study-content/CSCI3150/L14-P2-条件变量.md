## 父线程需要等待哪件事（p.20–22）

> **p.22** What we would like to see here is:

p.20 是条件变量分节页。p.21 把等待目标写成一个能判断真假的条件，例如「子线程已完成指定工作」。此时父线程即使拿得到一把空闲锁，也无法由此推知子线程是否已经做完。

p.22 的题面给出期待的输出顺序 `parent: begin → child → parent: end`。第一行在创建子线程前，天然排在前面。创建成功只表示子线程可以运行，父线程可能马上执行最后一次打印。要使第三行一定排在第二行之后，子线程需在打印后宣布完成，父线程需在观察到完成后才能继续。

## 用状态记住事件，用等待队列省下 CPU（p.23–25）【新】

> **p.25** Before returning after being woken, the wait call re-acquires the lock.

p.23 用 `done` 记住事件，子线程打印后写 1，父线程在 0 时循环检查。即使子线程只改一次，父线程也可能空转整个时间片。**补充**：讲义此处用 `volatile` 演示忙等。在 C 的线程模型中，普通共享整数加上 volatile 仍缺少跨线程同步，实际代码应采用后面的锁协议或适当的原子操作。

p.24 **条件变量**（condition variable，CV）提供等待队列。`pthread_cond_wait(&cond, &mutex)` 用于当前条件尚不满足的线程；另一个线程在改变共享状态后 `pthread_cond_signal(&cond)`，让等待者有机会继续。条件是否成立由受保护的数据表达，譬如 `initialized`，单从队列看不出来。

p.25 等待者先持锁检查 `initialized`。若为 0，wait 把「释放锁并进入等待」相对于另一个持该锁的通知者连为一步。于是通知者能取得锁、把它改成 1 并发出 signal。等待者被唤醒后还要重新获得原锁，wait 才返回。若它抱着锁睡觉，通知者连改值的机会都没有。

## 从 while 到一个完整的 join（p.26–28）

> **p.26** The waiting thread re-checks the condition in a while loop, instead of a simple if statement.

p.26 即使刚收到通知，线程也可能花一阵才拿回锁。此间共享状态可以再变一次。把 wait 放进 `while`，返回位置就通向下一次判断；只有当前亲自读到条件为真，才离开循环。

p.27 用三个对象实现等待。整数 `done` 初始为 0，互斥锁 `m` 保护所有相关读写，条件变量 `c` 接收等待者。子线程打印后进入 `thr_exit`，持锁写 1、signal、解锁。父线程在 `thr_join` 中持锁检查；子线程先完成时，父线程第一次检查就能过去。

**对照读法（按 p.27 缩写）**。两列逻辑各由一个线程执行。

```text
父线程                         子线程（已打印 child）
lock(m)                        lock(m)
while done == 0:               done = 1
    wait(c, m)                 signal(c)
unlock(m)                      unlock(m)
```

p.28 把这些函数接回 main。创建子线程后调用 `thr_join()`，返回才打印结束语。因子线程把 `done` 写为 1 之前已打印，期望的三行顺序成立。这里自定义的 join 等的是这个标记，真实库函数还处理线程终止与相关资源。

## 两种丢失唤醒的路径（p.29–31）

> **p.30** Imagine the case where the child runs immediately.

p.29 从父线程先运行的情况跟踪。父检查到 0 后在 wait 内解锁睡眠。子打印、写 1、signal，此时父可以变为就绪；子解锁后，父才能在持锁状态下重新检查 1 并完成。课件把更新状态写在通知之前，并用同一把锁保护这两步。父线程判断 done 的时刻在它重新获得锁之后；即使发生虚假唤醒，它也会回到 while 检查。

p.30 删掉 `done`，只保留锁和通知。若子先运行，此刻队列里没人，signal 随即结束。父随后到来，无条件 wait，再没人会叫醒它。保留一个持久的完成标志，就能让晚到者读出已经发生的事件。

p.31 换一种删法：保留 `done`，却拆掉保护检查与等待的锁。父刚读到 0 就被切走，子写 1 并通知空队列，父回来沿着早已选定的分支睡下。此时内存的确是 1，父却没有机会再读。修复要让「查条件 → 进入等待」与通知者使用同一互斥协议。页中单参数 wait 是说明错误思路的简写。

## 有界缓冲区的两个进入条件（p.32–34）【新】

> **p.34** Only put data into the buffer when count is zero.

p.32 网络服务器的生产者把收到的 HTTP 请求放入工作队列，消费者取走处理。两者速度可以不同。有限容量意味着生产者有时得等空位，消费者有时得等数据。

p.33 的管道例子是 `grep foo file.txt | wc -l`。grep 把匹配行写入内核缓冲，wc 从中读取并统计行数。缓冲满时写方需要等读方腾空间，空时读方可能等下一批数据。这里的管道说明相互依赖，后面的共享变量是演示这种关系的线程模型。

p.34 容量先取讲义的 1。`buffer` 放整数，`count` 记录目前是否有货。put 要求 0，写入后变 1；get 要求 1，取出后变 0。assert 只能在条件被违反时报告，不能让调用者等待条件成立。

## 一个锁和一个条件变量够吗（p.35–37）

> **p.37** If we have more than one of producer and consumer?

p.35 生产者依次写整数，消费者循环取出并打印。若生产者连跑两轮，第二次 put 遇到上一份还在槽里；若消费者先跑，第一次 get 就遇到空槽。需要把「现在可以操作吗」的判断与等待一起补进来。

p.36 生产者 p1 取得 mutex，在 p2 检查满时到 p3 等待，随后 p4 写入，p5 signal，p6 解锁。把 signal 放在写入之后，等待者才有新的状态可检查。

p.37 消费者对应在 c2 检查空，在 c3 等待，c4 取数据，c5 通知，c6 解锁。在讲义假设的单生产者、单消费者且无额外唤醒的轨迹里，发给另一方的通知能使它继续。若再加一个消费者，两个人就可能先后依赖同一次「有货」；下面的表给出具体反例。

## 醒来时那件货已经被取走（p.38–40）

> **p.38** Oh oh! No data

p.38 的列名 Tc1、Tc2、Tp 分别代表两个消费者和生产者，小写 c1–c6、p1–p6 是代码行号。沿 Count 列看这五步：

| 执行者 | 操作 | count | 等待者接下来能做什么 |
|---|---|---|---|
| Tc1 | 发现空，在 c3 睡眠 | 0 | 释放锁 |
| Tp | p4 放入，p5 唤醒 Tc1 | 1 | Tc1 进入就绪队列 |
| Tp | 再次想放入，满，在 p3 睡眠 | 1 | 释放锁 |
| Tc2 | 先抢到锁，c4 拿走唯一数据，c5 唤醒 Tp | 0 | Tc1 仍未取到货 |
| Tc1 | 恢复后越过 if，直接执行 c4 | 0 | get 的断言失败 |

p.39 用 **Mesa 语义**解释 Ready 和 Running 的区别。signal 后等待者获得重新竞争的机会，轮到它时条件可能已改变。课件用 Hoare 语义作对照，后者立即把执行机会交给被唤醒者。按前者写程序，就必须在重新持锁时作决定。

p.40 把生产者 p2 改为 while，消费者也按相同原则复查。重走上表最后一行，Tc1 改走「count 为 0，回到 c3」，这次不会从空槽取数据。仍须检查另一件事：真正能继续的人会不会一直睡着？

## while 保护了取数，仍可能叫错人（p.41–43）

> **p.43** Everyone asleep …

p.41 消费者醒后在 c2 重查，这使 c4 的前置条件成立。但 producer 和 consumer 仍睡在同一个 cond 上，c5 无法表达「请叫一个等空位的人」。

p.42 表从两个消费者都因空而睡开始。Tp 放一件货，只唤醒 Tc1；Tp 下一轮因满也睡下。Tc1 取货后槽空，真正能工作的是 Tp。偏偏这次 signal 选中也在同队列的 Tc2。

p.43 续表中，Tc1 再次取货时看到空，睡下。Tc2 醒后正确地重查，也因空睡下。最后 count 为 0，两个消费者和唯一的生产者全在睡。没有人取错数据，却也没有人再制造下一次通知。这是进展失败。<a name="r-a1"></a>[见附录 A1](#a1)。

## 把等空位与等数据的人分开（p.44–45）

> **p.44** Use two condition variables and while

p.44 生产者满时等 `empty`，put 后通知 `fill`。用变量名描述「我在等什么」最容易读对。两条等待队列共用一把 mutex，因为两方读写的是同一个缓冲状态。

p.45 消费者空时等 `fill`，get 后通知 `empty`。回到 p.42 的岔路，Tc1 取货后只能从等空位的队列唤醒人。通知方向解决叫错角色，while 解决目标角色拿到锁时资源可能已被同行抢先使用。

## 从一个槽扩展到环形缓冲（p.46–48）

> **p.48** p2: A producer only sleeps if all buffers are currently filled.

p.46 用 `fill` 指下次写的位置，`use` 指下次读的位置，`count` 指占用槽数。两个下标前进一格后对 MAX 取余。**算一遍**（容量 2 和数据 A、B、C 为自取）：从三个量均为 0 开始，放 A、B 后 fill 回到 0，count 为 2；取 A 后 use 为 1，count 为 1；放 C 覆写空出的 0 号槽。此后依次取到 B、C。初始和装满时两个下标都相等，单靠它们无法分辨空满。

p.47 把这两个例程放进锁内。生产者仅在 `count == MAX` 时等待，写好后通知 full；消费者仅在 `count == 0` 时等待。注意数组写下标 fill 与前页同名的条件变量承担不同职责，本版用 full 命名「已有数据」的队列。

p.48 取货后通知 empty，再解锁和打印。容量增大后生产者可以连续放入多件，双方不用每件都切换一次。同一时刻修改槽位、下标与计数的代码仍由 mutex 串行保护。

## 一次释放 50 字节，该叫醒谁（p.49–51）【新】

**原题｜L14 p.49 · Covering Conditions**

> **p.49** Which waiting thread should be woken up?

p.49 从空闲 0 字节开始，Ta 要 100，Tb 要 10，两者都睡，Tc 归还 50。现在 Tb 的请求能够满足；若它获得分配，余下 40。Ta 即使先醒，也必须再睡。若 signal 只叫到 Ta，明明有 50 字节够 Tb 使用，Tb 却可能一直等不到下一次通知。

p.50 在分配者的锁内比较 `bytesLeft < size`，不足就 wait，否则实际分配并扣去 size。归还者持同一把锁增加 bytesLeft。一个 CV 上的等待者各带不同的 size，因此仅凭「有人释放」无法直接从队列中挑出适合者。

p.51 采取广播（broadcast），让所有等待者醒来、依次拿锁，各自按当前余量判断。Ta 先拿锁也会重新睡，Tb 随后能分走 10；若 Tb 先拿锁，Ta 看见 40 也会重新睡。代价是更多唤醒和锁竞争。所有请求都等待“可用内存发生变化”这一较宽的条件，再分别检查自己的具体请求是否满足。这个较宽的条件称为 **covering condition**。
