### p.21–23：互斥之外，还需要先后关系

> **p.21** There are many cases where a thread wishes to check whether a condition is true before continuing its execution.

> **p.23** Parent waiting fore child: Spin-based Approach

> **p.23** This is hugely inefficient as the parent spins and wastes CPU time.

**课件程序与接口（p.23，原页片段）**

```text
1   volatile int done = 0;
2
3   void *child(void *arg) {
4       printf("child\n");
5       done = 1;
6       return NULL;
7   }
8
9   int main(int argc, char *argv[]) {
10      printf("parent: begin\n");
11      pthread_t c;
12      Pthread_create(&c, NULL, child, NULL); // create child
13      while (done == 0)
14          ; // spin
15      printf("parent: end\n");
16      return 0;
17  }
```

原例希望输出严格为 `parent: begin`、`child`、`parent: end`。仅创建child不足以保证最后一行等到它完成；父线程不断轮询done会浪费CPU，普通 `volatile`也不能代替同步。需要一份持久状态done和等待机制。

### p.24–26：wait的三个环节缺一不可

> **p.24** Condition variables are useful when some kind of signaling must take place between threads.
>
> pthread\_cond\_wait:
>
> Put the calling thread to sleep on a queue.
>
> Wait for some other thread to signal it.
>
> pthread\_cond\_signal:
>
> Unblock at least one of the threads that are blocked on the condition variable

**课件程序与接口（p.24，原页片段）**

```text
int pthread_cond_wait(pthread_cond_t *cond,
                       pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);
```

> **p.25** A thread calling wait routine:
>
> The wait call releases the lock when putting said caller to sleep.
>
> Before returning after being woken, the wait call re-acquires the lock.
>
> A thread calling signal routine:

**课件程序与接口（p.25，原页片段）**

```text
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t init = PTHREAD_COND_INITIALIZER;

pthread_mutex_lock(&lock);
while (initialized == 0)
    pthread_cond_wait(&init, &lock);
pthread_mutex_unlock(&lock);
```

**课件程序与接口（p.25，原页片段）**

```text
pthread_mutex_lock(&lock);
initialized = 1;
pthread_cond_signal(&init);
pthread_mutex_unlock(&lock);
```

> **p.26** The waiting thread re-checks the condition in a while loop, instead of a simple if statement.
>
> Without rechecking, the waiting thread will continue thinking that the condition has changed even though it has not (the condition can be changed before an awakened thread returns from pthread\_cond\_wait()).

`pthread_cond_wait(&c,&m)` 在持锁调用时，原子地释放m并进入等待；醒来后先重新取得m才返回。它不是“抱着锁睡觉”。调用方应在 `while(!predicate)` 内wait，返回后重新检查谓词，因为其他线程可能先拿走资源，也可能发生无需对应signal的唤醒。

signal只是通知等待者有机会重新检查，既不转移mutex所有权，也不存储一个永久事件。

### p.27–29：done使两种执行顺序都成立

> **p.27** Parent waiting for Child: Use a condition variable

**课件程序与接口（p.27，原页片段）**

```text
1   int done = 0;
2   pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
3   pthread_cond_t c = PTHREAD_COND_INITIALIZER;
4
5   void thr_exit() {
6       Pthread_mutex_lock(&m);
7       done = 1;
8       Pthread_cond_signal(&c);
9       Pthread_mutex_unlock(&m);
10  }
11
12  void *child(void *arg) {
13      printf("child\n");
14      thr_exit();
15      return NULL;
16  }
17
18  void thr_join() {
19      Pthread_mutex_lock(&m);
20      while (done == 0)
21          Pthread_cond_wait(&c, &m);
22      Pthread_mutex_unlock(&m);
23  }
24
```

**课件程序与接口（p.28，原页片段）**

```text
(cont.)
25  int main(int argc, char *argv[]) {
26      printf("parent: begin\n");
27      pthread_t p;
28      Pthread_create(&p, NULL, child, NULL);
29      thr_join();
30      printf("parent: end\n");
31      return 0;
32  }
```

> **p.29** Parent:
>
> Create the child thread and continues running itself.
>
> Call into thr\_join() to wait for the child thread to complete.
>
> Acquire the lock
>
> Check if the child is done
>
> Put itself to sleep by calling wait()
>
> Release the lock
>
> Child:
>
> Print the message “child”
>
> Call thr\_exit() to wake the parent thread
>
> Grab the lock
>
> Set the state variable done
>
> Signal the parent thus waking it.

原代码child在锁m内设置done=1并signal；parent在同一锁内循环检查done，若为0则wait。若parent先来，它释放锁睡眠，child可以取得锁更新并唤醒。若child先完成，done已是1，parent根本不wait。两条路径都形成目标打印顺序。

p.29把“睡眠、释放锁”列为两行只是说明；真正接口要保证它们与通知者的同步不可出现丢失通知的间隙。

**补充：done是事实，signal只是提醒。** 可以把done理解为一块由锁保护的告示牌，写上“孩子已完成”后会一直保留；signal只是提醒当前等待者再看牌。若没人正在等，提醒可以消失，但事实仍在，所以后来到达的parent看见done=1就不必睡。

正确顺序的要点不在于“signal一定要让谁马上跑”，而在于parent持锁检查done与释放锁进入等待之间不能让child插入一个无法被观察到的完成。cond_wait把释放与等待协调起来；返回前又拿回锁，保证重新读取谓词时和修改者遵守同一协议。拿着锁普通sleep则会阻止child写done；先手工解锁再普通sleep则可能错过完成，两个看似相近的替代都不成立。

### p.30–31：有通知没状态、有状态没锁都不够

> **p.30** Imagine the case where the child runs immediately.
>
> The child will signal, but there is no thread asleep on the condition.
>
> When the parent runs, it will call wait and be stuck.
>
> No thread will ever wake it.

**课件程序与接口（p.30，原页片段）**

```text
1   void thr_exit() {
2       Pthread_mutex_lock(&m);
3       Pthread_cond_signal(&c);
4       Pthread_mutex_unlock(&m);
5   }
6
7   void thr_join() {
8       Pthread_mutex_lock(&m);
9       Pthread_cond_wait(&c, &m);
10      Pthread_mutex_unlock(&m);
11  }
```

> **p.30** thr\_exit() and thr\_join() without variable done

> **p.31** The issue here is a subtle race condition.
>
> The parent calls thr\_join().
>
> The parent checks the value of done.
>
> It will see that it is 0 and try to go to sleep.
>
> Just before it calls wait to go to sleep, the parent is interrupted and the child runs.
>
> The child changes the state variable done to 1 and signals.
>
> But no thread is waiting and thus no thread is woken.
>
> When the parent runs again, it sleeps forever.

**课件程序与接口（p.31，原页片段）**

```text
1   void thr_exit() {
2       done = 1;
3       Pthread_cond_signal(&c);
4   }
5
6   void thr_join() {
7       if (done == 0)
8           Pthread_cond_wait(&c);
9   }
```

删done后，child先signal但当时无人等待，parent后来的wait会永久睡下。删mutex后，即便保留done，也可能parent读0→切到child写1并signal→parent才开始wait，仍错过通知。共享谓词、保护它的锁、wait原子释放入队一起才封住这条缝隙。

### p.32–34：有界缓冲区的两个谓词

> **p.32** The Producer / Consumer (Bound Buffer) Problem

> **p.32** Producer
>
> Produce data items
>
> Wish to place data items in a buffer
>
> Consumer
>
> Grab data items out of the buffer consume them in some way
>
> Example: Multi-threaded web server
>
> A producer puts HTTP requests in to a work queue
>
> Consumer threads take requests out of this queue and process them

> **p.33** A bounded buffer is used when you pipe the output of one program into another.
>
> Example: grep foo file.txt \| wc –l
>
> The grep process is the producer.
>
> The wc process is the consumer.
>
> Between them is an in-kernel bounded buffer.
>
> Bounded buffer is Shared resource  Synchronized access is required.

> **p.34** Only put data into the buffer when count is zero.
>
> i.e., when the buffer is empty.
>
> Only get data from the buffer when count is one.
>
> i.e., when the buffer is full.

**课件程序与接口（p.34，原页片段）**

```text
1   int buffer;
2   int count = 0;  // initially, empty
3
4   void put(int value) {
5       assert(count == 0);
6       count = 1;
7       buffer = value;
8   }
9
10  int get() {
11      assert(count == 1);
12      count = 0;
13      return buffer;
14  }
```

管道 `grep foo file.txt | wc -l` 可视为生产者把字节写入内核缓冲，消费者取出。单槽原例有buffer与count，put要求count=0并置1，get要求count=1并置0。这些assert只是检查前提，不负责等前提成立，也不阻止并发。

### p.38–39：醒来的消费者被另一个抢先

图p.38的完整关键轨迹是：C1发现空并睡→P放入一项count=1、唤醒C1→P下一轮见满睡→C2先得锁取走，count=0，并通知P→C1终于返回wait，却跳过检查执行get，断言失败。被唤醒只代表ready，不代表立即运行。

旧PDF的p.38注释与p.39采用不一致的兼容图片；已回查原始PPTX正文层。p.39真正解释的是Mesa与Hoare语义：Mesa下被唤醒者不保证立即运行，期间缓冲可被C2改变，故醒来必须重查；Hoare语义提供被唤醒者立即运行的更强保证。课件以Mesa作为常见系统模型，不能把signal理解成直接移交CPU与条件。

**表（p.38）：if 版本逐行状态。** R=运行，Q=就绪，S=睡眠；c1/p1 是加锁，c2/p2 检查，c3/p3 等待，c4/p4 取/放，c5/p5 通知，c6/p6 解锁。每行状态是该步之后；这些符号对应前面的完整程序。

### p.42–43：唤醒同类导致没人能改变条件

> **p.43** A consumer should not wake other consumers, only producers, and vice-versa.

> **p.43** Thread Trace: Broken Solution (Version 2) (Cont.)

### p.44–45：两个CV分别等待两种状态

> **p.44** Use two condition variables and while
>
> Producer threads wait on the condition empty, and signals fill.
>
> Consumer threads wait on fill and signal empty.

**课件程序与接口（p.44，原页片段）**

```text
9               Pthread_cond_wait(&empty, &mutex);
```

```text
(Cont.)
16  void *consumer(void *arg) {
17      int i;
18      for (i = 0; i < loops; i++) {
19          Pthread_mutex_lock(&mutex);
20          while (count == 0)
21              Pthread_cond_wait(&fill, &mutex);
```

```text
9               Pthread_cond_wait(&empty, &mutex);  // p3
10          put(i);                     // p4
11          Pthread_cond_signal(&full);         // p5
12          Pthread_mutex_unlock(&mutex);       // p6
13      }
14  }
15
16  void *consumer(void *arg) {
17      int i;
18      for (i = 0; i < loops; i++) {
19          Pthread_mutex_lock(&mutex);         // c1
20          while (count == 0)          // c2
21              Pthread_cond_wait(&full, &mutex);   // c3
22          int tmp = get();                // c4
```

> **p.48** p2: A producer only sleeps if all buffers are currently filled.
>
> c2: A consumer only sleeps if all buffers are currently empty.

课件最终put使用 `buffer[fill]=value; fill=(fill+1)%MAX; count++;`，get对应读取use位置、递增use并count--。producer仅在count==MAX等待，consumer仅在count==0等待；始终保持 $0\le count\le MAX$。

**补充完整演算**：MAX=3，初始fill=use=count=0；put10→(1,0,1)，put20→(2,0,2)，get得到10→(2,1,1)，put30→(0,1,2)，put40→(1,1,3)。此时fill==use却是满；初始二者也相等却是空，必须用count或等价状态区分。缓冲扩大允许生产消费阶段更灵活交错，但被同一mutex保护的单次put/get仍互斥。

### p.49–51：不同等待者的条件不一样时用broadcast

**课件程序与接口（p.50，原页片段）**

```text
1   // how many bytes of the heap are free?
2   int bytesLeft = MAX_HEAP_SIZE;
3
4   // need lock and condition too
5   cond_t c;
6   mutex_t m;
7
8   void *
9   allocate(int size) {
10      Pthread_mutex_lock(&m);
11      while (bytesLeft < size)
12          Pthread_cond_wait(&c, &m);
13      void *ptr = ...;        // get mem from heap
14      bytesLeft -= size;
15      Pthread_mutex_unlock(&m);
16      return ptr;
17  }
18
19  void free(void *ptr, int size) {
20      Pthread_mutex_lock(&m);
21      bytesLeft += size;
22      Pthread_cond_signal(&c);    // whom to signal??
23      Pthread_mutex_unlock(&m);
24  }
```

> **p.51** Solution (Suggested by Lampson and Redell)
>
> Replace pthread\_cond\_signal() with pthread\_cond\_broadcast()
>
> pthread\_cond\_broadcast()
>
> Wake up all waiting threads.
>
> Cost: too many threads might be woken.
>
> Threads that shouldn’t be awake will simply wake up, re-check the condition, and then go back to sleep.

原题：空闲0 B，Ta要100 B、Tb要10 B，两者都睡；Tc释放50 B。若signal只唤醒Ta，它重查50<100再睡，而能继续的Tb仍睡。broadcast让所有等待者争锁重查：Ta仍等，Tb可扣10，剩40 B。

广播不把50 B同时承诺给所有线程，因为每个分配仍在锁内检查并扣减。代价是无资格者也被唤醒，产生额外调度。

**补充：让有限生产者结束后，消费者也能退出。** 原无限循环示例强调等待条件。若生产者终将停止，消费者除了“有数据”还需知道“以后不会再有数据”。可增加受同一mutex保护的关闭状态：缓冲为空且仍可能有生产者时等待；有数据时继续消费；缓冲为空且已关闭时结束。最后一个生产者更新关闭事实后通知可能仍在等的消费者。

不能仅由主线程destroy条件变量来“把大家叫醒”，销毁不是通知；也不能只signal一个消费者就假设所有等待者都会退出。如果多个消费者都等在空缓冲上，完成关闭时应让它们都有机会重查退出条件。此处给出生命周期推理，不把它冒充原课件已经提供的完整停机代码。

:::hint 自测：broadcast之后是否可能两个消费者同时拿走最后一件物品？

在正确协议中不可能。它们分别竞争同一mutex，第一个取得后消费并更新count；第二个重新拿到锁时用while检查，会看到count已变。若仍错误使用if跳过检查，广播只会更容易暴露错误，不能替代谓词循环。

:::endhint

### p.52：把三件事各归其位

mutex保护共享状态的原子更新；谓词记录“现在能否继续”；CV提供睡眠与通知。做题先写谓词与不变量，再安排while、wait和通知对象，不从机械背诵signal位置开始。
