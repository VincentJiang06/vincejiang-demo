## 逐页伴读

### p.1–3：环境一致性是可复现的一部分

p.1介绍本次Lab，p.2分为环境、GCC和练习，列出9月18日截止；这是所读版本中的日期。p.3明确Linux20.04、64位、GCC9.4.0。代码在宿主macOS编译成功不代表在课程Linux上成功，系统接口、库和工具链都可能不同。

仓库[开发约定](../环境/Docker-开发约定.md)登记已有工作根 `课程工作目录/CSCI3150-Lab1`，容器路径 `/work`，Lab01在exercise。登记的ARM64、GCC9.4.0、Make4.2.1来自9月17日既有验证，本次重写没有重新运行容器。64位也不自动等于x86-64，涉及汇编或二进制时还需核对架构。

### p.4–6：虚拟机与容器分别封装什么

原VirtualBox方案为XUbuntu20.04、4CPU、4GB内存、100GB虚拟磁盘与GCC9.4.0。Docker方案先装Docker Desktop，再装VS Code Dev Containers扩展。图p.6标出扩展市场中的Dev Containers，不是随意名称相近的插件。

容器共享其Linux宿主内核环境中的机制，VM提供整套虚拟硬件上的系统；macOS上的Docker还有Linux虚拟化层。课程目的是得到匹配的执行环境，而不是比较哪一个工具名字更新。

### p.7–9：打开工作目录，不是打开配置子目录

原目录树把`.devcontainer/devcontainer.json`放在源码工作根下面，macOS点开头目录默认隐藏，可用Command+Shift+.显示。图p.9选择“Open Folder in Container”时应选包含`.devcontainer`的工作根；若选配置目录本身，源码挂载与相对路径都会错。

已有工作区无需再按旧课件复制一份覆盖。新增兼容单元在同一根下独立建目录，先比较OS、编译器、架构和依赖，具体遵守[规则登记](../管理/rules.json)。本伴读仅解释步骤，没有改动环境配置或作答。

### p.10–12：验证的是容器内命令

p.10是课件版本的Docker CLI可发现性排查截图；p.11终端示例显示GCC9.4.0，应在容器终端运行ASCII命令 `gcc --version`。课件正文的长横线不是可直接复制的参数。

p.12说明工作目录挂载让宿主可看到文件；容器内另装的包与挂载源码不是同一种持久性，重建容器可能需要重装包。图中约600MB与4GB是其示例体积，不是当前下载大小保证。

### p.13–14：重开既有容器与远程Linux

图p.13通过Remote Explorer的Dev Containers入口重开已有环境，避免无意新建另一个工作根。p.14给远程路径：先SSH到课程网关，再到Linux服务器；替代方案需CSE VPN。这些主机名是课件信息，本次没有联网登录验证可用性。无论本地还是远程，先确定源码在哪个文件系统、命令在哪个系统执行，再解释编译结果。
