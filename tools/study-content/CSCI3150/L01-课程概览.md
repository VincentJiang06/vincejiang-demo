>

>
> How to achieve this – Virtualization
>
> OS takes a physical resource and transforms it into a virtual form of itself.
>
> Physical resource: Processor, Memory, Disk …
>
> The virtual form is more general, powerful and easy-to-use.
>
> We can refer to the OS as a “virtual” machine.

> **p.7** OS provides services (to utilize resources) via System Call (typically a few hundred) to run process, access memory/devices, etc.

> **p.7** The Design Of The Unix Operating System (Maurice Bach, 1986)

p.5 把 OS 的职责分为两面：管理 CPU、内存、磁盘等有限资源；向进程提供启动程序、管理内存、访问设备等服务。p.6 的**虚拟化**（virtualization）就是把有限物理资源组织成程序更容易使用的视图。程序看到自己像是在连续运行、拥有自己的地址空间，并不表示机器真的为每个程序新增了一套硬件。

p.7 的**系统调用**（system call）是请求这些服务的接口。它把“我要读取文件”与“设备如何完成读取”分开。图中 user programs、libraries 位于用户侧，system call interface 以下连接 file system 与 process control subsystem，底部才是 hardware control 和 hardware。

图（p.7）：Unix 系统调用接口
元素：用户程序可经库调用进入 system call interface；文件系统连接 buffer cache、设备驱动；进程控制关联调度、进程间通信和内存管理；虚线区分用户、内核与硬件层。
看什么：库是程序可使用的一层接口，但真正管理受保护资源的请求进入内核。图不是说所有库函数都必须陷入内核。

**补充：进入内核与换一个进程不是同一动作。** 当当前程序执行一次系统调用时，CPU 可以仍在为这个进程做事，只是进入受保护的内核代码；若请求立即完成，就回到该程序继续执行。若请求必须等设备，内核才可能把它置为等待状态，选择另一个就绪进程。因而“系统调用发生了”不能直接推出“进程一定切换了”。反过来，程序没有主动调用任何阻塞接口，也可能因计时器中断而被调度器切走。

把这段过程接回 p.4 的 PC：用户代码有下一条指令位置，内核服务有自己的执行位置；恢复用户执行时必须回到正确位置，并交还规定的返回值。程序不是从 main 重新开始。这里先建立执行连续性，后面读 fork、缺页恢复与线程切换时，才能分清哪些地方继续原执行流、哪些地方开始另一条执行流。

p.15 两个 PID 打印相同的虚拟地址区间，却分别输出 1、2、3、4。这说明数值相同的地址可以属于不同进程的地址空间。PID 区分进程；`p` 是进程内部使用的地址；两者要一起看，不能跨进程只比较指针数字。

**补充：同一指针数字为什么能指向不同东西。** 可以把虚拟地址想成“房间内第 16 个抽屉”，进程身份像房间号。P1 的地址 16 与 P2 的地址 16，缺少房间号时看似相同，实际需要分别查各自映射。这个比喻只帮助理解命名，真实硬件并不在每次访存时拼接 PID 文本。映射由当前地址空间的配置决定。

把 p.15 的观察分成三步：先确认是两个 PID；再确认两个进程各自修改 `*p`；最后看其中一个递增是否改变另一个的值。相同打印地址只支持“虚拟布局可能相同”，不能单独证明隔离，也不能单独证明共享。要证明共享，必须有共同映射的依据，再观察双方对同一对象的读写。显式共享内存、同一进程的两个线程与普通 fork 后私有对象是三种不同情况。

### 私有地址空间与共享物理内存（p.16）【新】

> **p.16** Each process accesses its own private virtual address space.
>
> The OS maps address space onto the physical memory.
>
> A memory reference within one running program does not affect the address space of other processes.
>
> Physical memory is a shared resource, managed by the OS.

程序通常在自己的**虚拟地址空间**里访问内存。操作系统管理映射，把访问送到正确的物理位置，并维持进程之间的隔离。物理内存作为硬件是共享资源，而“每个进程有私有地址空间”描述的是程序看到的访问规则，两句话并不冲突。

**补充**：这页描述默认私有内存模型。显式共享内存是另外配置的映射，不能拿它反过来否定本页；具体转换机制将在 L09–L12 展开。

**考试角度**：（C 级 通识）常见考法是给两个 PID 与相同指针值，判断是否足以证明它们操作同一物理对象；仅凭指针值不足以证明。

### 两个线程怎样运行同一个 worker（p.17–19）【新】

> **p.17** The OS is juggling many things at once, first running one process, then another, and so forth.

> **p.19** The main program creates two threads.
>
> Thread: a function running within the same memory space. Each thread starts running in a routine called worker().
>
> worker(): increments a counter

**课件程序与接口（p.19，原页片段）**

```text
16  int
17  main(int argc, char *argv[])
18  {
19      if (argc != 2) {
20          fprintf(stderr, "usage: threads <value>\n");
21          exit(1);
22      }
23      loops = atoi(argv[1]);
24      pthread_t p1, p2;
25      printf("Initial value : %d\n", counter);
26

28      pthread_create(&p2, NULL, worker, NULL);

30      pthread_join(p2, NULL);
31      printf("Final value : %d\n", counter);
32      return 0;
```

p.17 把问题从多个进程推进到同一个程序中的多个线程。p.18 的共享变量 `counter` 初值为 0；每个 `worker` 做 loops 次 `counter++`。p.19 的主线程创建 p1 与 p2，再分别 `pthread_join`，最后打印 counter。

这里要分清两种约束：join 让主线程等 worker 结束，因此最后打印发生在两个 worker 结束以后；它没有限制两个 worker 在循环内部怎样交错。**补充**：`volatile` 也不把读、加、写合成不可分割的操作。语言层面的数据竞争还涉及 C 的内存模型，本讲先用三条机器指令的教学模型展示丢失更新。

### 初值 50 为什么只变成 51（p.22）

**题面**（L01-课程概览-2026T1.pdf · 两线程自增示例 · p.22）

> **p.22** Example with two threads

> **p.22** counter = counter + 1 (initial value: 50)

> **p.22** We expect the result is 52. However,

表（p.22）：讲义所示交错，PC 与 eax 为当前运行线程的状态

| 动作 | PC | eax | counter |
|---|---:|---:|---:|
| T1 初始 | 100 | 0 | 50 |
| T1 读内存 | 105 | 50 | 50 |
| T1 加一 | 108 | 51 | 50 |
| 保存 T1、恢复 T2 | 100 | 0 | 50 |
| T2 读内存 | 105 | 50 | 50 |
| T2 加一 | 108 | 51 | 50 |
| T2 写回 | 113 | 51 | 51 |
| 保存 T2、恢复 T1 | 108 | 51 | 51 |
| T1 写回 | 113 | 51 | 51 |

**算一遍**：T1 把 50 读入自己的寄存器，算出 51，还没写内存就切换；T2 仍从内存读出 50，也算出 51 并写回；恢复 T1 时恢复的是它保存的寄存器 51，所以它再次写 51。两次加法都执行了，但两次都基于旧值 50，第二次存储覆盖的是相同结果，最终只净增 1。下列各页逐步拆开表中的取指与执行阶段。

**补充：先认清这三条汇编指令的读法。** 本例采用源操作数在左、目的操作数在右的写法。`%eax` 是寄存器名；`$0x1` 中的 `$` 表示立即数，`0x1` 就是十进制 1；没有 `$` 的 `0x8049a1c` 在这里表示要访问的内存位置。因此三行应读成：

| 原指令 | 读哪里 | 写哪里 | 此步是否修改共享 counter |
|---|---|---|---|
| `mov 0x8049a1c, %eax` | counter 所在的内存 | 当前线程的 eax | 否，只取得旧值 |
| `add $0x1, %eax` | eax 和常数 1 | 当前线程的 eax | 否，只计算中间值 |
| `mov %eax, 0x8049a1c` | 当前线程的 eax | counter 所在的内存 | 是，覆盖原内存值 |

`mov` 是复制，不是把源位置清空。图里还有两类“内存格”：一类存共享 counter，另一类存暂停线程的 PC、eax 现场。它们即使都画在 Memory 框内，也不是同一个变量。切换时复制保存格只负责记住线程做到哪里，不会顺带把 eax 中算出的 51 提交给 counter。带着这个区分逐页读 p.23–45，就能判断每个箭头究竟是取指、读数据、保存现场还是写共享变量。

**课件程序与接口（p.47，原页片段）**

```text
1   #include <stdio.h>
2   #include <unistd.h>
3   #include <assert.h>
4   #include <fcntl.h>

15      return 0;
16  }
```

> **p.47** open(), write(), and close() system calls are routed to the part of OS called the file system, which handles the requests

> **p.48** What OS does in order to write data to the disk?
>
> Store file meta data in the disk (file name, creation time, etc.)
>
> Figure out where on the disk this new data will reside
>
> Issue I/O requests to the underlying storage device
>
> File system handles system crashes during write.
>
> Journaling or copy-on-write
>
> Carefully order writes to disk

p.46 说明 DRAM 中的数据不能作为断电后仍保存的承诺。持久化需要硬盘、SSD 等设备，也需要文件系统组织文件、目录与设备相关对象。硬件回答“在哪里存”，软件回答“哪个文件的哪些字节放在哪里”。

p.47 的程序先 `open` 获取文件描述符 fd，以写入、创建和截断标志打开 `myfile`；再 `write`；最后 `close`。描述符是操作系统提供的引用编号，不是磁盘块地址。**算一遍**：本页字符串 `hello world\n` 含 5+1+5+1=12 个可见字符及换行字节，末尾还有一个 C 字符串终止字节，因此代码的写入长度 13 会把该终止字节也写进文件。若只要求通常的文本行，长度应是 12；这是对页上代码行为的逐字节解释，不把 13 默改成 12。

p.48 把写文件拆为保存元数据、定位存储位置、发出 I/O 请求。发生崩溃时，数据和元数据可能只完成一部分，文件系统因而还要安排写入顺序，或采用日志、写时复制来维持可恢复状态。**补充**：一次 write 返回成功与设备已经抗断电持久化不是同一个条件，本页未展开同步持久化接口。

### 从丢失更新反推正确保护范围（补充，教材通识）

p.22 的错误并不是 CPU 算错了 50+1，而是两个执行流都把同一个旧值当作起点。修复时需要保护整个“读旧值→计算新值→写回”事务。若只给最后一条 store 上锁，T1、T2 仍可能先各自在寄存器里算出 51；它们轮流存储 51 依旧只增加一次。若锁只存在于 T1 的代码而 T2 完全不遵守，同样无法形成互斥。

画时序时每行只改变被执行操作会影响的状态：load 改寄存器，不改 counter；算术改寄存器，不改另一线程的寄存器；store 才改共享内存。上下文切换保存/恢复的是各线程的 PC 和寄存器，不能把 T2 的临时计算结果自动送给 T1。这个规则也解释为什么 join 只能保证最后观察发生在工作结束以后，不能修复工作期间已经覆盖掉的数据。

:::hint 自测：若每次运行都得到正确总数，是否证明没有数据竞争？

先区分观测与保证。一次正确输出只记录这次调度的一个结果；可能恰好没有发生会暴露丢失更新的交错。

进一步说，真实 C 程序对普通共享对象发生未同步数据竞争还涉及未定义行为，三指令模型只用于解释一种失败方式，并不是枚举其所有合法输出的语言保证。证明应指出所有共享访问使用的同步关系，而不是增加循环次数后“暂时没有复现”。

:::endhint
