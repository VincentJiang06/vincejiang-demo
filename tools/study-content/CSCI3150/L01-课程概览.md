## 从机器到操作系统

### 本讲的位置与程序的装入（p.2–3）【新】

图（p.2）：自底向上的课程组织
元素：底层 Course Overview 被红框选中，其上依次为 System Calls、Persistence、Virtualization、Concurrency。
看什么：本讲先建立后续各章共同使用的机器与执行模型。

图（p.3）：磁盘上的程序变为内存中的进程
元素：Disk 内含 code 与 static data，红色虚线指向 Memory 中的进程地址空间；地址空间包含 code、static data、heap、stack；CPU 经总线访问内存。
看什么：程序是存放的代码与数据；执行它时，系统建立运行时状态，CPU 才能从内存取指。

p.2 把文件系统放在持久化部分，把 CPU 与内存管理放在虚拟化部分，把线程与锁放在并发部分。p.3 则提供共同起点：磁盘不会自己执行程序。装入使指令和初始数据进入进程可访问的地址空间，随后程序才可能申请堆对象、形成函数调用栈。**补充**：堆通常存放动态分配对象，栈保存调用过程中的局部状态；这不是说整个虚拟空间必须一次性装满物理内存。

### CPU 的取指、译码、执行（p.4）【新】

> **p.4** Fetch an instruction from memory.

图（p.4）：简化 CPU 与内存
元素：控制单元含 PC、IR、PSR；通用寄存器中有 eax；ALU 接收操作数并给出结果；总线连接 CPU 与内存。
看什么：PC 给出要取哪条指令，IR 暂存取到的指令，ALU 执行算术逻辑，寄存器保存执行状态。

PC 是程序计数器，值是一个指令地址，不是已经执行的指令数。IR 是指令寄存器，装的是指令本身；PSR 保存处理器状态。取指读“怎么做”，数据访存读“对什么做”，两者都访问内存但含义不同。课件把运行写成循环：取指→译码→执行→再取指。

**算一遍**：本讲 p.22 的指令地址依次是 100、105、108，执行完后一条后 PC 为 113。它们相差 5、3、5，说明该例指令长度不同；不能机械地把 PC 每次加 1。PC=105 时取到加法指令，执行结果写寄存器，之后才指向 108 的存储指令。

### 操作系统管理什么，怎样提供服务（p.5–7）【新】

> **p.6** OS takes a physical resource and transforms it into a virtual form of itself.

p.5 把 OS 的职责分为两面：管理 CPU、内存、磁盘等有限资源；向进程提供启动程序、管理内存、访问设备等服务。p.6 的**虚拟化**（virtualization）就是把有限物理资源组织成程序更容易使用的视图。程序看到自己像是在连续运行、拥有自己的地址空间，并不表示机器真的为每个程序新增了一套硬件。

p.7 的**系统调用**（system call）是请求这些服务的接口。它把“我要读取文件”与“设备如何完成读取”分开。图中 user programs、libraries 位于用户侧，system call interface 以下连接 file system 与 process control subsystem，底部才是 hardware control 和 hardware。

图（p.7）：Unix 系统调用接口
元素：用户程序可经库调用进入 system call interface；文件系统连接 buffer cache、设备驱动；进程控制关联调度、进程间通信和内存管理；虚线区分用户、内核与硬件层。
看什么：库是程序可使用的一层接口，但真正管理受保护资源的请求进入内核。图不是说所有库函数都必须陷入内核。

## 虚拟化的两个可见效果

### 一个 CPU 上的四个程序（p.8–10）【新】

> **p.8** Allow many processes to seemingly run at the same time

p.8 的“seemingly”是关键：多个程序在一段时间内都取得进展，并不等于单个 CPU 同一瞬间执行四条指令。p.9 的 `cpu.c` 接受一个字符串参数，令 `i=0`，每轮先 `sleep(1)`、再递增 `i`、再打印字符串；`i<100` 时继续。p.10 先编译成 `cpu`，再执行 `./cpu A`，终端看见多行 A；Ctrl-C 可以提前打断。

**算一遍**：沿 p.9 代码，第一次检查 0<100 成立，休眠后 i=1，打印第 1 次；第 100 轮后 i=100，再检查失败。因此正常结束打印 100 次。课件写的是每轮请求休眠一秒，不能由此推出整个程序严格只耗时 100 秒；打印与调度也需要时间（补充）。

### 后台运行与地址是什么（p.11–12）

> **p.11** Even though we have only one CPU, the four processes seem to be running at the same time!

p.11 在四条命令后使用 `&`，终端因而不用等前一条结束再启动下一条。输出出现 A、B、D、C 等交错，表明四个执行流都在取得进展；输出的某一次顺序不能当成每次都成立的调度规则。**补充**：这段程序大量休眠，一个进程等待期间 CPU 可以服务另一个，因此它也不是证明“四倍 CPU 算力”的基准测试。

p.12 把物理内存看成按字节编号的数组。load 根据地址取内容，store 同时需要地址与要写的值。地址回答“哪个位置”，值回答“那里是什么”；把两者混为一谈，后面看到相同指针数值就会误以为一定在共享数据。

### 动态内存与两份互不干扰的计数（p.13–15）

> **p.15** Each running program has allocated memory at its own address space.

p.13 的 `malloc(MAX*sizeof(int))` 申请 MAX 个整数的空间，成功后 `p` 是首元素指针；`p+MAX-1` 指向最后一个整数的起始位置。代码只修改 `*p`，并没有遍历整个数组。p.14 的一个进程从 0 开始，每轮加一，依次打印 1 到 10。

**算一遍**：MAX=100000000。若按课件地址差所对应的 4 字节整数计算，空间为 100000000×4=400000000 字节；最后元素起点与首地址相差 99999999×4=399999996 字节。最后一个元素还占 4 字节，所以不能用“两地址之差”代替整个分配长度。

p.15 两个 PID 打印相同的虚拟地址区间，却分别输出 1、2、3、4。这说明数值相同的地址可以属于不同进程的地址空间。PID 区分进程；`p` 是进程内部使用的地址；两者要一起看，不能跨进程只比较指针数字。

### 私有地址空间与共享物理内存（p.16）【新】

> **p.16** The OS maps address space onto the physical memory.

程序通常在自己的**虚拟地址空间**里访问内存。操作系统管理映射，把访问送到正确的物理位置，并维持进程之间的隔离。物理内存作为硬件是共享资源，而“每个进程有私有地址空间”描述的是程序看到的访问规则，两句话并不冲突。

**补充**：这页描述默认私有内存模型。显式共享内存是另外配置的映射，不能拿它反过来否定本页；具体转换机制将在 L09–L12 展开。

**考试角度**：（C 级 通识）常见考法是给两个 PID 与相同指针值，判断是否足以证明它们操作同一物理对象；仅凭指针值不足以证明。

## 并发为什么会丢失更新

### 两个线程怎样运行同一个 worker（p.17–19）【新】

> **p.19** The main program creates two threads.

p.17 把问题从多个进程推进到同一个程序中的多个线程。p.18 的共享变量 `counter` 初值为 0；每个 `worker` 做 loops 次 `counter++`。p.19 的主线程创建 p1 与 p2，再分别 `pthread_join`，最后打印 counter。

这里要分清两种约束：join 让主线程等 worker 结束，因此最后打印发生在两个 worker 结束以后；它没有限制两个 worker 在循环内部怎样交错。**补充**：`volatile` 也不把读、加、写合成不可分割的操作。语言层面的数据竞争还涉及 C 的内存模型，本讲先用三条机器指令的教学模型展示丢失更新。

### 从正确的期望值到错误的实测值（p.20–21）

> **p.21** These three instructions do not execute atomically.

p.20 在 loops=1000 时给出 2000，但在 loops=1000000000 时给出 1997974414 与 1997940107。前一次“恰好正确”没有证明程序安全，只说明那次运行没有显露出错误结果。p.21 将自增拆为 load、increment、store；原子性要求其他执行流看不到把整体拆开的中间状态，这三条指令却可以被切换打断。

**算一遍**：大循环的理想值为 2×1000000000=2000000000。第一份输出少了 2000000000−1997974414=2025586；第二份少了 2059893。差额展示丢失的净更新量，不能据此恢复唯一的线程切换时序。

### 初值 50 为什么只变成 51（p.22）

**题面**（L01-课程概览-2026T1.pdf · 两线程自增示例 · p.22）

> **p.22** Example with two threads

> **p.22** counter = counter + 1 (initial value: 50)

> **p.22** We expect the result is 52. However,

表（p.22）：讲义所示交错，PC 与 eax 为当前运行线程的状态

| 动作 | PC | eax | counter |
|---|---:|---:|---:|
| T1 初始 | 100 | 0 | 50 |
| T1 读内存 | 105 | 50 | 50 |
| T1 加一 | 108 | 51 | 50 |
| 保存 T1、恢复 T2 | 100 | 0 | 50 |
| T2 读内存 | 105 | 50 | 50 |
| T2 加一 | 108 | 51 | 50 |
| T2 写回 | 113 | 51 | 51 |
| 保存 T2、恢复 T1 | 108 | 51 | 51 |
| T1 写回 | 113 | 51 | 51 |

**算一遍**：T1 把 50 读入自己的寄存器，算出 51，还没写内存就切换；T2 仍从内存读出 50，也算出 51 并写回；恢复 T1 时恢复的是它保存的寄存器 51，所以它再次写 51。两次加法都执行了，但两次都基于旧值 50，第二次存储覆盖的是相同结果，最终只净增 1。下列各页逐步拆开表中的取指与执行阶段。

### T1 前进到加法（p.26）

### T1 覆盖为同一个 51（p.44）

图（p.44）：CPU、共享 counter 与线程保存区
元素：PC、IR、eax、三条指令地址 100/105/108、counter 地址 0x8049a1c，以及 T1/T2 的 PC 与 eax 保存格；红色数值及箭头标记本步变化。
看什么：把 eax=51 写入已为 51 的 counter，内存值不变。这就是丢失更新：没有丢掉线程，也没有跳过加法，丢的是两个逻辑加一应当累积的效果。

### 最终 PC 与最终值（p.45）

图（p.45）：CPU、共享 counter 与线程保存区

## 数据为什么能够跨越一次运行

### 持久化与文件接口（p.46–48）【新】

> **p.46** Devices such as DRAM store values in a volatile manner.

p.46 说明 DRAM 中的数据不能作为断电后仍保存的承诺。持久化需要硬盘、SSD 等设备，也需要文件系统组织文件、目录与设备相关对象。硬件回答“在哪里存”，软件回答“哪个文件的哪些字节放在哪里”。

p.47 的程序先 `open` 获取文件描述符 fd，以写入、创建和截断标志打开 `myfile`；再 `write`；最后 `close`。描述符是操作系统提供的引用编号，不是磁盘块地址。**算一遍**：本页字符串 `hello world\n` 含 5+1+5+1=12 个可见字符及换行字节，末尾还有一个 C 字符串终止字节，因此代码的写入长度 13 会把该终止字节也写进文件。若只要求通常的文本行，长度应是 12；这是对页上代码行为的逐字节解释，不把 13 默改成 12。

p.48 把写文件拆为保存元数据、定位存储位置、发出 I/O 请求。发生崩溃时，数据和元数据可能只完成一部分，文件系统因而还要安排写入顺序，或采用日志、写时复制来维持可恢复状态。**补充**：一次 write 返回成功与设备已经抗断电持久化不是同一个条件，本页未展开同步持久化接口。

### 目标之间的关系与本讲收束（p.49–50）

> **p.49** Isolation: Bad behavior of one does not harm others and the OS itself.

p.49 列出抽象、性能、保护、可靠性以及能耗、安全、移动性。抽象让程序少处理硬件细节；性能要求抽象的成本可控；保护防止程序破坏其他进程与 OS；可靠性要求系统持续正确运行。它们是设计评价维度，某个接口方便并不自动说明它开销小或隔离强。

p.50 把硬件、虚拟化和系统调用重新连起来：硬件执行指令，OS 管理资源，程序通过接口使用服务。下一讲不从调度算法开始，而是先学习用户程序怎样创建与控制进程，这与 p.2 的自底向上路线一致。

## 本讲核心考点

- 程序与进程、PC与IR的区别（p.3–4，C 级通识考法）。
