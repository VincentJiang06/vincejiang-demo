## 在四个应用的样本里数故障（p.31–33）

> **p.32** Bugs In Modern Applications

p.31 是 Part II 分节页，标题中的 Currency 按整讲标题及后文读作 Concurrency。p.32 表按应用列出非死锁、死锁两列。MySQL 为 14 和 9，Apache 为 13 和 4，Mozilla 为 41 和 16，OpenOffice 为 6 和 2。逐列相加得到 74 和 31，共 105 例，非死锁约占 70.5%。分母是课件这批样本，不能把比例外推到任意程序。

p.33 将非死锁问题进一步分为**原子性违反**与**顺序违反**。分析前先写下程序原本需要的保证：一组动作应当整体执行，还是某个事件必须在另一个之前发生？两个线程都能结束，也可能已经产生了错误结果。

## 检查和使用之间的原子性（p.34–35）【新】

> **p.34** The desired serializability among multiple memory accesses is violated.

p.34 的共享字段 `proc_info` 在条件判断和后面的输出调用中各读一次。进入 if 只能证明第一次读时字段非空，无法让第二次读取沿用那一刻的状态。把「检查到可用 → 使用」看成一次操作，就能找出它依赖的连续区间。

p.35 用同一把锁把检查及整个使用过程包住，另一方更新字段也先取得这把锁。现在有两种串行结果：先清空，读者在检查处跳过；先使用，更新者等到读者释放后才能清空。若只给两次读分别加锁，读者第一次释放同一把锁到再次取得它之间，字段仍可能改变。

## 当真正缺的是先后顺序（p.36–38）【新】

> **p.36** The desired order between two memory accesses is flipped.

p.36 创建方把创建结果存入 `mThread`，工作线程要从它读取 State。运行新线程与创建方完成赋值之间缺少程序保证。即使两段代码从不同时执行，先执行读取、后执行初始化，顺序也错。因此仅加一把允许任意一方先进入的锁仍不够。

p.37 创建方在完成赋值后，取得 mtLock，把 `mtInit` 从 0 改成 1，再 signal 并解锁。标志记录初始化已完成，先完成时这一事实也能留给以后才开始运行的读者。

p.38 工作线程在同一把锁内检查 mtInit。看到 0 就 wait，释放锁让创建方完成；再次握有锁且看到 1 才继续读取 State。本例假定初始化成功且对象此后仍有效。顺序链可以写成「写入引用 → 发布完成标志 → 观察完成标志 → 读取对象」。这里的条件不能简化成「我收到过一次信号」。

## 从两把锁画出等待环（p.39–41）【新】

> **p.39** The presence of a cycle

p.39 从上往下跟两列代码。T1 先持 L1，T2 先持 L2；T1 想要 L2，T2 想要 L1。图里有两种关系：谁持有某锁，以及谁还需要某锁。把它们连起来，T1 等 T2 放 L2，T2 又等 T1 放 L1，两人都到不了 unlock。画环必须写出当前持有关系，仅仅看到代码中出现两把锁还不能断言这次执行已经死锁。

p.40 大型程序的锁依赖会跨组件。调用者可能在持锁状态进入另一个模块，那个模块又在内部获取一把锁。封装隐藏了细节，也可能让局部看似合理的顺序在全局拼出环。

p.41 讲义用 Vector 的 AddAll 演示：一次调用要同时访问目的向量和源向量。若依据「先目的、后源」加锁，`v1.AddAll(v2)` 产生 v1→v2，而反向调用产生 v2→v1。方法内部每次都遵循同一句规则，两个对象互换角色后却形成相反的资源顺序。

## 四个必要条件与两种预防法（p.42–44）

> **p.42** Four conditions need to hold for a deadlock to occur.

p.42 把 p.39 的例子逐项对上：每把锁一次归一人是**互斥**；手里留着第一把再等第二把是**占有并等待**；别人不能强行取走已持锁是**不可抢占**；等待链闭合是**循环等待**。四项是发生此类资源死锁的必要条件。预防策略只要保证其中一项无法成立即可。

p.43 破坏循环等待：全程序约定先 L1 后 L2。若 T1 已拿 L1，T2 要先停在 L1，无法先占 L2 来阻挡 T1。推广到多把锁时，按统一顺序递增加锁，等待链就不能回到起点。这要求嵌套调用同样遵守顺序。

p.44 破坏占有并等待的一种做法，是在申请整组锁前先过总入口 prevention。所有申请者都遵守该协议时，另一组抢锁动作不会插进这一组获取操作之间；释放已持有资源的路径必须仍能前进。讲义把这称作原子获取，相对于其他申请者看才是整体，操作系统仍可切换线程。代价是事先要知道所需锁，而且不相关的申请也可能排队。

## trylock、活锁与 CAS 的返回值（p.45–47）

> **p.46** Progress is not being made.

p.45 先拿 L1，对 L2 使用 trylock。若成功，两把齐全；若失败，立刻释放 L1，从头再尝试。这里是持有者主动退让，使对方能取得资源。课件用 −1 代表失败，按实际库调用时应遵循该接口的返回约定。

p.46 两方若同时抢第一把、同时发现第二把不可用、同时退让，就可能不断重试却没人完成。这叫**活锁**（livelock）。死锁时相关线程都在等待；活锁时线程仍执行，完成的工作却没有增加。重试前随机延迟有助于错开步调。

p.47 **比较并交换**（compare-and-swap，CAS）是原子操作。它比较当前值和 expected，仅在相同的时候写入 new。按本页约定，成功返回 1，失败返回 0。判断 p.48 的加法和 p.50 的链表插入是否应重试，都要依据这条约定。**补充**：讲义用了 wait-free 一词；严格意义的 wait-free 要求每个操作都能在有界的自身步骤内结束，使用 CAS 和重试本身不提供这项保证。

## 原子加法与链表头插的重试方向（p.48–50）

> **p.48** Repeatedly tries to update the value to the new amount and uses the compare-and-swap to do so.

p.48 每轮先读 old，再尝试把仍为 old 的值换成 old 加 amount。**算一遍**（数字为自取）：初值 5，两人都想加 2。A 先把 5 换成 7；B 用 expected=5 失败，重新读到 7，再换成 9。B 若仍用旧的 5，便不会完成。示意代码把 old 声明在 do 块内又在块外条件中使用，按 C 改写需让它在循环条件处仍可见。

p.49 头插先造私有结点 n，填好 value，再令 n.next 指向旧 head，最后发布新 head。假设初始头为 H，A 和 B 各把自己的 next 都指向 H，再先后写 head，链上只会留下最后发布的结点和 H。分配的是两个不同结点，发生竞争的是共享的头以及「以哪个旧头为前驱状态」这一假设。

p.50 上半段把读旧头、接 next、改 head 放进同一临界区。下半段想用 CAS：每轮先保存当前头到 n.next，再尝试「若头仍等于 n.next，就换成 n」。**讲义校勘**：本页循环写作 `while (CompareAndSwap(&head, n->next, n));`。按 p.47 的成功 1、失败 0，应在**返回 0 时重试**。原写法会在失败时退出、成功后反而再试；若成功后无人改头，下一轮甚至可能把 n.next 指回 n 自己。按正确方向，先成功的 A 连着 H；B 的旧头比较失败，再把 next 更新为 A，最后形成 B→A→H。这里讨论的是只有插入的课堂模型。<a name="r-a1"></a>[见附录 A1](#a1)。

## 调度器怎样提前避开交错（p.51–53）

> **p.52** We have two processors and four threads.

p.51 **避免死锁**可以在调度前利用额外信息：预先知道每个线程可能要哪些锁，限制某些线程的执行区间不重叠。这样做需要知道全局的需求；只看局部请求很难安排。被分开的线程要先释放相关锁再运行下一组，仅在两个核之间换个位置并不能消除等待环。

p.52 的矩阵中，T1、T2 都要 L1 和 L2；T3 只要 L2；T4 两把都不用。T3 即使暂时占了 L2，也不会再等 L1 而闭环。图上 CPU 2 先跑完 T1 再跑 T2，CPU 1 依次运行 T3、T4。这样有并行机会，又避免 T1 与 T2 分持不同锁再互等。T3 与 T1 仍可能短暂争 L2，允许短暂等待与避免死锁可以同时做到。

p.53 的变化只有一个：T3 也需要 L1 和 L2。前页对它的判断随即失效。图上 CPU 2 串行运行 T1、T2、T3，CPU 1 运行 T4 后空闲。这项保守安排换来保证，却让总完成时间变长。读图只需判断哪些矩形重叠，课件没有给每个矩形可换算的时间单位。

## 允许发生，检测后恢复（p.54–55）

> **p.54** A deadlock detector runs periodically.

p.54 若预防的成本太高，另一种选择是允许死锁偶尔发生，再定期建资源图寻找等待环。在讲义的单实例锁模型中，环可以说明互等。系统冻结后重启是较粗的恢复方式。**补充**：数据库也可回滚被选中的事务，释放它持有的锁，使其余事务继续；这让检测与恢复不必总以整机为单位。

p.55 把两部分串回同一道审题步骤。看到信号量先问许可代表什么，再问哪项进展依赖谁；看到共享变量先判断是否缺少原子性或先后顺序；看到两个阻塞点再把持有与请求的资源连成图。各自需要检查的状态不同。

## 本讲核心考点

- 对给定共享访问，区分检查后状态被改与初始化顺序缺失，并说明同步应覆盖哪段（p.34–38，C 级）。
- 用两线程两把锁标出死锁四条件，说明统一顺序和退让重试怎样改变等待关系（p.39–46，C 级）。
- 从 CAS 的返回约定检查循环方向，跟踪两次头插能否都保留（p.47–50，C 级）。
- 对照两张需求矩阵说明 T3 为何在第二张需要串行，以及代价是什么（p.51–54，C 级）。
