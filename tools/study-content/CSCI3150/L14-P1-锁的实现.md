### p.4–6：锁状态与临界区

> **p.4** Ensure that any critical section executes as if it were a single atomic instruction.
>
> An example: the canonical update of a shared variable
>
> Add some code around the critical section

**课件程序与接口（p.4，原页片段）**

```text
balance = balance + 1;
```

**思路分析（逐步读）**

1. 先读 balance 的旧值，再在 CPU 中算旧值加 1。
2. 把计算结果写回 balance，才完成这一条 C 语句的效果。
3. 若另一个线程在读和写之间也更新 balance，就会竞争；一行源码不等于一个原子操作。

**课件程序与接口（p.4，原页片段）**

```text
1    lock_t mutex; // some globally-allocated lock ‘mutex’
2    …
3    lock(&mutex);
4    balance = balance + 1;
5    unlock(&mutex);
```

> **p.5** Lock variable holds the state of the lock.
>
> available (or unlocked or free)
>
> No thread holds the lock.
>
> acquired (or locked or held)
>
> Exactly one thread holds the lock and presumably is in a critical section.

> **p.6** lock()
>
> Try to acquire the lock.
>
> If no other thread holds the lock, the thread will acquire the lock.
>
> Enter the critical section.
>
> This thread is said to be the owner of the lock.
>
> Other threads are prevented from entering the critical section while the first thread that holds the lock is in there.

**思路分析（逐步读）**

1. mutex 代表保护 balance 的同一把锁，省略处应包括正确初始化。
2. 进入前 lock，再在独占期间完成 balance 的读改写。
3. 完成后 unlock，所有访问者必须遵守这套协议，否则未加锁的访问仍能造成竞争。

原例用lock和unlock包住 `balance=balance+1`。锁有free与held两种逻辑状态；一个线程成功取得后成为owner，其余遵守相同锁协议的线程不能同时进入。锁的意义是把一串访问作为整体保护，不是让这串机器指令物理上融合成一条。

### p.7–9：三个评价标准分别回答三个问题

> **p.7** The name that the POSIX library uses for a lock.
>
> Used to provide mutual exclusion between threads.
>
> We may be using different locks to protect different variables  Increase concurrency (a more fine-grained approach).

**课件程序与接口（p.7，原页片段）**

```text
1   pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
2
3   Pthread_mutex_lock(&lock); // wrapper for pthread_mutex_lock()
4   balance = balance + 1;
5   Pthread_mutex_unlock(&lock);
```

> **p.8** Efficient locks provided mutual exclusion at low cost.
>
> Building a lock need some help from the hardware and the OS.

> **p.9** Mutual exclusion
>
> Does the lock work, preventing multiple threads from entering a critical section?
>
> Fairness
>
> Does each thread contending for the lock get a fair shot at acquiring it once it is free? (Starvation)
>
> Performance
>
> The time overheads added by using the lock

**思路分析（逐步读）**

1. 先静态初始化 pthread 互斥量 lock。
2. 调用包装函数取得锁，再修改 balance；大写 Pthread 通常表示带错误检查的教学包装。
3. 最后释放同一把锁，包装函数需另行定义，不能当系统自带接口直接使用。

pthread mutex提供互斥；不同互不相关的数据用不同锁可增加并发，但关联的不变量不能随意拆开保护。构造锁要问：是否确实只有一个线程进入（正确性），等待者是否可能饿死（公平性），获取、竞争与释放代价多大（性能）。正确不自动推出公平或快。

### p.10–12：关中断和普通flag各在哪里失败

> **p.10** Disable Interrupts for critical sections
>
> One of the earliest solutions used to provide mutual exclusion
>
> Invented for single-processor systems.
>
> Problem:
>
> Require too much trust in applications
>
> Greedy (or malicious) program could monopolize the processor.
>
> Do not work on multiprocessors
>
> Code that masks or unmasks interrupts be executed slowly by modern CPUs

**课件程序与接口（p.10，原页片段）**

```text
void lock() {
     DisableInterrupts();
 }
 void unlock() {
     EnableInterrupts();
 }
```

> **p.11** First attempt: Using a flag denoting whether the lock is held or not.
>
> The code below has problems.

**思路分析（逐步读）**

1. lock 通过关闭本 CPU 的中断，试图阻止中断引发的调度切换。
2. 临界区结束后 unlock 重新打开中断。
3. 这种方法依赖内核权限和单 CPU 假设，不能阻止其他 CPU 同时访问；真实内核还需保存并恢复原中断状态。

**课件程序与接口（p.11，原页片段）**

```text
typedef struct __lock_t { int flag; } lock_t;

 void init(lock_t *mutex) {
    // 0  lock is available, 1  held
    mutex->flag = 0;
 }

 void lock(lock_t *mutex) {
    while (mutex->flag == 1)  // TEST the flag
        ;  // spin-wait (do nothing)
    mutex->flag = 1;  // now SET it !
 }

 void unlock(lock_t *mutex) {
    mutex->flag = 0;
 }
```

> **p.12** Problem 1: No Mutual Exclusion (assume flag=0 to begin)
>
> Problem 2: Spin-waiting wastes time waiting for another thread
>
> So, we need an atomic instruction supported by Hardware!
>
> test-and-set instruction, also known as atomic exchange

**思路分析（逐步读）**

1. flag=0 表示空闲，lock 循环检查它是否为 1，空闲后再把它设成 1。
2. 漏洞在检查和赋值分成两步：线程 A 检查完空闲后切走，线程 B 也能通过检查。
3. 两者随后都设为 1 并进入临界区，因此它不是正确的互斥锁；普通共享 flag 还涉及 C 数据竞争。

**课件程序与接口（p.12，原页片段）**

```text
call lock()
while (flag == 1)
interrupt: switch to Thread 2
```

**思路分析（逐步读）**

1. 线程 1 调用 lock，检查 flag；此交错假设它读到 0，所以准备退出 while。
2. 此时尚未执行 `flag=1` 就被切走。
3. 线程 2 因而仍能看见 0；问题发生在检查与占有之间的空隙。

**课件程序与接口（p.12，原页片段）**

```text
call lock()
while (flag == 1)
flag = 1;
interrupt: switch to Thread 1
```

**思路分析（逐步读）**

1. 线程 2 也检查到 flag=0，退出 while。
2. 它先执行 flag=1，认为自己取得锁。
3. 切回线程 1 时，线程 1 会接着原先的位置执行，而不会自动重做已经通过的检查。

**课件程序与接口（p.12，原页片段）**

```text
flag = 1; // set flag to 1 (too!)
```

**思路分析（逐步读）**

1. 线程 1 从先前检查之后恢复，继续执行 flag=1。
2. 它没有意识到线程 2 已经占有锁，也把自己当成持有者。
3. 两个线程都能进入临界区，这一赋值展示了分离 test/set 的失败结果。

关闭本CPU中断在早期单处理器内核场景可防某些抢占，但不能停止另一CPU访问共享数据，也不能给普通应用任意长期关中断的权力。

课件错误实现是 `while(flag==1) ; flag=1;`。题设flag初值0；T1检查为0后切换，T2也检查为0，T2写1并进入，随后T1写1也进入。即使每次单独读写flag都不可分割，**检查与占有之间仍有缝隙**。这就是需要原子read-modify-write的原因。该教学交错之外，真实语言内存模型也要求使用合适原子或同步原语。

### p.13–15：TestAndSet把检查和占有合成一个动作

> **p.13** An instruction to support the creation of simple locks
>
> return(testing) old value pointed to by the ptr.
>
> Simultaneously update(setting) said value to new.
>
> This sequence of operations is performed atomically.

**课件程序与接口（p.13，原页片段）**

```text
int TestAndSet(int *ptr, int new) {
    int old = *ptr; // fetch old value at ptr
    *ptr = new; // store ‘new’ into ptr
    return old; // return the old value
 }
```

> **p.14** Note: To work correctly on a single processor, it requires a preemptive scheduler.

**思路分析（逐步读）**

1. 先用 old 保存 `*ptr` 的旧值，再把 new 写入同一位置，最后返回旧值。
2. 调用者通过旧值判断此前是否已被占有，例如旧值 0 表示本次抢到了空闲锁。
3. 这里用 C 描述原子指令的语义；把这三句普通 C 原样执行并不会自动具有原子性。

**课件程序与接口（p.14，原页片段）**

```text
typedef struct __lock_t {
    int flag;
 } lock_t;

 void init(lock_t *lock) {
    // 0 indicates that lock is available,
    // 1 that it is held
    lock->flag = 0;
 }

 void lock(lock_t *lock) {
    while (TestAndSet(&lock->flag, 1) == 1)
        ;   // spin-wait
 }

 void unlock(lock_t *lock) {
    lock->flag = 0;
 }
```

> **p.15** Correctness: yes
>
> The spin lock only allows a single thread to enter the critical section.
>
> Fairness: no
>
> Spin locks don’t provide any fairness guarantees.
>
> Indeed, a thread spinning may spin forever.
>
> Performance:
>
> In a single CPU, performance overheads can be quire painful.
>
> If the number of threads roughly equals the number of CPUs, spin locks work reasonably well.

**思路分析（逐步读）**

1. init 把 flag 设为 0，表示尚无持有者。
2. 循环执行原子的 TestAndSet：它无论如何都写 1，但只有返回旧值 0 的线程能离开循环。
3. 返回旧值 1 的线程继续自旋，unlock 写 0 后才有新的成功者；真实实现还要提供正确的原子操作和内存顺序。

课件定义TestAndSet原子地读取旧值、写入new并返回旧值。以下是原机制的精简表达，不是可用普通C赋值实现原子性的保证：

```text
lock:   while TestAndSet(flag,1) == 1: retry
unlock: flag = 0
```

**思路分析（逐步读）**

1. 这是上一实现的伪代码摘要：尝试占有锁，同时取回原状态。
2. 旧状态为 1 就重试，为 0 才进入受保护区。
3. unlock 把状态恢复为 0；必须依赖原子 TestAndSet，不能拆成普通读取和赋值。

初值0时，第一个操作返回0且写1，所以获锁；后来的操作返回1，继续等待。释放后某个竞争者再次读到旧0获锁。单CPU需允许调度到持有者，否则等待者永远自旋而持有者无法解锁。该锁无FIFO保证，一个线程可能多次被别人抢先。

**补充：为什么测试并设置必须是一个硬件动作。** 按p.13的约定，TestAndSet同时返回旧值并写1。初始flag=0时，即使T1/T2几乎同时调用，硬件也使它们具有某种先后：排第一者读旧0并写1，第二者读到的是已经变成1的值。胜者进入的理由是“我拿到旧0”，不是“现在flag为1”，因为失败者此刻看见的flag同样为1。

| 事件 | 返回给调用者的旧值 | 操作后flag | 决定 |
|---|---:|---:|---|
| T1首次尝试 | 0 | 1 | T1进入 |
| T2尝试 | 1 | 1 | T2继续等 |
| T1释放 | — | 0 | 资源可重新竞争 |
| T2下一次尝试 | 0 | 1 | T2进入 |

真实语言实现还须用满足同步要求的原子操作及获取/释放顺序，使临界区数据对后续持锁者可见。仅仅用一个名字叫TestAndSet的普通C函数包住读取和写入，不会让它获得硬件原子性。

:::hint 自测：锁每次都只允许一个线程进入，是否就证明每个等待者最终会进入？

互斥只证明安全性。若释放时总被别的线程抢先，同一个等待者仍可能长期失败；这属于饥饿。需要公平的排队/调度条件才能进一步证明等待有界，不能从“flag只有0和1”推出公平。

:::endhint

### p.16–17：yield只退到ready，不等于睡到解锁

> **p.16** Hardware-based spin locks are simple and they work.
>
> In some cases, these solutions can be quite inefficient.
>
> Any time a thread gets caught spinning, it wastes an entire time slice doing nothing but checking a value.

> **p.17** When you are going to spin, give up the CPU to another thread.
>
> OS system call moves the caller from the running state to the ready state.
>
> The cost of a context switch can be substantial and the starvation problem still exists.

**课件程序与接口（p.17，原页片段）**

```text
void init() {
     flag = 0;
 }

 void lock() {
     while (TestAndSet(&flag, 1) == 1)
         yield(); // give up the CPU
 }

 void unlock() {
     flag = 0;
 }
```

**思路分析（逐步读）**

1. 初始化 flag=0，每次用原子 TestAndSet 尝试取得锁。
2. 失败时调用 yield 主动让出 CPU，而不是一直空转。
3. 再次获调度后仍要重新竞争，yield 不保证下次成功或公平；unlock 仍负责释放状态。

自旋占用CPU重复检查。失败后yield使线程从running回到ready，调度器可能运行持有者，也可能很快又选到竞争者，因此减少某些忙等却增加上下文切换，仍不能保证公平。把yield误认成“已经排队等待特定锁释放”会误判程序行为。

### p.18–19：等待队列与两阶段锁

> **p.18** Queue to keep track of which threads are waiting to enter the lock.
>
> park()
>
> Put a calling thread to sleep
>
> unpark(threadID)
>
> Wake a particular thread as designated by threadID.

> **p.19** A two-phase lock realizes that spinning can be useful if the lock is about to be released.
>
> First phase
>
> The lock spins for a while, hoping that it can acquire the lock.
>
> If the lock is not acquired during the first spin phase, a second phase is entered,
>
> Second phase
>
> The caller is put to sleep.
>
> The caller is only woken up when the lock becomes free later.

park让当前线程睡眠，unpark唤醒指定线程；锁维护队列，释放者找到等待者。**补充实现注意**：检查锁、入队和睡眠必须协调，不能让unpark发生在尚未park的空档而丢失唤醒。

两阶段锁先短暂自旋，预计持有者很快释放时省去睡眠切换；超过阈值再睡眠。选择与临界区长度、CPU数量和调度情况有关，不是固定“自旋总快”或“睡眠总快”。

**补充：把丢失唤醒的空档画成四步。** T1 发现锁忙，决定睡眠；T2 释放锁并通知 T1；T1 此时尚未真正进入睡眠；T1 接着睡下。如果通知不被记住、又没有协调入队与睡眠，锁已经空闲，却可能再没有线程负责叫醒 T1。这是“等待条件已满足但等待者睡过去”的问题，不是互斥失败。

解决要求是协议上的：等待者准备睡眠与释放者的通知之间必须有正确的交接，或通知能以许可/令牌形式可靠保留。仅仅把“检查锁”那一行做成原子指令，不能自动使后续入队和睡眠也成为不可分割的整体。本页只列 park/unpark 的用途，没有给出一套可以直接照抄的完整实现；下一部分条件变量把释放互斥锁和进入等待作为一个协调操作，正好回应这一缺口。
