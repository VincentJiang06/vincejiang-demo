### p.34–35：检查后使用需要共同保护

> **p.34** The desired serializability among multiple memory accesses is violated.
>
> Simple Example found in MySQL:
>
> Two different threads access the field proc\_info in the struct thd.

**课件程序与接口（p.34，原页片段）**

```text
1     Thread1::
2     if(thd->proc_info){
3       …
4   fputs(thd->proc_info , …);
5   …
6     }
7
8     Thread2::
9     thd->proc_info = NULL;
```

> **p.35** Solution: Simply add locks around the shared-variable references.

**课件程序与接口（p.35，原页片段）**

```text
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

 Thread1::
 pthread_mutex_lock(&lock);
 if(thd->proc_info){
    …
    fputs(thd->proc_info , …);
    …
 }
 pthread_mutex_unlock(&lock);

 Thread2::
 pthread_mutex_lock(&lock);
 thd->proc_info = NULL;
 pthread_mutex_unlock(&lock);
```

原例T1执行 `if(thd->proc_info) ... fputs(thd->proc_info,...)`，T2可设 `thd->proc_info=NULL`。若T2插入检查与使用之间，检查通过不保证使用时仍非空。修复让T1从检查到使用全程持同一锁，T2赋值也用此锁；只给赋值或只给if上锁均不足。

### p.36–38：互斥不能自动规定谁先发生

> **p.36** The desired order between two memory accesses is flipped.
>
> i.e., A should always be executed before B, but the order is not enforced during execution.
>
> Example:
>
> The code in Thread2 seems to assume that the variable mThread has already been initialized (and is not NULL).

**课件程序与接口（p.36，原页片段）**

```text
Thread1::
 void init(){
    mThread = PR_CreateThread(mMain, …);
 }

 Thread2::
 void mMain(…){
    mState = mThread->State
 }
```

> **p.37** Solution: Enforce ordering using condition variables

**课件程序与接口（p.37，原页片段）**

```text
pthread_mutex_t mtLock = PTHREAD_MUTEX_INITIALIZER;
 pthread_cond_t mtCond = PTHREAD_COND_INITIALIZER;
 int mtInit = 0;

 Thread 1::
 void init(){
    …
    mThread = PR_CreateThread(mMain,…);

    // signal that the thread has been created.
    pthread_mutex_lock(&mtLock);
    mtInit = 1;
    pthread_cond_signal(&mtCond);
    pthread_mutex_unlock(&mtLock);
    …
 }

 Thread2::
 void mMain(…){
    …
```

**课件程序与接口（p.38，原页片段）**

```text
// wait for the thread to be initialized …
    pthread_mutex_lock(&mtLock);
    while(mtInit == 0)
        pthread_cond_wait(&mtCond, &mtLock);
    pthread_mutex_unlock(&mtLock);

    mState = mThread->State;
    …
}
```

原例创建线程的返回值要赋给mThread，但新线程可能在赋值完成前运行并访问 `mThread->State`。它需要“初始化完成后才能用”的顺序保证。课件用mtInit谓词、mtLock与mtCond：初始化完成后持锁设1并通知；使用者持锁while等到1再继续。只各自加锁却允许使用者先抢到，仍不满足先后关系。

### p.39–41：画出谁持有、谁等待

> **p.39** The presence of a cycle
>
> Thread1 is holding a lock L1 and waiting for another one, L2.
>
> Thread2 that holds lock L2 is waiting for L1 to be release.

> **p.40** Reason 1:
>
> In large code bases, complex dependencies arise between components.
>
> Reason 2:
>
> Due to the nature of encapsulation
>
> Hide details of implementations and make software easier to build in a modular way.
>
> Such modularity does not mesh well with locking.

> **p.41** Example: Java Vector class and the method AddAll()
>
> Locks for both the vector being added to (v1) and the parameter (v2) need to be acquired.
>
> The routine acquires said locks in some arbitrary order (v1 then v2).
>
> If some other thread calls v2.AddAll(v1) at nearly the same time  We have the potential for deadlock.

**课件程序与接口（p.41，原页片段）**

```text
Vector v1,v2;
 v1.AddAll(v2);
```

两锁原例T1先L1后L2，T2先L2后L1；在各取得第一把后，图形成T1等L2、L2由T2持有、T2等L1、L1由T1持有的环。封装可能隐藏获取次序：`v1.AddAll(v2)` 与 `v2.AddAll(v1)` 看似对象方法，内部却以相反次序取两对象锁。

**补充：用一张等待表把“程序不动了”变成可证明的死锁。** 沿两锁原例，在T1成功取得L1、T2成功取得L2之后：

| 线程 | 已持有 | 下一步等谁 | 能解除等待的动作 |
|---|---|---|---|
| T1 | L1 | L2 | T2释放L2 |
| T2 | L2 | L1 | T1释放L1 |

两线程都在阻塞式获取第二把锁，释放各自第一把锁的语句又位于后面，所以没有一方能执行解除对方等待的动作。若只是T1等待L2、T2正正常计算并最终释放，则不是这个死锁；等待需要结合持有关系与可执行路径判断。

统一锁序的证明也从表出发：所有线程只能持较小编号再请求较大编号，一条等待链的锁编号严格增加，有限集合中不可能沿链回到更小的起点。该证明依赖所有参与者遵守同一个顺序，嵌套函数内部获取的隐藏锁也算，不能只检查当前函数显式出现的两行。

### p.42–44：破坏必要条件来预防

> **p.42** Four conditions need to hold for a deadlock to occur.
>
> If any of these four conditions are not met, deadlock cannot occur.

> **p.43** Provide a total ordering on lock acquisition
>
> This approach requires careful design of global locking strategies.
>
> Example:
>
> There are two locks in the system (L1 and L2)
>
> We can prevent deadlock by always acquiring L1 before L2.

> **p.44** Acquire all locks at once, atomically.
>
> This code guarantees that no untimely thread switch can occur in the midst of lock acquisition.
>
> Problem:
>
> Require us to know when calling a routine exactly which locks must be held and to acquire them ahead of time.
>
> Decrease concurrency

**课件程序与接口（p.44，原页片段）**

```text
1    lock(prevention);
2    lock(L1);
3    lock(L2);
4    …
5    unlock(prevention);
```

死锁四个必要条件是互斥、持有并等待、不可强制抢占、循环等待。全局锁序L1<L2让所有线程都先L1后L2，消除环。p.44用prevention锁串行化整批获取，意图避免多个线程各拿一部分再互等；所有参与者须遵守协议且预先知道所需锁。

课件说这种写法保证获取中不会发生不合时宜的线程切换，措辞不精确：mutex不禁止调度切换，它限制其他遵守同一prevention锁的线程同时进入获取阶段。持有业务锁的旧线程如何释放也须不依赖该prevention锁，否则仍可能另造依赖。

**表（p.42）：课件完整字段与状态。** 下表保留原页术语和数值；读写轨迹的同一格按原页由上到下排列，空格以“—”表示。

| Condition | Description |
|---|---|
| Mutual Exclusion | Threads claim exclusive control of resources that they require. |
| Hold-and-wait | Threads hold resources allocated to them while waiting for additional resources |
| No preemption | Resources cannot be forcibly removed from threads that are holding them. |
| Circular wait | There exists a circular chain of threads such that each thread holds one more resources that are being requested by the next thread in the chain |

### p.45–46：失败释放再试，仍可能活锁

> **p.45** Multiple lock acquisition often gets us into trouble because when waiting for one lock we are holding another.
>
> trylock()
>
> Used to build a deadlock-free, ordering-robust lock acquisition protocol.
>
> Grab the lock (if it is available).
>
> Or, return -1: you should try again later.

**课件程序与接口（p.45，原页片段）**

```text
top:
    lock(L1);
    if( tryLock(L2) == -1 ){
        unlock(L1);
        goto top;
    }
```

> **p.46** livelock
>
> Both systems are running through the code sequence over and over again.
>
> Progress is not being made.
>
> Solution:
>
> Add a random delay before looping back and trying the entire thing over again.

原伪代码先L1，尝试L2失败就释放L1重试。它避免抱着L1阻塞等L2，却可能两线程同步重试、同步失败，忙着执行而无进展，即livelock。随机退避有助于打散节奏，但不是对任意调度的绝对完成证明。

课件把tryLock失败写-1，是其伪接口约定；pthread_mutex_trylock真实返回非零错误码，不能直接照抄 `== -1`。

### p.47–48：CAS循环需正确原子和成功条件

> **p.47** wait-free
>
> Using powerful hardware instruction.
>
> You can build data structures in a manner that does not require explicit locking.

**课件程序与接口（p.47，原页片段）**

```text
int CompareAndSwap(int *address, int expected, int new){
    if(*address == expected){
        *address = new;
        return 1; // success
    }
    return 0;
 }
```

> **p.48** We now wanted to atomically increment a value by a certain amount:
>
> Repeatedly tries to update the value to the new amount and uses the compare-and-swap to do so.
>
> No lock is acquired
>
> No deadlock can arise
>
> livelock is still a possibility.

**课件程序与接口（p.48，原页片段）**

```text
void AtomicIncrement(int *value, int amount){
    do{
        int old = *value;
    }while( CompareAndSwap(value, old, old+amount)==0);
 }
```

CompareAndSwap原子比较当前值与expected，相等则改new并按本讲约定返回1，不等返回0。原增量例应不断读old、尝试old+amount，直到CAS成功。p.48把old声明在do块内却在while条件引用，普通C作用域不成立；下面是校正后的机制伪代码：

```text
do:
    old = atomic_load(value)
while CAS(value, old, old + amount) == 0
```

CAS重试算法可能使某线程无限失败。课件用wait-free称呼过宽：wait-free要求每个线程在有限自身步骤完成，仅“没显式锁”不足以证明。原子类型和内存顺序也需按真实语言接口处理。

### p.49–50：链表插入的两个修复与一处条件错误

> **p.49** More complex example: list insertion
>
> If called by multiple threads at the “same time”, this code has a race condition.

**课件程序与接口（p.49，原页片段）**

```text
void insert(int value){
    node_t * n = malloc(sizeof(node_t));
    assert( n != NULL );
    n->value    = value ;
    n->next     = head;
    head    = n;
 }
```

> **p.50** Solution:
>
> Surrounding this code with a lock acquire and release.
>
> wait-free manner using the compare-and-swap instruction

**课件程序与接口（p.50，原页片段）**

```text
void insert(int value){
    node_t * n = malloc(sizeof(node_t));
    assert( n != NULL );
    n->value = value ;
    lock(listlock); // begin critical section
    n->next = head;
    head    = n;
    unlock(listlock) ;  //end critical section
 }
```

**课件程序与接口（p.50，原页片段）**

```text
void insert(int value) {
    node_t *n = malloc(sizeof(node_t));
    assert(n != NULL);
    n->value = value;
    do {
        n->next = head;
    } while (CompareAndSwap(&head, n->next, n));
 }
```

原无锁插入先 `n->next=head` 再 `head=n`；两个线程读到同一个旧head时，最后写head的人会使另一新节点不可达。互斥版锁住这两步即可；节点私有初始化可在锁外做。

CAS版每次令n->next等于当前head，再尝试把head从该旧值改为n。按p.47“成功返回1”的约定，p.50的 `while(CompareAndSwap(...))` 条件写反：应在 `==0` 时重试。否则成功后再循环甚至可能令n->next指向n而形成自环。该校正只讨论插入核心机制，完整无锁结构还涉及内存回收等课件未展开问题。

### p.51–53：避免法牺牲一部分并行度

> **p.51** In some scenarios deadlock avoidance is preferable.
>
> Global knowledge is required:
>
> Which locks various threads might grab during their execution.
>
> Subsequently schedules said threads in a way as to guarantee no deadlock can occur.

> **p.52** Example of Deadlock Avoidance via Scheduling (1)

> **p.52** We have two processors and four threads.
>
> Lock acquisition demands of the threads:
>
> A smart scheduler could compute that as long as T1 and T2 are not run at the same time, no deadlock could ever arise.

> **p.53** Example of Deadlock Avoidance via Scheduling (2)

> **p.53** More contention for the same resources
>
> A possible schedule that guarantees that no deadlock could ever occur.
>
> The total time to complete the jobs is lengthened considerably.

第一张原需求表：T1、T2都用L1/L2，T3只用L2，T4无锁。使T1/T2不重叠，并让T3/T4在另一CPU运行，可避开二者相反取锁造成的环。第二张T3也需两锁，于是把T1、T2、T3串行，T4另核运行，并行机会更少。

### p.54–55：检测恢复与整讲回看

> **p.54** Allow deadlock to occasionally occur and then take some action.
>
> Example: if an OS froze, you would reboot it.
>
> Many database systems employ deadlock detection and recovery technique.
>
> A deadlock detector runs periodically.
>
> Building a resource graph and checking it for cycles.
>
> In deadlock, the system need to be restarted.

> **p.55** Semaphore
>
> Definition: sem\_init(), sem\_wait(), and sem\_post()
>
> Applications: Lock, Condition Variable, Producer/Consumer, Read/Write Locks, and Dinning Philoshpers
>
> Common Concurrency Problems
>
> Non-deadlock bugs
>
> Atomicity Violation and Order Violation
>
> Deadlock bugs
>
> Conditions of deadlock
>
> Prevention
>
> Next: Review

检测允许死锁发生，再发现依赖环、选择恢复动作。单实例锁的等待环可证明死锁；多实例资源须更细判断，不能对任意资源图见环就下结论。课件举重启，数据库也可中止并回滚部分事务，未必重启整个系统。

最后按故障问诊：检查与使用被插队→原子性；初始化前使用→顺序；彼此占有并相互等待→死锁；一直重试无进展→活锁；某线程长期拿不到机会→饥饿。它们需要不同证据和修复。

:::hint 自测：CAS循环没有mutex，为什么仍不能直接称为wait-free？

设T1每次读出old后，T2都抢先成功修改同一原子对象，T1的CAS就不断失败。系统整体可能不断前进，但T1没有有限自身步骤内完成的保证，所以不能仅凭没有阻塞锁断言wait-free。

还要区分另一风险：链表节点可能被删除并重新利用，旧指针数字再次出现并不保证仍是原对象。p.50只展示插入核心，不足以证明任意含删除和回收的并发链表都安全；必须另有对象生命周期方案，不能把CAS当成自动内存回收器。

:::endhint
