p.80 Outline，进入 CFG 与程序语言。

### 编译器中 parser 的位置（p.81–83）

p.81 把程序与机器指令并列，目标是将结构化源程序变成低层执行步骤。图（p.82）：source file→lexer→token流→parser→parse tree→codegen→object code。看什么：词法分析先把字符分成记号，语法分析再判断记号组合结构，代码生成消费该结构。图底部人名是原课件背景，不用于推导算法。

p.83 parser 必须知道语言文法。它不能只靠“这个字母出现过”来确认整个程序合法，因为合法性涉及记号之间的嵌套和顺序。

### 从程序规则到表达式树（p.84–86）

p.84 的 PROGRAM 展开为语句列表，列表递归地产生分号分隔的语句，STMT 可以是表达式、if、while 或花括号块。这里的文法是演示结构，不承诺已消除前面讲过的算术及 else 歧义。

p.85 输入 `10 + 2 * 5`，文法 $E\to E+E\mid E\ast E\mid INT$ 给出 $E\Rightarrow E+E\Rightarrow E+E\ast E\Rightarrow10+E\ast E\Rightarrow10+2\ast E\Rightarrow10+2\ast5$。INT 表示词法得到的整数记号，具体10、2、5由记号携带。p.86 对应树根为加，右子树为乘。原推导不是严格最左推导，但仍是合法一般推导；不要因展开了右变量就说它无效。

### 结构决定代码生成顺序（p.87–89）

p.87 图先生成 `mult a, 2, 5`，再 `add b, 10, a`：临时变量 a=10，b=20。乘法子树先产生可供父加法使用的结果，正是依赖关系而非版面顺序决定执行次序。

p.88 BNF 用 `::=` 写产生式、尖括号写非终结符，表达能力仍沿用文法思想；LL、LR 是可线性解析的受限文法类，不能由此推出任意 CFG 都线性可解析。p.89 区分语法与语义：赋值语句可符合结构规则，却可能在类型或含义层面不合要求。页面把“given CFG is inherently ambiguous”并列为难题；术语上固有歧义属于语言，文法本身谈歧义，两者不要混用。本页没有给判定算法，因此不能把“难”误读成已有可运行的慢算法。

p.90 Questions 结束页。

**考试角度**：（C 级 通识）常见考法是解释 token、语法树与代码生成的分工，或按树的依赖顺序求表达式值。

### 同一输入沿编译数据流走到底（补充）

继续用正文的 `10 + 2 * 5`。lexer 先把两个字符 `1`、`0` 合成一个整数 token，它的种类为 INT，附带值为10；后面依次为 PLUS、INT(2)、TIMES、INT(5)。parser 读取的是这些 token 的种类与顺序，建立加法根、整数10左子树和乘法右子树。树中的 INT 并不是运行时值本身，词法附带的数值才让后续计算知道是10而不是任意整数。

codegen 按子树依赖产生临时结果：先令 t1=2×5=10，再令 t2=10+t1=20。t1 从乘法完成开始有效，直到加法使用后才不再需要；若优化器复用保存 t1 的位置，必须在它最后一次被读取之后，不能提前覆盖。这是临时值的生命周期，不是要求源程序一定声明这两个变量。

排查失败也按接口定位：`10 + * 5` 的字符和记号都可能合法，但记号组合缺操作数，parser 可拒绝；`x + 5` 可能语法合法，却需后续查 x 是否声明、类型是否支持加法。若树正确但结果成60，检查是否误用了“先加后乘”的执行结构，不能只归咎于 lexer。每一阶段的输入、输出和保证不同，分开检查才知道错误在哪里。

:::hint 自检：一段程序通过 CFG 语法检查，能否保证运行不出错？

CFG 检查的是结构，哪些事实还没由它检查？

:::hint 展开推理与答案

不能。变量绑定、类型约束、数组越界或除零等通常不由这里的 CFG 单独保证；有些由静态语义检查处理，有些取决于运行数据。语法树可作为后续检查的输入，但它不是程序安全或正确性的全部证明。

:::endhint
:::endhint
